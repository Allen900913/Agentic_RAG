## 零、五條判讀鐵律

每一條都被違反過至少一次：

1. **先問「這個差值超過噪音嗎」，再問「為什麼」。** MDE（95%, n=100）換算成「要幾題從 0 修到 0.5」是 **4~7 題**，而典型 ingest 改動只動 2~5 題。**不要拿落在噪音裡的數字反推機制——機制聽起來越合理越危險。**
2. **任何機制宣稱都要先有能證偽它的確定性測試**（零 LLM、可重跑、無抽樣變異）＋ 變異測試。實測有四個「聽起來合理」的機制假設被自己的測試推翻。
3. **稽核回傳「0 筆問題」先當壞消息查；稽核回報 FAIL，先問「是不是量尺錯」。** 兩個方向的查證成本一樣是一次 `grep`，而錯誤結論會被寫進文件。
4. **量尺不可與被測物耦合**（犯過六次）。① 量尺讀了修法會改動的產物 ② 量尺**自備輸入**，於是從來沒驗過生產供不供得出那個輸入。
5. **N/A 不能併進 PASS。** 它是「這一輪沒量到東西」不是通過——量尺不會自己說「我這次沒量到東西」。

## 二、量測噪音與重放快取

**核心事實：這個專案的量測解析度比多數改動的效果粗一個數量級。**

| 噪音層 | 實測 | 量法 |
|---|---|---|
| RAGAS judge | `context_precision` **0.046**；`answer_correctness` **0.012** | 同一份結果檔重評兩次 |
| Plan 節點 | **12/25 題（48%）子問題不同** | 同輸入連呼叫兩次 |
| query 英譯 → 檢索 | **47/100 題 top-8 不同** | 同組態完整重跑兩次 |

**`temperature=0` 不等於確定性**：MoE 的溫度只固定取樣、不固定專家路由。
**MDE（95%, n=100）**：recall 0.029／precision 0.036／faithfulness 0.028／correctness 0.019 → **要幾題從 0 修到 0.5＝4~7 題**。

### 噪音常數的兩個陷阱
⚠ **一對樣本只是噪音的一次抽樣，不是噪音的上界。** `NOISE["answer_correctness"]` 一度定成 .007（單一對），據此把一個 −.009 判成「略高於噪音的下降」並開始找機制——**它是假的**（同一份輸入再餵一次就差 .012），改用同期基準重比後真實差值是 **+.003**。
> **兩個教訓，第二個比第一個難堪**：① **跨輪比 RAGAS 聚合值 ＝ 把 judge 噪音算進系統差異**。② **寫下警告不等於服從警告**——那支腳本的註解本來就寫著「一對樣本不是噪音的上界」，然後同一段程式仍然用一對定了門檻。**引用任何 `NOISE` 常數之前，先看它是幾對量出來的。**

⚠ **取新舊較大值。** `context_precision` 新測 .005 看起來噪音小了十倍，但舊值 .046 的成因寫在碼上——**precision 對每個 context 做二元判定再依排名加權，最高排名那個判定翻面整題就 1.0→0.0**。**門檻取大只會要求更多證據，錯的方向是安全的那一邊。**

### `llm_replay.py`：把 A/B 變成受控實驗
設 `RAG_REPLAY_CACHE` → 兩臂共用同一份 plan／英譯／Grader 決策／ratio／期間意圖／ticker。

**key 的兩個相反設計，各有理由**：
- plan／translate 的 key **不含 system prompt**——planner 的 prompt 內嵌隨 collection 變動的 coverage snapshot，納入 key 會讓跨 collection A/B 全部 miss。副作用：改 planner prompt 時要手動刪檔。
- checker 的 key **含這次看到的候選 id**——候選變了是**合法 miss**，那正是被測改動造成的差異。

⚠ **blocking 是必要條件不是充分條件**：擋不住 Grader（跨 collection 必然 miss）、生成層 `GEN_TEMPERATURE=0.3`、RAGAS judge。
⚠ **共用一份 fixture 只是 K=1 個 block**。要多 block **不需改碼**（`RAG_REPLAY_CACHE` 是路徑，一個 block 一個檔；**同 block 內必須先後跑**，並行＝兩臂都 miss）。
⚠ 買到的是「兩臂共用同一份中間產物」，**買不到生產端穩定**。固定下來的是「某一次抽樣」不是「正確答案」——**定版後別再重生成**。
⚠ **2026-08-09 起 `strip_citation_footer` 也剝句末 inline 引用**（佔答案本文 25% 字元）→ **當日之後的數字與之前不可比**。剝除的理由是「像比像」不是「分數變好」（實測 correctness 反而 −0.041）——照「分數變低就退回」做就是在 gaming 量尺。
⚠ **「確定性指標」不會自動變確定**：量測路徑上只要還有一次 LLM 呼叫（例如英譯），它就跟 RAGAS 一樣髒。

## 三、量尺飽和：切塊這條路已經到頂

**（提任何 ingest 實驗前必讀。）結論：RAGAS 的檢索類指標已經量不到切塊改動了。**

### (1) 六個指標有五個已達或超過 gold 上限
上限常數＝**把 `reference_answers.json` 原文當成系統答案餵進去評的分數**。2026-09-06 在新 judge（`google/gemma-4-31b-it`）＋ 65 題上整組重量：

| metric | gold 上限 | 系統實測 | 噪音門檻 | 判讀 |
|---|---|---|---|---|
| `context_recall` | .826 | .822 | .017 | 噪音內 |
| `context_precision` | .780 | .769 | .046 | 噪音內 |
| `nv_context_relevance` | .923 | .918 | .012 | **到頂** |
| `faithfulness` | .726 | **.876** | .021 | **已超過（負空間）** |
| `answer_relevancy` | .888 | .859 | .004 | +.029，很窄的第二條細縫 |
| `answer_correctness` | **.987** | **.654** | .012 | **唯一有空間的（+0.333）** |

⚠ **換 judge 沒有動搖這張表的任何一格判讀**（舊 judge 上的落差是 .330，新的是 .333），但**跨 2026-09-04 的絕對值一律不可比**。
⚠ **`faithfulness` 是負空間**：gold 依 `gold_files` 生成、與實際 contexts 不同源。**往上推等於要求系統比標準答案更保守。停止追。**

### (2) 檢索已經不是瓶頸（RAGAS 視角）
把 100 題按檢索成敗分桶：recall=1.0（44 題）平均 correctness 0.684／0.5~0.99（42 題）0.669／<0.5（12 題）0.543。**檢索完美與檢索全失敗只差 0.141**，就算全修到完美也只 +0.024＝**低於噪音底線**。
**歷史軌跡佐證**：十二次全量跑分，`context_recall` 全落在 0.73~0.77、`answer_correctness` 全落在 0.62~0.66。

### (3) 剩下那 0.33 有多少是真的？部分不是
`answer_correctness` ＝ factual-F1(0.75) ＋ 語意(0.25)，主要由「系統答案 vs 固定 reference 的**詳略對齊**」決定。實例：`lex-07` 答 $7.46、`lex-14` 答 $23.49——**兩題數字都完全正確、引用也對**，correctness 卻只有 0.415／0.424（扣分來自參考答案多寫了佐證陳述）。**它罰的是陳述集合的差異，不是對錯。**
⚠ 但**不能因此說整個 gap 都是假的**：gold 自己拿 .987，代表指標**給得出滿分**；長度比與 correctness 的相關係數只有 +0.125。**目前沒有把「真的答錯」與「陳述顆粒度不同」分開的工具。**

### (4) 但「量尺飽和」是關於量尺，不是關於系統——這兩句被混為一談過
用 chunk 層 gold（[`../eval/probe_chunk_gold_recall.py`](../eval/probe_chunk_gold_recall.py)，41 題×3 輪、翻面 0）量到：**`gold@5 0.878`／`gold@20 0.976`、5/41＝12.2% 的可量題有檢索層缺陷**（1 召回 `sem-05` ＋ 4 排序 `sem-03`／`sem-04`／`mix-08`／`col-03`）。
- **問題的主體是排序不是召回（4:1）**，而排序那四題三輪都一樣。
- **層級歸因**（[`../eval/probe_recall_layer_attribution.py`](../eval/probe_recall_layer_attribution.py)，`experiments/rla_20260911.json`）在修好的 gold 上**四個名額格全部是 0** ⇒ 名額問題結案（RRF 20→30 把它清光），且 collapse／hard filter **兩次都沒有刪掉過 gold**。
- **三段漏斗**（`experiments/gold_funnel_r4_20260911.json`）：② 撈到了被圈選／`COMMIT_TOP_K` 丟掉 **5 題** vs ③ 檢索根本沒撈到 **2 題** ⇒ **能動的在圈選層不在召回層**。
- ⚠ **別把「丟掉 92%」讀成「92% 的損害」**：`mh-03` 單題確實是撈 78 顆只有 6 顆進 `collected`，但全量上 gold 落進 ② 的只有少數。**那是兩個不同的分母。**
- ⚠ **「有缺陷」與「修了有用」是兩個問題**：`forced_pass` 的交叉分析顯示那些題多半不是檢索問題。第二個問題**仍然沒有量尺**。

### (5) 所以還能往哪走
1. **改生成層／Grader 圈選**——唯一還能動 `answer_correctness` 的槓桿。
2. **換量尺**——擴充 `check_number_defects` 的覆蓋率。
3. **接受現況收工。**

## 四、量尺自己壞掉的歷史

### 4.0 為什麼一直錯：五個根因（2026-09-11 歸類）

| **E** | **取樣框架排除了目標** | 1（`probe_kb_content_ceiling` 的陰性對照抽樣自**生產判夠**的子問題，結構上看不到「生產判不夠而事實在 KB 裡」） | **否** | 設計複核項，沒有自動化的尺 |

**C 這次的根因值得逐字記下來，因為它同時解釋了三支尺的誤報。**
`chunk_gold.literal_matcher` 的數字邊界寫成 `(?<![0-9,.])…(?![0-9,.])`，本意是不讓 `1,353` 吃到 `21,353`；但它把**數字的延續**與**一般標點**混為一談 ⇒ **任何後面緊跟逗號或句點的數字一律匹配不到**，而英文散文裡數字後面最常見的正是這兩個。於是 `lex-04` 的 gold 指到兩顆**附件索引**（`3/7/2006`），真正的答案 `With our introduction of CUDA in 2006, we opened …` 一顆都沒收 ⇒ `probe_chunk_gold_recall`／`probe_recall_layer_attribution`／`probe_gold_funnel` **三支尺一起把一個答對且逐字有據的題目報成檢索缺陷**。修好之後 gold 95 → 102 顆。
⚠ **自測表裡本來就有那個 literal 和那句話**：`("2006", "CUDA in 2006", True)`——**它把生產文字的逗號拿掉了**。**這是本 repo 第七次踩到「測資的形狀與生產不同，那條路等於從來沒被測過」**（前六次：⑰i、⑱f、⑳e、⑭j、⑮q、⑲k/⑲m）。
⚠ **兩把尺方向相反也算 C**：`number_claims` 的 `mix-03` 只認捨位後的 `6.4 billion|64 億`，而 `check_rounding_fidelity` 正把「捨成約值」當缺陷在量 ⇒ 答案寫精確值 `63.98 億（$6,398 百萬）` 反而被判 FAIL。**同一件事在兩支腳本裡有相反的期望，比任何一邊判錯都糟。**
⚠ **B 家族有一個反模式要特別記**：把 patch 點從 `ar.` 搬到定義模組確實會讓斷言變綠，但那是**遷就缺陷**——它讓那個裸名呼叫永久隱形。09-11 的連鎖：H2 抓到裸名呼叫 → 呼叫端改 `_pkg.` → ⑰f 的注入點搬回 `ar.` → ⑬a 發現凍結清單少列 → ⑬b 抓到 `graph.py:47` 的 `from .validators import` **壓了一份綁定**＝真正的根。**一個 import 行，四層閘門才挖到底。**

### 4.1 `check_number_defects` 的六次失效
`anchored_pct` 原本用「答案的第一個百分比 vs gold 的第一個」，**四種比法被實測推翻**（比第一個／比任一個／接地後先後找／接地後取最近），每一種都在某個真實 run 上誤報或漏抓。
→ **兩層教訓。第一層：不接地不行**（答案裡有 4~8 個百分比、容差 ±1pt，任何值幾乎都能湊到）。**第二層：接地後「挑哪一個值」也猜不出來**——值在 anchor 前或後都是合法中文寫法。現行做法是問**集合成員關係**（anchor ±N 內的百分比集合），與措辭方向無關。
**第五次（anchor 措辭寫死）**：`col-11` 答對了卻用「雲端營收」這個措辭 → anchor 落空 → 判 **N/A**。**這是最危險的失效方式**：前四次是判錯，這次是**護欄安靜地停止量測**。
**第六次**：切片把百分比 token 剖半（`mix-09` 判 N/A 而答案是對的）。

> ⚠ **判別力由 `forbid_pct` 承擔，不是 `expect_pct`**。⚠ **forbid 只在「錯值不會與正解正當並存」時可用**。⚠ **anchor 本質上是詞表**，只能用在已人工驗證過的單一主張上；放寬的判準是「同一主張的其他合法中文寫法」，**不是「把更多數字納進窗口」**。

### 4.2 「量尺與被測物耦合」的六次
①~③ 量尺**讀了修法會改動的產物**（端到端斷言讀 `experiments/`）→ 一修好陽性就消失。④ `_news_freshness_gaps` 的 cutoff 讀真實 KB coverage，KB 拔掉新聞後三條陽性斷言測不出東西。⑤ anchor 措辭寫死 → 靜默 N/A。⑥ **量尺自備輸入**：閘門⑪ 的 8 條斷言全部拿測試自造的 dict 餵進去、全綠，而生產的 `rq.retrieve()` **根本沒把 `period_basis` 放進 chunk dict** → validator 在線上結構性永遠不觸發。

**⑥ 是最難自己發現的一種**：「payload 裡有這個欄位」和「chunk dict 裡有這個欄位」是兩件事，中間隔著一個建構子——而閘門⑪ 原本**有**一條活體斷言在掃 payload、PASS，**正好把人的注意力擋在建構子前面一步**。
→ **通則：驗證器讀哪個欄位，就要有一條斷言拿真實資料餵生產的建構路徑。** 把建構抽成具名函式（`rq._payload_to_chunk`）就是為了讓這件事可測。
**修法要防的是「量尺讀了會被修好的東西」**：閘門② 的陽性答案因此**逐字凍結在測試檔裡，不讀 `experiments/`**。

### 4.3 false-negative gold（五批，全在 eval 側非系統）
reference 誤寫「來源未揭露」但語料白紙黑字有，**系統答對甚至比 gold 準，卻被打 recall=0**。全量稽核 13 題 23 處錯（已全修）：
- **機械層 100% 乾淨**（glob 0 個落空、逐字對齊、無 stale cache）→ **量尺壞掉的地方全在語意層，機械檢查給不出警訊。**
- **10 倍單位錯 6 題 14 處**：來源寫 `$253.49B`，reference 抄成「253.49 億美元」（正解 2,534.9 億）。**對照組證明這不是隨機**——來源是 `(In millions)` 表格時換算全對，**錯的只有「B 結尾」那一種字面**。
- **句內自我矛盾 2 題**（開頭「11.1 億」vs 內文「111.44 億」）→ **同一句話裡對的錯的並存，抽樣看必漏。**
- **期間錯置 2 題**（把 10-Q 的九個月累計當成單季）。

**根因＝防護「有印警告但不修」**：生成端早有兩道防護，但**重試耗盡後只 `print("⚠ 需人工檢查")` 就放行**。同一種病在生成腳本裡共**四處**。
**修法＝勸不動就用程式修**（`repair_yi_against_source`，三條件同時成立才動手，回測 14/14 全抓、0 危險誤報）。
> **寫 guard 時自己踩的兩個坑**：① 幣別標記寫成**可選** → 「10 億**使用者**」被當金額。**漏修無害、改壞有害，一律從嚴。** ② 「後接括號就當已雙寫」太粗 → 敘述性括號被誤跳過。
**方法論：判準要自足。** 有效判準是 ① 雙寫括號內外自洽（`N 億美元（$M billion）` → N==M×10，全庫 0 錯）② 沒雙寫的才逐筆查來源字面單位。⚠ **稽核腳本自身的 regex 也會騙人**：`(?![\w])` 抓不到 `$60.46B` 的尾隨 `B`，害四題被誤標。

### 4.4 其他量尺特性
- **footer 毒害 faithfulness**：答案尾端的引用 footer 是 metadata、context 裡不存在 → 逐 claim 判 unsupported（**這解釋了 lexical 悖論：檢索近乎完美但 faith 全類最低**）。剝除後 faith 0.763 → **0.815**、lexical 0.672 → **0.889**。
- **`context_precision` 對多 chunk 比較題判定器不穩**（同一份正確答案在 0/0.333/1.0 亂跳）。**比較題別信 precision 欄。**
- **`--from-results` 吃多個檔是「拼接同一臂」不是 A/B**：同 id 會被平均，而那個平均正好落在歷史噪音帶裡、看起來毫無異常——**這樣燒掉過 2h49m**。
- **NaN 一定要補完再定稿**：補完前某差值 +0.067（正好卡在門檻上），補完後 +0.063 明確落在噪音內。
- **Python 輸出時 stdout 會被緩衝**（非 tty），背景跑分要加 `-u`。

### 4.5 live 量尺：斷言是零噪音的，輸入不是
`web_claims.json` 的 `_meta` 自稱「零噪音」——**那個性質是從斷言的形式推來的，沒有被量過**。實際量了之後同一份碼、同一個 collection 判定會翻面。
→ **通則：判斷一把量尺是不是零噪音，要看它讀的欄位怎麼產生的，不是看它怎麼比對。**

三層成因，只有第三層是系統缺陷：
1. **fixture key 綁死 LLM 生成的 query 字面**（量尺問題）。⚠ **重錄 fixture 解決不了**，只是換一組會再度 miss 的 key。
2. **刻意的大聲失敗被 catch-all 吞掉**（已修）：`_tavily_search` 對 `FixtureMiss` 是故意 re-raise 的，但確定性 executor 的 `except Exception` 把它接成「降級」，外觀與「系統沒打 web」**完全無法區分**。
   **修法與通則**：把 `FixtureMiss`／`RecordError`／`ReplayCacheMiss` 移出 `Exception` 階層、改繼承 `BaseException`。判準與 `SystemExit` 同一條——**「這不是可以就地處理的錯誤，這是『這次測量無效，停下來』」**。
   → **一個「絕不可被吞掉」的保證，不要寫成契約（呼叫端記得 re-raise），要寫成型別。** 契約是 O(n) 的：全碼庫 16 個 `except Exception`，漏一個就破功，而且破得靜默。
3. **`realtime_need` 對「近期動態」措辭真的會判錯**（已改善：0/3 → 5/5，四題陰性對照不動）。
   → **通則：一個 LLM 分類欄位失手時，先問「是 prompt 沒講清楚，還是架構把太多責任壓在它身上」。** 這次是前者（prompt 從頭到尾沒說「候選全是財報不構成填 none 的理由」），成本是幾小時；當成後者去拆架構要幾天，而且拆完仍然要回來寫這幾句話。

### 4.6 續集：flaky 的是 fixture 不是斷言（2026-09-02 結案）
重錄 fixture（綁生產 collection ＋ as-of 2026-09-02）之後跑 7 輪，web-02～05 **全 PASS**。所以 4.5 的翻面**成因是 fixture 綁在拔除新聞之前的世界**，不是斷言在抖。
⚠ **判讀這種「全部一致」的結果一定要配一個反向證據，否則分不出「量尺穩」與「量尺死了」**：這裡的反向證據是**四輪每一題的答案全都不一樣**（沒有任何一題在任兩輪逐字相同）。LLM 一直在變、判定不動 → 斷言真的只測「不論 LLM 挑哪個來源都成立」的性質。

### 4.7 Tavily 的回應會隨時間變——「重跑一次相同」不等於「系統性」
重錄時某 query 拿回 12 筆垃圾，我把該筆刪掉、**強制重打一次**拿回**逐字相同**的結果，於是判定「系統性不是偶發」，還據此寫了一條 BACKLOG 缺陷、把斷言標成 `blocked`。**那個推論是錯的——約一小時後同一句拿回 5/12 有值、top 0.899。**
⚠ **相隔十分鐘的相同回應，同樣可以只是 API 在快取那個 query。** 少的對照不是「再錄一次」，是**時間上分得夠開的一次**。
→ **通則：對外部服務下「這是系統性的」這種結論，重複必須跨越它的快取尺度。**（與「MoE 不固定路由，`--repeat 3` 以上」是同一條規則的另一面：那裡要跨越**取樣**噪音，這裡要跨越**快取**。）
**副產品是一個 null result**：`probe_web_query_form` 第一輪看起來像「query 帶 ticker 大幅改善命中」，**三小時後的第二輪沒有重現**（同一句 query 的 top 分數兩輪間 0.377 ↔ 0.899）。**不動 `_web_query_en`。**

## 五、多年語料：損害與收益兩半

KB 原本只有**一年**（21 份），所以「答錯期別」結構上幾乎不可能發生——**過去所有評測分數都是在這個保護傘下拿到的**。2026-08-19 補到 77 份壓測，08-27 升生產。**決定的兩半必須都量。**

### 5.1 損害：硬 filter 全吸收，沒提期間的題全崩

| intent | Δgold@5 | Δ排擠率 | Δ錯期率 | Δ兄弟密度 |
|---|---|---|---|---|
| **relative**（最新一季） | **±0.000** | +0.009 | **±0.000** | **+5.62**（1.90→7.52） |
| none（問題沒提期間） | −0.120 | **+0.400** | +0.120 | +2.48 |
| explicit（明講年份） | −0.333 | +0.200 | +0.333 | +3.34 |

① **結論跟直覺相反：競爭密度上升最多的那一類完全沒有退步**——`relative` 的兄弟密度漲了 4 倍，指標一格都沒動。**metadata 硬 filter 完整吸收了 4 倍競爭。**
② **陽性對照把硬 filter 的價值量化了，而且它隨語料放大**：relative gold@5（路由開→關）在單年是 0.857 → 0.809，在多年是 0.857 → **0.381**；錯期率 0.000 → 0.048 vs 0.000 → **0.476**。**同一個開關的價值放大了約 10 倍**——那條路由在單年是可有可無的優化，KB 一長到兩年就變成不能拔的命脈。⚠ 而它原本靠硬編碼詞表觸發，**漏一題的代價從「差一季」變成「差兩年」**——這就是把它換成 LLM 判斷的理由。
③ 真正壞掉的是「問題沒提期間」那類（沒有任何 filter 會觸發）。
④ **F1（排擠）遠大於 F2（錯選）：68 個浪費席位 vs 4 題錯期** ⇒ **病灶是多樣性不是期別選擇**。⚠ **拆開報這兩個指標是必要的**。
⑤ **最有說服力的單例，也是文獻沒涵蓋的 failure mode**：`col-02` 的 top-5 有 4 席被 MSFT 三個年度 10-K 的同一節佔滿（Item 1／1A 年年 80~90% 逐字相同，embedding 與 cross-encoder 兩層都分不出來）。查過的 temporal IR survey **沒有處理「同一份文件跨年份的近重複」**（學界 benchmark 是新聞／知識圖譜，文件之間本來就不會逐字重複）。**這是財報 RAG 特有的，不能指望照抄論文。**
⑥ **盲區**：少數題的 filing gold 連候選池都進不去（被 news 硬路由攔掉）。**那是別的缺陷，不是期別干擾**，表格上獨立列成「池外」一欄就是為了不讓下一個人誤讀。

### 5.2 兩個修法與四次自我否決

| 組態 | gold@5 | 錯期率 | 排擠率 | explicit | relative | none |
|---|---|---|---|---|---|---|
| **單年 `mdna`** | **1.000** | **0.000** | 0.062 | 1.000 | 1.000 | 1.000 |
| 多年 ＋ B | 0.933 | 0.067 | 0.213 | 0.667 | 1.000 | 0.920 |
| **多年 ＋ A ＋ B**（現行） | 0.956 | 0.044 | 0.204 | **1.000** | 1.000 | 0.920 |

- **A（`RQ_PERIOD_INTENT_LLM`）**：`explicit` 類 0.667 → **1.000**、錯期率減三分之一。
- **B（`RAG_CROSS_PERIOD_COLLAPSE`，`keep=2`／`prefer=newest`）**：純 Python、零 LLM、零額外延遲，**在單年上逐題 no-op、在多年上自己生效**。「資料還不需要時不作用、需要時自己生效」才是敢翻預設的理由。
- **殘餘落差全在 `none` 類**（45 題掉 2 題）——**那一類沒有任何 filter 會觸發**。
- ⚠ **A 與 B 不能分兩次做**：B 的趨勢題保護要靠 A，而多年語料上線時 A 沒開會讓當期題退步。

**四次自我否決（四個都是我提的，四個都錯）**
1. **`prefer="rank"`（留 rerank 最高那份）——嚴重退步**（gold@5 0.837 → 0.653）。**cross-encoder 對年份無感**，「分數最高」與「對的年份」無關。**降低排擠卻換來 F2，正是原本要防的東西換個方向發作。**
2. **`prefer="hybrid"`——等於不修**，還多刪一個 gold；而樸素的「兩個最新」剛好涵蓋那些題。**有原則的設計輸給運氣好的設計，就採用後者並寫下它是運氣。**
3. **`keep=1`——聚合最好，但那是拿趨勢題換的**（趨勢題期別數 −38%，且會讓單年 collection 退步）。⚠ 原本還寫了「新增 3 個沉默失效」，逐題人工讀原文後**撤回**（全是量尺假陽性）。⚠ **反過來也不能說 `keep=1` 安全**——這組 gold 裡沒有一題能證偽它，那是測資不足。
4. **A 的第一版讓 `relative` 退步 0.095——兩個設計錯，不是 LLM 判錯**：① `granularity=None` 時 `ladder_pick` 挑了「所有類型裡最新的」＝年報，**預設方向被我弄反了**（舊的詞表路由本質上是季路由）② 「這一季…跟去年同期相比」LLM 判 `range` **語意上完全正確**，錯的是我把 `range` 對應到「不注入 filter」——**財報有個領域事實**：單一份 10-Q 本身就含去年同期對照。

**A 為什麼不能併進 `parse_query_filters`**：那個函式前面有 `_FILING_HINT_RE` 詞表閘門，實測**擋掉 21 題 `relative` 裡的 20 題**。那道閘門的正確性論證（「這類 query 的 LLM 本來就只會回空」）**只對『抽取明確約束』成立**，而 `period_ref` 問的正是隱含意圖。

### 5.3 收益：歷史題探針
**造題階段就被自己的前提檢查擋下兩次**：① 原本舉的例子是錯的（「Apple FY2024 的總營收」單年 KB 本來就答得出來——10-K 損益表自帶三年、MD&A 自帶兩年）⇒ **真正的收益區從 T-3 才開始**，拿 T-1／T-2 造題會憑空灌出一倍以上的「收益」。② gold 由 `literal` 在 collection 裡確定性定位 ⇒ 「gold 是哪幾份」與前提檢查「這個事實在單年 KB 到底在不在」**是同一個操作**（當場擋掉兩個候選題）。

| | 單年 `mdna` | 多年＋A | 多年（A 關） |
|---|---|---|---|
| historical：gold 進 top-5 | 0（**定義使然**） | **17/18** | 17/18 |
| historical：同節別期席位 | **33/90** | 10/90 | 10/90 |
| control：gold 進 top-5 | 4/4 | **4/4** | **3/4** |

1. **收益是語料買到的，不是修法買到的**（historical 那幾列 A 開與關完全一樣）。兌現率 0.944——⚠ 剩下的 0.056 才是這一列的資訊：**語料裡有 ≠ 撈得到**。
2. **單年 KB 對歷史題不是空手**（多數題 top-5 至少有一席是「同一節、別的年份」）。⚠ 這是檢索層的**風險**不是實害（見 5.4）。
3. **當期題的損害是 A 擋掉的**（control 三列只在 A 關掉時才動）。

**兩個 FAIL 的成因不同，而且都不是「年份太多」**
- **`bh-07`——命中比落空更糟。** A 正確解析出 `fiscal_year=2023`，問題是**它命中了**：`fiscal_year` 與 `report_label_year` 的**雙座標系 OR** 讓 `MSFT_10Q_202312`（財年其實是 FY2024 Q2）被撈進來，而真正含答案的年報被擋在門外。**對照組就在同一份結果檔裡**：問 FY2022 時語料裡沒有任何 fiscal_year 2022 → Tier 1 落空 → **一降級 rerank 立刻把三年表排到第 1**。**落空會觸發救援，命中不會。** ⚠ **回頭查證更嚴重：這不是多年語料的問題，單年 collection 上就在發生**（問「Microsoft 2025 財年營收」top-5 五席全是 `MSFT_10Q_202512`）。→ **這是「先問是不是量尺錯」的反向版本：量尺沒叫，不代表系統沒壞。**
- **`bh-14`——實體解析，不是期別**（「AWS」沒被解析成 AMZN → Tier 3 退回無 filter → 跨公司污染）。**併成一個「多年語料的損害」數字，就會把兩個該修在不同地方的缺陷誤診成同一個。**

⚠ **這把尺的極限**：historical 那一列**沒有陽性對照**（A 開關一樣，而單年臂的 0/18 是定義使然）＝間接證據；而且**這支量的是檢索，不是生成**。

### 5.4 生成端：擔心的那件事沒有發生

| | before（單年） | after（多年） |
|---|---|---|
| 答對 | **0/18** | **16/18** |
| 承認問到的期間不可得（誠實） | **18/18** | 2/18 |
| **拿別年份硬答且沒交代** | **0** | **0** |

**危險態兩臂都是 0。檢索層的風險沒有兌現成生成層的實害**——這是「不要把檢索指標直接讀成答案品質」的一個乾淨反例。

**量尺被自己的資料推翻三次，每次都是「答對了卻被判成危險態」**：① 用 `looks_like_refusal()` 判誠實 → 整片判錯（那個函式問的是「整份都不作答」還帶 150 字上限，而最典型的誠實答案是**長的**）② 詞表漏英文與兩個中文措辭 ③ `literal` 是英文片語而答案是中文 → 把兩個職責拆開（`literal` 管前提檢查與 gold 定位，`answer_literals` 管「答案有沒有講出來」）。

**最重要的副產品：值不存在 ≠ 事實不存在。** 兩題「在單年 KB 其實答得出來」——10-K 的補充未審計表帶著**重述後**的值，而前提檢查比對的是原始值。⚠ **抓到它們的不是前提檢查，是生成端這一輪** ⇒ `check_historical_generation.py` 的 before 臂實際上是**比值比對更強的前提檢查**。

### 5.5 升生產的驗收：≥2 輪這條規則當場救了一次
多年 r1 的 `check_number_defects` 是 7/1/0、r2 是 8/0/0。那個 FAIL **不是升生產造成的**，三個獨立證據缺一都還不能下結論：① 穩定性表顯示它在兩個 collection 上都在跳 ② 它引的五個 chunk **全部在單年 KB 裡**——因果鏈第一環根本不成立 ③ 這條主張的註記早就記過同一個失效在單年 r2 上發生過。
⚠ **如果只跑 r1 就收工**，這裡會寫成「升生產讓指標從 8/0 掉到 7/1」，然後大概會花半天去追一個不存在的期別干擾。
**新增的舊 filing 是真的有在用**：多年 r1 引用的 217 個 chunk 有 45 個（20.7%）來自新增的舊年度 filing，涉及 23/65 題。

### 5.6 期別探針的 gold 人工複審（引用 gold@k 的收益數字前必讀）
① gold 的指稱沒有被新資料破壞（14 組全等）。② **46/49 的 gold 就是該 `(ticker, form)` 最新的那一份，而 collapse 的規則正是「留最新」** ⇒ `gold@k` 對它**結構上偏袒**。**引用增益時必須同時講這一句。** ③ 那 3 題「gold 不是最新」的陰性對照人工查證後**全部無效**。④ `wrong_period` 對「定性答案」會假陽性（四個案例兩真兩假）。⑤ 萬用字元 gold 凍結後會**過嚴**（方向與②相反）——**這把尺在那幾題上是低估不是高估**。
**兩把想取代人工的聚合尺都失敗了，原因都是老坑**：「gold 句子在舊 filing 逐字重現率」被章節樣板句稀釋；「標準答案的數字在不在 gold 檔裡」49 題有 23 題報「對不上」而**全是單位換算**。

### 5.7 Tier 1「命中」不等於「答得了」
承 `bh-07`。**這是這個專案第一個「先在量尺上抓到、再回頭在生產上複現」的缺陷。**
**先量清楚那半個 OR 買到什麼**（掃 77 份 filing）：**10-K 的 `fiscal_year` 與 `report_label_year` 永遠相等（21/21）**，10-Q 則有 15 份不等 ⇒ **那半個 OR 的全部效果，就是額外放行「曆年標籤是 V、財年不是 V」的 10-Q**。
**修法**：`tier1_hit_is_qualified(filters, fused)`——Tier 1 撈到東西之後再問一次「這批裡有沒有任何一個的 `fiscal_year` 真的等於問的年份」，沒有就當落空、照常降級。⚠ **`fiscal_year` 為空的點算合格**（News／Fundamentals，一起判不合格就是誤殺）。
**65 題題庫一題都不受影響——這正是它從沒被抓到的原因，不是它不重要。**
**留下的代價**：曆年語意的年份查詢也被趕去 Tier 2，**內容沒變差**，變的是多一句揭露語——而舊措辭是**自相矛盾**的（「沒有 2025 的資料，改用最接近的（…2025）」）。⚠ **這句同時是使用者可見句與注入 generator 的事實，說錯比不說更糟**；改成講「所詢問**財年**」之後才成立。
⚠ 閘門的判別力在 **⑥b**：⑥a 全餵合成 payload，**哪天 ingest 讓 10-K 的兩個欄位也分歧，⑥a 照樣全綠而整個推理前提會崩**。

## 六、KB 拔除新聞

**（看到 news 類題目或分數變動前必讀。）**

|  | 記錄（filing／Fundamentals） | 流（news） |
|---|---|---|
| 權威性 | 法定揭露 | 聚合站與評論 |
| 時間標籤 | `fiscal_year`＋`fiscal_period` | **payload 覆蓋率 0%** |
| 正確性判準 | 期別對＋有引用＋數字可驗 | 夠新＋來源可信 |

這個專案為期別正確性做的每一層**對新聞沒有一項成立**。
**資料實況（拔除前實測）**：24 檔／98 chunks ＝ 生產 collection 的 **2.5%**；日期停在 2026-07-21；分佈極不均；4 檔是影片逐字稿。**最尖銳的一項**：28 條來源標記有 **17 條（61%）**來自本專案自己的 `WEB_ALLOWED_DOMAINS` 會拒絕的站——**你已經定義過「什麼算有編輯流程的財經新聞」，而 ingest 進 KB 的新聞六成不合自己的標準。**
**代價與收益**：新聞佔 2.5% 語料，卻是拔除前**最大的殘留檢索失敗**（`looks_like_news_query` 把複合題硬路由到 `doc_type=news`，filing gold 連候選池都進不去）。

**量尺的三個變動——跨 2026-08-19 的分數一律不可直接比**
① 題庫 100 → 63 → 65。⚠ **冷凍不是刪除**：那 37 題是日後驗收「live web 能不能取代 KB 新聞」唯一的現成題庫。
② `check_number_defects` 6 → 4 → 7 條。⚠ **拆分當天掉到 4 條那不是改善是組成變動**。
③ `verify_answer_validators` 閘門④ 一度 FAIL 3 項——**那是量尺失去判別力，不是機制壞掉**。修法是讓閘門**自帶合成 coverage**（而不是刪掉斷言），現在它守的是「新聞若復活，警語必須立刻正確」，**比原本更好**。

**三個機制因此永久閒置（刻意保留，不刪）**：`find_authority_conflicts` 的 news 桶／`_news_freshness_gaps`／`rq.looks_like_news_query`（只剩診斷探針拿它當分類標籤）。**閒置是對的，不是退化。**

**後續：時效警語一度整個死掉。** 拔除新聞時把 `_news_freshness_gaps` 標成「閒置但保留」，**低估了後果**：判準沒有指涉對象 → 警語永遠不印，而風險只是換了位置（即時題 → 打 web → 預算用完 → 回頭用財報生成 → **零揭露**）。
> **教訓：拔掉一個資料來源時，要檢查的不只是「誰會壞」，還有「誰的判準會失去指涉對象」。後者不會拋錯、不會 FAIL，只會安靜地永遠回空。**

**一次「只跑一輪就下結論」的自我打臉**：把 `lex-16`／`lex-17` 去掉新聞子句補回來後，r1 全 PASS，我寫下「根因是新聞污染」並**已經改了 BACKLOG、CHANGELOG 與本檔**；r2 跑完立刻推翻（`MSFT_Fundamentals#0` 沒進池，答 18% 而非 18.30%）。
- **這條管線本來就不是確定性的**，而這個缺陷的觸發**恰恰取決於子問題長什麼樣**——**它自己的記載早就寫過這件事**。
- **「只跑一輪」的危險是不對稱的**：跑出 FAIL 只會讓人多查一次，**跑出 PASS 會讓人宣告修好、還會順手把舊記載改掉**。

**真的被拔除新聞修好的是 `mix-07`**（2/2 從 FAIL 翻成 PASS）——**那一題才是拔除新聞的直接收益**，且是零噪音量到的。

## 七、live web 能不能取代 KB 新聞

**先把問題拆開**：① 這題**會不會**被送去 web（只燒 LLM，`probe_news_web_routing.py`）② web 拿回來的東西**夠不夠**（連網、燒 Tavily）。**① 是 ② 的必要條件**——直接去錄 37 題的 fixture 等於**在不知道有幾題走不到 web 的情況下先付錢**。

**① 路由：不是瓶頸**

| 臂 | 類別 | 觸發 web |
|---|---|---|
| news_set | news ／ **multi_intent** | 13/15 ／ **15/15** |
| news_set | colloquial ／ multi_hop | 2/2 ／ 5/5 |
| control(strict) | lexical／semantic／mixed | **0/6** |

`multi_intent` 那一格最值得看：**最危險的失敗形狀是財報半讓 Grader 判「夠了」而整題不打 web**，實測沒有發生。
**陰性對照踩到的坑**：第一版把「NVIDIA 現在值多少錢」放進 strict 對照，它打了 3 次 web 被記成「浪費」——**錯的是對照不是系統**（市值在 KB 裡是兩個月前的快照，而另一支腳本對同型問題的斷言正是「必須打 web ≥1 次」）。→ **同一件事在兩支腳本裡有相反的期望 ＝ 量尺自相矛盾，那比任何一邊判錯都糟。** 修法是把對照分兩級：`CONTROL_STRICT`（斷言 0 次）／`CONTROL_LOOSE`（只觀察不斷言）。
⚠ **一個不可以拿來下結論的數字**：57% 打滿了 web 預算——**那是樁造成的**（回空字串 → Grader 永遠不滿意）。它唯一能誠實支撐的是 ② 的成本上界。

**② 內容：可信，但發現一個 live 專屬的引用缺陷。** 結果 **PASS 35／FAIL 5**：觸發 web 35/37、答案引用了 web 33/37、引用主機全在白名單（11 個網域）、**地區子網域 0 次**、陰性對照打 web 0/3。5 個 FAIL 全是同一個缺陷（`Reference N, chunk #M` 指向不存在的東西，修法見 [`AGENTIC.md`](AGENTIC.md) A7）。
⚠ **修法生效與「這次剛好沒發生」要分開講**：5 題裡只有 2 題的模型仍吐出序號引用（兩題都被完整還原），**另外 3 題這一輪根本沒吐**——它們的 PASS **不能算在修法頭上**。
⚠ **驗收標準為什麼不是「對照新聞 gold」**：那批 gold 是「2026 年 6 月的新聞說了什麼」，live web 回答「現在的網路說什麼」——**兩個不同的問題**，對照會系統性低估而**低分的原因與 web 好不好無關**。
⚠ **為什麼這批不能用 `numbers_must_be_in_fixture`**：這批題天生是混合的，答案裡 KB 與 web 數字並存（實測某題 20 個數字有 7 個不在 fixture，**逐一讀完全部是 Fundamentals 的值，一個幻覺都沒有**）。**沒有任何字面樣式能把兩種來源分開。**

**對「要不要把新聞放回 KB」的意義**：路由不是瓶頸、來源合規、時效有揭露，**唯一擋在前面的是引用可追溯性，而那是本地程式的缺陷、不是 web 的缺陷**（snapshot 路徑上不存在，也不會因為把新聞放回 KB 而改善）。→ **沒有任何一項證據支持「把新聞加回 ingest」。**

## 八、分類別抵銷效應：單發 vs agentic

**（看到「整體無顯著差異」之前必讀。）**

| metric | 單發 | agentic | 差值 | 判定（噪音 0.067） |
|---|---|---|---|---|
| context_recall | 0.711 | 0.767 | +0.055 | 噪音內 |
| context_precision | 0.772 | 0.835 | +0.063 | 噪音內 |
| nv_context_relevance | 0.860 | **0.963** | **+0.103** | **超過噪音** |
| faithfulness | 0.838 | 0.794 | −0.044 | 噪音內 |
| answer_relevancy | 0.678 | **0.822** | **+0.144** | **超過噪音** |
| answer_correctness | 0.616 | 0.658 | +0.042 | 噪音內 |

**agentic 贏在檢索相關性，但最終答案正確性過不了門檻——不能宣稱 agentic 讓答案更正確。**
`context_recall` 攤開到類別：multi_hop **+0.267**／multi_intent **+0.184**／colloquial +0.142／mixed +0.032／semantic **−0.073**／lexical **−0.078**。**需要多份不同證據的題拿到好處；單一精確詞查找的題被拆解引入雜訊**（lexical 單發已經 0.911，本來就沒有發揮空間）。

**⚠ 三條判讀限制**
1. **分類別的數字個別不顯著**（n=10~15 對應門檻約 0.17~0.21）。有證據力的是「兩個指標下 multi_hop／multi_intent 都排前二、lexical 都墊底」這個**跨指標一致的模式**。
2. **這不是控制變因的 A/B**：agentic 天生檢索多個子問題 → contexts 更多，**機械性地有利於 recall／relevance 類指標**。
3. **量尺在 agentic 這一側也飽和了**（`nv_context_relevance` 0.963 幾乎等於 gold 上限）。

**faithfulness −0.068 查證為量尺偏誤，非幻覺**，三個機制：**拒答紅利**（單管線只剩 1 個聲明 → 1.000；agentic 兩跳都答對 → 0.333）／**雙寫稀釋**（判官逐聲明查字面支持，算術正確的換算形字面不在來源 → 判 unsupported）／長度中介假說**被推翻**。
**真錯誤只有 2 個，且都不是算術**（推翻「LLM 減法弱、該給 calculator」的直覺）：一題把「六個月累計」欄當單季（**減法除法全對，錯在運算元的期間欄**），一題把單一部門當全公司。→ **calculator 對兩題都零效果**：前者會忠實回傳同樣的錯誤答案，後者根本沒觸發運算。**病灶在算術之前的「範圍/期間」選擇。**

## 九、檢索側 LLM 換模型

**為什麼這件事可以零噪音量**：檢索堆疊本身**沒有 LLM**（BGE-M3 → Qdrant → RRF → cross-encoder），檢索側模型只驅動 query understanding，其中兩項輸出是結構化的。

| 配對 | chunk 集合相同 | 平均 Jaccard |
|---|---|---|
| 120b#0 vs 120b#1（**噪音底線**） | 85/100 | 0.9476 |
| 120b#0 vs 20b#0（訊號） | 72/100 | 0.8971 |

**判讀**：候選池**確實**被換掉了（超過噪音），但**換掉的全是無關 chunk**——gold recall 差 0.0020，而同模型跑兩次的差是 0.0014。**結論：檢索側兩個模型等價。** 但方向是反的：20b 在 NIM 上**慢一倍**，所以該做的不是把單發降 20b，而是把 agentic 升 120b。

**三個方法論教訓**
- **字串比對對「翻譯」這種輸出沒有判別力**：86/100 不同，但其中 **68 題是同一個模型自己跑兩次就不一樣**。**唯一有意義的判準是「送進真實檢索器後結果有沒有變」。**
- **量任何「換模型」之前先確認那個模型真的被呼叫**：`parse_query_filters` 有 91/100 題被效率 gate 擋在 LLM 之前 → 這個參數實際只影響 9 題。
- **A/B 兩臂的 LLM 輸出要先錄下來再釘死**，噪音底線用「同模型的第二次跑」而不是憑感覺設閾值。

```bash
    --timeout 900 --nvidia-passes 2
```

- **只改動少數題的 reference 時不必重跑全部 RAGAS**：用 `--ids <題號…>` 只評改動題再拼接回原結果。全部重跑只是多疊一層 judge 噪音。
- ⚠ **部分腳本的 `--output` 預設值仍指向 `eval/`**，跑的時候要自己帶 `--output experiments/...`。
- **新機器還原評測環境**：`python -m venv .venv-ragas` → `pip install -r requirements-ragas.txt`。兩個環境為何不能合併見 [`../README.md`](../README.md) §4-1。
- ⚠ **`answer_correctness` 偏低常是量尺問題**（長度對齊／false-negative gold），不是系統答錯——下結論前先讀第三、四節。

### 反覆出現的方法論教訓（一句話版）
繞過 brain 測 ≠ 真實 graph／先排除工具環境毛病再懷疑系統／單次 LLM-judge 不能論因果、要確定性消融／別過度外推（file-level 無效 ≠ chunk-level 無效）／**prompt 是機率不是保證，grounding 與 citation 要靠 Python 強制、不靠拜託模型**／**提實驗之前先 `ls experiments/`——能證偽假設的測試可能已經跑過了**。
