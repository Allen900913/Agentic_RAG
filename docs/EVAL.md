### 量尺飽和：切塊這條路已經到頂（2026-08-13，**提任何 ingest 實驗前必讀**）

**結論：RAGAS 的檢索類指標已經量不到切塊改動了，`answer_correctness` 的剩餘空間在生成層不在檢索層。**

#### (1) 六個指標有五個已達或超過 gold 上限

上限常數＝把 `reference_answers.json` 原文當成系統答案餵進去評的分數（`eval_ragas_vs_rubric.py` 的 `GOLD_BASELINE`）。它回答「這個指標還有沒有可追空間」：

| metric | gold 上限 | `mdna` 實測 | 判讀 |
|---|---|---|---|
| `context_recall` | 0.766 | **0.770** | 已超過 |
| `context_precision` | 0.822 | **0.831** | 已超過 |
| `nv_context_relevance` | 0.965 | 0.963 | 到頂 |
| `faithfulness` | 0.656 | **0.808** | 已超過（負空間，見〈已接受的極限〉） |
| `answer_relevancy` | 0.842 | 0.831 | 剩 0.011 |
| `answer_correctness` | 0.989 | 0.660 | **唯一有空間的（+0.329）** |

切塊／ingest 改動只能影響前三個檢索指標，而它們全部飽和。**再改也量不到，不是「改動沒效果」而是「尺沒有刻度了」。**

#### (2) 檢索已經不是瓶頸——把 100 題按檢索成敗分桶

| 分桶 | 題數 | 平均 `answer_correctness` |
|---|---|---|
| `context_recall` = 1.0（檢索完全成功） | 44 | 0.684 |
| 0.5 ~ 0.99 | 42 | 0.669 |
| < 0.5（檢索失敗） | 12 | 0.543 |

檢索完美與檢索全失敗只差 **0.141**。就算把 100 題的檢索全修到完美，correctness 也只從 0.660 推到 ~0.684＝**+0.024，低於 0.067 的噪音底線**。而且 44 題檢索完美的題裡只有 5 題 correctness < 0.5。

#### (3) 歷史軌跡佐證

2026-08-06 之後的十二次全量跑分，`context_recall` 全部落在 **0.73~0.77**、`answer_correctness` 全部落在 **0.62~0.66**。整個離散範圍就是噪音寬度。真正的躍升發生在 08-02 → 08-06（correctness 0.585 → 0.626），之後每一次都在同一個平台上擺盪。

#### (4) 剩下那 0.329 有多少是真的？部分不是

`lex-07`（Apple FY2025 Diluted EPS）系統答 **$7.46**、`lex-14`（Meta）答 **$23.49**——**兩題數字都完全正確、引用也對**，`answer_correctness` 卻只有 0.415／0.424。扣分來自參考答案多寫了佐證陳述（分子分母），RAGAS 的 statement-level F1 把它們算成 false negative。**它罰的是陳述集合的差異，不是對錯。**

⚠ 但不能因此說整個 gap 都是假的：gold 自己拿 0.989（85/100 滿分），代表指標**給得出滿分**。量過 `log(答案長度比)` 與 correctness 的相關係數只有 **+0.125**（弱相關），所以也不是單純的冗長度問題。目前沒有把「真的答錯」與「陳述顆粒度不同」分開的工具。

#### (5) 所以還能往哪走

1. **改生成層**——讓 Generator 補齊佐證陳述。唯一還能動 `answer_correctness` 的槓桿，但要先想清楚要的是「答案更好」還是「分數更好」（`lex-07` 現在的答案對使用者已經夠好）。
2. **換量尺**——`check_number_defects` 那種確定性斷言是零噪音的，只是覆蓋率僅 6 題。要數字驅動開發就得擴充它。
3. **接受現況收工。**

### 分類別抵銷效應：整體差值在噪音內 ≠ 兩條管線一樣（2026-08-14，**看到「整體無顯著差異」之前必讀**）

**結論：單發 vs agentic 的 `context_recall` 整體只差 +0.055（噪音內），但那是 multi_hop +0.267、multi_intent +0.184 的大幅領先，被 lexical −0.078、semantic −0.073 的退步抵銷掉的結果。只看整體會得到「agentic 沒用」這個錯誤結論。**

#### 對照條件

兩臂同 collection（`us_stock_rag_edgar_mdna`）、同 100 題、`freshness_mode=snapshot`、web 全程關閉、各自跑一次 RAGAS，n=100 且 **0 NaN**。結果檔 `experiments/ragas_ARM_{single,agentic}_mdna.json`。

#### 整體六指標

| metric | 單發 | agentic | 差值 | 判定（噪音底線 0.067） | gold 上限 |
|---|---|---|---|---|---|
| context_recall | 0.711 | 0.767 | +0.055 | 噪音內 | 0.766 |
| context_precision | 0.772 | 0.835 | +0.063 | 噪音內 | 0.822 |
| nv_context_relevance | 0.860 | **0.963** | **+0.103** | **超過噪音** | 0.965 |
| faithfulness | 0.838 | 0.794 | −0.044 | 噪音內 | 0.656 |
| answer_relevancy | 0.678 | **0.822** | **+0.144** | **超過噪音** | 0.842 |
| answer_correctness | 0.616 | 0.658 | +0.042 | 噪音內 | 0.989 |

**agentic 贏在檢索相關性（兩個指標超過噪音），但最終答案正確性 +0.042 過不了門檻——不能宣稱 agentic 讓答案更正確。**

#### 抵銷效應（本節重點）

`context_recall` 攤開到類別：

| category | 單發 | agentic | 差值 |
|---|---|---|---|
| multi_hop | 0.667 | 0.933 | **+0.267** |
| multi_intent | 0.494 | 0.678 | **+0.184** |
| colloquial | 0.607 | 0.748 | +0.142 |
| mixed | 0.793 | 0.826 | +0.032 |
| news | 0.777 | 0.761 | −0.016 |
| semantic | 0.716 | 0.643 | **−0.073** |
| lexical | 0.911 | 0.833 | **−0.078** |

`answer_correctness` 同向：multi_intent +0.113、multi_hop +0.111 領先；mixed −0.031、news −0.034 落後。

**機制解釋**（與架構預期一致，不是事後編的）：agentic 把問題拆成子問題各自檢索。**需要多份不同證據的題拿到好處**（multi_hop 要串接、multi_intent 要同時撈財報與新聞）；**單一精確詞查找的題被拆解引入雜訊**——lexical 單發已經有 0.911，本來就沒有讓 agentic 發揮的空間，拆解只會把不相關的子問題結果混進候選池。

#### ⚠ 三條判讀限制

1. **分類別的數字個別不顯著。** 0.067 是 n=100 的門檻；n=10~15 對應的門檻約 **0.17~0.21**。除了 multi_hop 的 +0.267 勉強夠看，其餘分類差值**個別都在解析度以下**。有證據力的是「兩個指標下 multi_hop／multi_intent 都排前二、lexical 都墊底」這個**跨指標一致的模式**，不是任何單一數字。
2. **這不是控制變因的 A/B**——但兩個變因裡**有一個已經在 2026-08-14 被排除**。
   - ~~query 前處理模型不同（單發 `gpt-oss-120b`／agentic `gpt-oss-20b`）~~ → **已量，無作用**。見下方〈檢索側 LLM 換模型：候選會動，gold 不動〉：兩個模型的 gold recall 差 0.0020，而同一個模型跑兩次的差是 0.0014。**這一項不必再對齊**，它本來就不影響檢索結果。
   - **仍然成立的那個**：agentic 天生檢索多個子問題 → contexts 更多，**機械性地有利於 recall／relevance 類指標**。要把功勞歸給「agentic 架構本身」，還得先處理這一項。
3. **量尺在 agentic 這一側也飽和了。** `nv_context_relevance` 0.963 幾乎等於 gold 上限 0.965、`context_recall` 0.767 已超過 gold 0.766。檢索類指標對 agentic 已經沒有解析空間，同〈量尺飽和〉。

#### 方法論教訓（各燒掉一次成本）

- **`eval_ragas_vs_rubric.py --from-results` 吃多個檔是「拼接同一臂」，不是 A/B。** 同 id 的多筆會被平均（`load_answers()` 用 `by_id[id].append`）。兩臂丟進同一次會得到**兩臂的平均值**，而那個平均正好落在歷史噪音帶裡、看起來毫無異常——**2026-08-14 這樣燒掉 2h49m**。要比兩臂就各跑一次、各給一個 `--output`。旗標 help 已補上警語。
- **NaN 一定要補完再定稿。** 補完前 `context_precision` 差值是 +0.067（正好卡在門檻上，判定含糊），補完後 +0.063，明確落在噪音內。用 `--ids <失敗題> --nvidia-passes 3 --timeout 300` 只重跑那幾題即可（腳本會 merge 回原輸出），不必整份重來。7 格 NaN 全是暫時性逾時，重跑後歸零。
- **Python 輸出時 stdout 會被緩衝**（非 tty），背景跑分要加 `-u`，否則看不到任何進度，只能猜它是活的還是卡住。

### 檢索側 LLM 換模型：候選會動，gold 不動（2026-08-14，**要換 query 前處理模型前必讀**）

**問題**：單發管線的檢索側預設 `gpt-oss-120b`、agentic 刻意用 `gpt-oss-20b`，兩邊都沒有對照支撐，而它同時是單發 vs agentic 對照的未控制變因。

**為什麼這件事可以零噪音量**：檢索堆疊本身**沒有 LLM**（BGE-M3 dense+sparse → Qdrant → RRF → cross-encoder）。檢索側模型只驅動 query understanding，其中兩項輸出是結構化的 → 可逐題機械比對。量法見 [`eval/ablate_retrieval_model.py`](../eval/ablate_retrieval_model.py)（兩 stage，n=100）。

**結果**：

| | 120b#0 | 120b#1 | 20b#0 |
|---|---|---|---|
| gold recall@5 | 0.8479 | 0.8465 | **0.8459** |
| 至少命中一個 gold | 0.96 | 0.96 | **0.96** |
| 完全撈不到 gold 的題 | col-07, lex-03, lex-07, lex-14 | 同左 | **同左** |
| 平均單次耗時（n=200） | **1.76s** | — | **3.57s** |

| 配對 | chunk 集合相同 | 平均 Jaccard |
|---|---|---|
| 120b#0 vs 120b#1（噪音底線） | 85/100 | 0.9476 |
| 120b#0 vs 20b#0（訊號） | 72/100 | 0.8971 |

**判讀**：候選池**確實**被換掉了（0.897 < 0.947，超過噪音），但**換掉的全是無關 chunk**——gold recall 差 0.0020，而同模型跑兩次的差是 0.0014，同一量級；逐題看兩邊都只掉 1 題（噪音 mi-14、訊號 mi-06）；四題全空的完全一致。順序變動在七類間均勻分佈，沒有任何類別被系統性打壞。**結論：檢索側兩個模型等價。**

**但方向是反的**：20b 在 NIM 上**慢一倍**。`agentic_rag_v2.py` 原本寫「用小模型求快」——前提是假的。該做的不是把單發降 20b，而是把 agentic 升 120b（同品質、快一倍）。

#### 三個方法論教訓

- **字串比對對「翻譯」這種輸出沒有判別力。** BACKLOG 原本設計「逐題比 `translate_en` 字串，不同的再看誰對」——實測 86/100 不同，但其中 **68 題是同一個模型自己跑兩次就不一樣**（temp=0 不保證 host 端確定性）。噪音吃掉全部訊號。**唯一有意義的判準是「送進真實檢索器後結果有沒有變」**，所以才需要 stage 2。
- **量任何「換模型」之前先確認那個模型真的被呼叫。** `parse_query_filters` 有 91/100 題被 `_FILING_HINT_RE` 效率 gate 擋在 LLM 之前 → 這個參數在那條路上實際只影響 9 題。不先算這個，會把「gate 擋掉所以相同」誤讀成「兩個模型一樣好」。
- **A/B 兩臂的 LLM 輸出要先錄下來再釘死。** stage 2 把 stage 1 錄的 filter/翻譯 monkeypatch 進去，所以整個 stage 2 **零 LLM**、同一份輸入重跑結果一樣。噪音底線用「同模型的第二次跑」而不是憑感覺設閾值。

### 多年語料的期別干擾：硬 filter 全吸收、沒提期間的題全崩（2026-08-19，**要往 KB 加舊年度之前必讀**）

KB 原本只有**一年**（每家 1×10-K ＋ 2×10-Q ＝ 21 份），所以「答錯期別」結構上幾乎不可能發生
——**過去所有評測分數都是在這個保護傘下拿到的**。2026-08-19 補到 **77 份**（每家 3×10-K ＋
8×10-Q，橫跨 ~2.5 年，13,120 chunks）灌進 `us_stock_rag_edgar_multiyear` 壓測，量尺是
[`eval/probe_temporal_interference.py`](../eval/probe_temporal_interference.py)（零 LLM 判定、
兩臂、49 題 filing gold）。**生產 collection 一個位元組都沒動。**

實驗是乾淨的：兩輪 `RAG_REPLAY_CACHE` **hit 65 / miss 0**，英譯逐字相同，Δ 裡沒有 LLM 抽樣噪音。

| intent | Δgold@5 | Δ排擠率 | Δ錯期率 | Δ兄弟密度 |
|---|---|---|---|---|
| **relative**（最新一季，21 題） | **±0.000** | +0.009 | **±0.000** | **+5.62**（1.90→7.52） |
| none（問題沒提期間，25 題） | −0.120 | **+0.400**（0.080→0.480） | +0.120 | +2.48 |
| explicit（明講年份，3 題） | −0.333 | +0.200 | +0.333 | +3.34 |

**① 結論跟直覺相反：競爭密度上升最多的那一類，完全沒有退步。**
`relative` 的兄弟密度漲了 4 倍，gold@5 與錯期率**一格都沒動**。原因是
[`rag_query._resolve_latest_quarter_filter`](../rag_query.py) 在那 21 題裡有 16 題會觸發，
把舊期別在**排序前**就砍掉——metadata 硬 filter 完整吸收了 4 倍競爭。這是「硬 filter 是唯一
提供保證的方法」這個主張在本專案上的直接證據。

**② 陽性對照把硬 filter 的價值量化了，而且它隨語料放大。**
關掉路由（`RQ_LATEST_QUARTER_ROUTING=0`）：

| 語料 | relative gold@5（開→關） | relative 錯期率（開→關） |
|---|---|---|
| 單年 | 0.857 → 0.809 | 0.000 → 0.048 |
| 多年 | 0.857 → **0.381** | 0.000 → **0.476** |

**同一個開關的價值放大了約 10 倍。** 換句話說：那條路由現在是可有可無的優化，KB 一長到兩年
就變成不能拔的命脈。⚠ 而它的觸發**靠硬編碼詞表**（`_LATEST_QUARTER_TIME_RE`），漏一題的代價
從「差一季」變成「差兩年」。

**③ 真正壞掉的是「問題沒提期間」那 25 題**——沒有任何 filter 會觸發，所以沒有東西保護它們。
排擠率 0.080 → **0.480**：top-5 有近一半席位被**同一節的別年份**佔走，gold rank 中位 1 → 3。

**④ F1（排擠）遠大於 F2（錯選）：68 個浪費席位 vs 4 題錯期。**
這個比例決定該修哪裡——**病灶是多樣性不是期別選擇**，指向跨期近重複去重／MMR，不是再加一道
期別 filter。⚠ 拆開報這兩個指標是必要的：只看聚合的「gold@5 掉了 0.082」會把兩件事攪在一起，
而它們該修的地方不同（同 `probe_multi_company_period.py` 那次 kind A / kind B 的教訓）。

**⑤ 最有說服力的單例，也是文獻沒涵蓋的 failure mode。**
`col-02`「微軟是怎麼把 AI 塞進 Office 那些軟體裡的？」——**top-5 有 4 席被 MSFT 三個年度
10-K 的同一節 `Item_1` 佔滿**。10-K 的 Item 1／Item 1A 年年 80~90% 逐字相同，embedding 與
cross-encoder 兩層都分不出來。查過的 temporal IR survey **沒有處理「同一份文件跨年份的近重複」**
——學界 benchmark 多是新聞／知識圖譜，文件之間本來就不會逐字重複。**這是財報 RAG 特有的，
不能指望照抄論文。**
⚠ 順帶推翻一個現成假設：[`rag_query._suppress_near_duplicates`](../rag_query.py) 的規則一寫著
「同一個 `source`（**跨檔絕不比**——不同公司/不同期的相同數字是巧合，不是重複）」。多年語料下
`AAPL_10K_2024` 與 `AAPL_10K_2025` 的同一張表**就是**真正的跨檔近重複，那條假設不再成立。

**⑥ `explicit` 只有 3 題、不能下定論，但機制對得上事前預測。**
`mix-15`「Tesla **2026 年**至今生產與交付了多少輛」問題明明寫了年份，gold `TSLA_10Q_202606`
仍從 rank 2 掉到 6，被 **2024 年的** `TSLA_10Q_202406`／`202409` 擠掉。預測是「期間解析的三條
路徑（regex／LLM 抽 filter／詞表路由）在單年下錯了也沒代價，多年下每一條的錯誤都直接變成 F2」
——這一題符合。要下結論得先補 explicit 類的測資。

**⑦ 這個量尺有一塊盲區，別誤讀**：`mi-01`／`mi-14` 的 filing gold 連候選池都進不去，因為
`looks_like_news_query` 把 multi-intent 題硬路由到 `doc_type=news`。**那是別的缺陷，不是期別
干擾**；它只拖低 gold@5，排擠與錯期兩個指標不受污染（都需要同節 chunk 在池裡），且 before/after
同樣被排除 → Δ 仍然有效。表格上獨立列成「池外」一欄就是為了不讓下一個人誤讀。

### 跨期 field collapsing 與期間意圖解析：兩個修法的四次自我否決（2026-08-19）

承〈多年語料的期別干擾〉量到的兩個病灶做的兩條修法。**這一節最值得讀的不是最後的數字，
是四個「聽起來合理」的設計被自己的對照組推翻的過程**——四個都是我提的，四個都錯。

#### 最終數字（`us_stock_rag_edgar_multiyear`，49 題 filing gold）

| 組態 | gold@5 | 錯期率 | 排擠率 | explicit | relative | none |
|---|---|---|---|---|---|---|
| 不修 | 0.837 | 0.082 | 0.278 | 0.667 | 0.857 | 0.840 |
| 只有 B（collapse） | 0.857 | 0.082 | 0.196 | 0.667 | 0.857 | 0.880 |
| 只有 A（period intent） | 0.878 | 0.041 | 0.274 | **1.000** | 0.857 | 0.880 |
| **A ＋ B** | **0.898** | **0.041** | **0.188** | **1.000** | 0.857 | **0.920** |

逐題比對 A+B vs 不修：**變好 3 題、變差 0 題**。兩者可加（+0.041 與 +0.020 → +0.061）。

#### 四次自我否決（這才是重點）

**① `prefer="rank"`（collapse 組內留 rerank 最高那份）——嚴重退步。**
最直覺的寫法，實測 gold@5 **0.837 → 0.653**、錯期率 ×3.5。原因是**cross-encoder 對年份無感**，
「分數最高」與「對的年份」無關：`sem-03`／`sem-04` 的 gold `MSFT_10K_2026` 在 `MSFT Item_1`
那組裡不是最高分，collapse 留下 `MSFT_10K_2024`、**把 gold 整個刪掉**（`gold_rank` 3 → None）。
降低排擠卻換來 F2，正是原本要防的東西換個方向發作。

**② `prefer="hybrid"`（一席給 rerank 最高、一席給最新）——等於不修，已刪碼。**
為了救「事實只存在於某一季」的事件錨定題而設計的，聽起來比 `newest` 有原則。實測 gold@5
**0.837（＝不修）**，還多刪一個 gold。`mix-07`（Google 收購 Wiz 的金額）的 gold 兩種資格都
不佔，反而樸素的「兩個最新」剛好涵蓋它。**有原則的設計輸給運氣好的設計，就採用後者並寫下
它是運氣。**

**③ `keep=1`——聚合最好，但那是拿趨勢題換的。**
gold@5 0.878 高於 `keep=2` 的 0.857，但代價是：趨勢題期別數 **−38%**、而且**會讓當時的單年
生產 collection 退步**（gold@5 0.918 → 0.878）。
⚠ **這一格改過**：原本還寫了「新增 3 個沉默失效（事件錨定題）」，2026-08-19 逐題人工讀原文
後**撤回**——那 3 題（`mix-07`／`lex-12`／`mix-10`）全是量尺假陽性，見〈期別探針的 gold
人工複審〉。所以 `keep=2` 只剩趨勢題這一條腿，但那條腿是獨立證據，決定不變。

`keep=2` 在單年上是**逐題完全的 no-op（0/49 題 top-5 有任何變化）**，在多年上改 23/49 題。**「資料還不需要時不作用、需要時自己生效」才是敢翻預設的理由。**

**④ A 的第一版讓 `relative` 類退步 0.095——兩個設計錯，不是 LLM 判錯。**
- `col-11`「微軟的雲端服務最近成長得快不快？」：LLM 判 `latest`＋`granularity=None`，而
  `ladder_pick(kind=None)` 挑了「所有類型裡最新的」＝年報 `MSFT_10K_2026`，把季報 gold 擠掉
  （rank 1 → None）。舊的 `_resolve_latest_quarter_filter` 本質上是**季路由**、只在偵測到
  年度意圖時讓路——**預設方向被我弄反了**。修法：`granularity` 缺漏一律落到 10-Q。
- `mix-12`「這一季…**跟去年同期相比**有何變化？」：LLM 判 `range`，**語意上完全正確**，錯的是
  我把 `range` 對應到「不注入 filter」→ gold rank 1 → 14。**財報有個領域事實**：單一份 10-Q
  本身就含去年同期對照，「當期 vs 去年同期」根本不需要撈兩份 filing。修法：prompt 裡明寫
  這條，把它歸 `latest`。
兩處修完後 `mix-12` 14 → 1、`col-11` None → 1，`relative` 回到 0.857。

#### 三個要記住的判準

- **收益指標不可以與規則同定義**：collapse 的規則與「排擠席位」是同一個定義 → 開了必然歸零。
  那是套套邏輯。收益要看 `gold@k`，損害要看**另外構造的陰性對照**
  （[`eval/period_probe_trend_queries.json`](../eval/period_probe_trend_queries.json)，8 題本來就
  需要多期的趨勢題）。eval_set 的 100 題裡**沒有任何一題**是這個形狀 → 那個方向的量尺是空的。
- **`relative` 那一類的「錯誤」要先懷疑量尺**：用來分桶的 `classify_period_intent` 本身就是
  一個詞表。實測 LLM 判 `mix-12`＝`range`、`col-04`（「現在有整合進搜尋引擎裡嗎」）＝`none`
  被記成「誤判」，查下來**兩題都是 LLM 對、分類器錯**——`relative` 是 21/21 站得住，不是 19/21。
- **collapse 是純 rerank 後處理**（不改 query／filter／候選池）→ 一次檢索就能掃全部 keep×prefer
  組合，與「每組各跑一次」逐位元相同。**把完整候選池存進結果檔**，加一個臂就不必再燒 1.2 小時
  （這一輪已經因為臨時要加 `prefer` 這一維而重跑過一次，正是 memory `eval-measurement-pitfalls`
  記的「只存結論不存中間產物」）。

#### 兩個旗標的預設值，以及為什麼不一樣

在**單年生產 collection**（`us_stock_rag_edgar_mdna`）上重跑同一組對照：

| 組態 | gold@5 | 錯期率 | 排擠率 | 逐題變動 |
|---|---|---|---|---|
| 不修 | 0.918 | 0.000 | 0.057 | — |
| 只有 B | 0.918 | 0.000 | 0.057 | **0/49** |
| A ＋ B | 0.918 | 0.000 | 0.049 | **變好 0、變差 0** |

- **B（`RAG_CROSS_PERIOD_COLLAPSE`）＝ 預設開啟。** 純 Python 後處理、零 LLM、零額外延遲，
  在單年上逐題 no-op、在多年上自己生效。**沒有理由不開。**
- **A（`RQ_PERIOD_INTENT_LLM`）＝ 預設關閉。** 它在目前的生產資料上**買不到任何東西**
  （0 題變動），卻要付每次 retrieve 一次 LLM（中位 1.54s，而且 agentic 是每個子問題每一輪
  都打）。**為零收益付真實成本是壞交易。**
  **翻預設的條件**：多年語料升生產的同一次改動裡一起翻——屆時它值 gold@5 +0.041、錯期率
  減半、`explicit` 類錯期率 0.333 → 0。⚠ 別分兩次做：B 的 `range` 保護要靠 A，
  多年語料上線而 A 沒開，趨勢題會吃到 collapse 的 −6%。

#### 成本

A 每次 retrieve 多一次 LLM 呼叫（`resolve_period_intent`，實測中位 **1.54s**）。它**不能**併進
`parse_query_filters`：那個函式前面有 `_FILING_HINT_RE` 詞表閘門，實測**擋掉 21 題 `relative`
裡的 20 題**（「Microsoft Azure 最新一季的營收成長率是多少？」不含年報／季報／FY／Qx／四位數
年份任何一個）。那道閘門的正確性論證是「這類 query 的 LLM 本來就只會回空」，而那句話**只對
『抽取明確約束』成立**；`period_ref` 問的正是隱含意圖。所以 A 用獨立函式＋獨立 `llm_replay`
kind，**不動任何既有 prompt、不讓任何既有 fixture 失效**。

### 期別探針的 gold 人工複審：量尺偏袒 B，且它的陰性對照是空的（2026-08-19，**引用 gold@k 的收益數字前必讀**）

2026-08-19 的兩個修法（B 跨期 collapse／A 期間意圖）驗收全靠 `probe_temporal_interference.py`
的 `gold@k`。事後**逐題人工讀原文**複審那 49 題 gold，結論是「修法的收益是真的，但**量尺本身
偏袒 B**，而且原本以為存在的陰性對照經查全是假警報」。三件事分開記：

**① gold 的指稱沒有被新資料破壞（唯一全綠的一項）。**
`period_probe_baseline.json` 的 21 份對照現在 77 份的 manifest：**沒有任何一份比快照更新的
filing 進來**（逐 `(ticker, form)` 比 `period_of_report`，14 組全等）。所以「最新一季／最新年報」
這類 gold 的指稱不變，append-only 在 gold 層面成立。

**② 46/49 的 gold 就是該 `(ticker, form)` 最新的那一份，而 B 的規則正是「留最新」。**
→ `gold@k` 對 B **結構上偏袒**。這與〈跨期 field collapsing〉那節記的「排擠席位與 collapse
規則同定義」是**同一種病的第二層**：第一層在指標定義上，第二層在 gold 分佈上。
**引用 B 的 gold@k 增益時必須同時講這一句。**

**③ 那 3 題「gold 不是最新」的陰性對照，人工查證後全部無效。**

| qid | gold | 人工讀原文的結果 |
|---|---|---|
| `mix-07` | `GOOGL_10Q_202603` | 202606 有**逐字相同**的 Wiz 段落（含 `$29.5 billion` 與 Google Cloud 影響）→ 換更新的一份答得一樣對 |
| `lex-12` | `GOOGL_10Q_202603` | 同上，「On March 11, 2026, we completed our acquisition of Wiz for $29.5 billion」兩份逐字都有 |
| `mix-10` | `AAPL_10Q_202603` | 被 `looks_like_news_query` 路由到 news，**任何一臂 gold 都不在 top-k** → 這題對 collapse 沒有判別力 |

→ **`keep=1` 造成「3 個沉默失效」這個說法不成立**（它是量尺假陽性）。`keep=2` 的決定仍然站得住，
但只剩**一條腿**：趨勢題 `periods_covered` −38%（獨立證據，不受此影響）。
⚠ 反過來也不能說 `keep=1` 安全——這組 gold 裡**沒有一題**能證偽它，那是測資不足不是它沒問題。

**④ `wrong_period` 這個指標對「定性答案」會假陽性。** 逐題讀原文的四個案例：

| qid | 闖入的舊期別 | 是真缺陷嗎 |
|---|---|---|
| `mix-15` | `TSLA_10Q_202406` | **真**。舊季說「2024 年至第二季生產約 844,000 輛」，gold 是「2026 年 860 千輛」——**差 2%、差兩年**，抽掉年份人看不出來 |
| `sem-05` | `AMZN_10K_2023/2024` | **真**。Anthropic 投資 2023 是 12.5 億、2025 資產負債表上是 148 億，差一個數量級 |
| `mix-10` | `AAPL_10Q_202503/202512` | **假**。答案「higher net sales of **Pro models**」在 202503／202512／202603／202606 **四份逐字都有**，定性結論完全相同 |

### KB 拔除新聞：只留「記錄」，把「流」交給 live web（2026-08-19，**看到 news 類題目或分數變動前必讀**）

**做了什麼**：`data/raw/News/` 加進 `data_update_edgar.RAW_EXCLUDE_DIRS` → KB 不再收新聞語料；
生產與壓測兩個 collection 各刪掉 98 個 news chunk；`fetch_data.py` 的新聞改成 `--with-news` opt-in；
`rag_query` 的 `doc_type=news` 硬路由整段移除。**歷史對照臂（exp4／ground／ground2／head／period）
刻意不動**——改它們就毀掉歷史可比性。

#### 為什麼：新聞與這個系統的正確性判準正交

|  | 記錄（filing／Fundamentals） | 流（news） |
|---|---|---|
| 權威性 | 法定揭露 | 聚合站與評論 |
| 時間標籤 | `fiscal_year`＋`fiscal_period` | **payload 覆蓋率 0%** |
| 正確性判準 | 期別對＋有引用＋數字可驗 | 夠新＋來源可信 |

這個專案為期別正確性做的每一層（切塊六層、期別階梯、跨期 collapse、期間意圖、citation validator、
`check_number_defects`）**對新聞沒有一項成立**。

**資料實況（拔除前實測）**：24 檔／98 chunks ＝ 生產 collection 的 **2.5%**；日期停在 2026-07-21；
分佈極不均（AAPL 7 則 vs AMZN／META 各 1 則）；4 檔是 Yahoo Finance **影片逐字稿**。
最尖銳的一項：**28 條來源標記有 17 條（61%）來自本專案自己的 `WEB_ALLOWED_DOMAINS` 會拒絕的站**
（Insider Monkey ×7、Seeking Alpha ×3、MarketBeat ×2、Trefis、IPO-Edge、CryptoProwl…）。
你已經定義過「什麼算有編輯流程的財經新聞」，而 ingest 進 KB 的新聞六成不合自己的標準。

**代價與收益**：新聞佔 2.5% 語料，卻是拔除前**最大的殘留檢索失敗**——`looks_like_news_query`
（20 個詞的硬編碼詞表）把複合題硬路由到 `doc_type=news`，filing gold 連候選池都進不去。
拔除後實測 `mi-01`「NVIDIA 最新財報…加上新聞中…」top-5 從「5 個 news chunk、gold 不在池裡」
變成 `NVDA_10Q_202604#42／#14` 排名 1、2。

#### 量尺的三個變動——**跨 2026-08-19 的分數一律不可直接比**

**① `eval_set.json` 100 → 63 → 65 題。** 37 題（relevant 含 `*_News_*.txt`）搬到 `eval/eval_set_news.json`
冷凍：16 題只靠新聞、21 題是複合（**multi_intent 全 15 題**＋col-15、col-14＋multi_hop 5 題）。
留下的是 semantic 15／mixed 15／lexical 15／colloquial 13／multi_hop 5，同日再補回 `lex-16`／`lex-17` → **lexical 17、共 65 題**。
`reference_answers.json`、`number_claims.json` 同步拆出 `*_news.json`。
⚠ **冷凍不是刪除**：那 37 題是日後驗收「live web 能不能取代 KB 新聞」唯一的現成題庫。
現在**不要**拿它跑分——eval 預設 `freshness_mode=snapshot`、web 是關的，跑了必然全滅，那不是證據。

**② `check_number_defects` 6 → 4 → 7 條。** 拆分當天掉到 4 條（PASS 3／FAIL 1），
⚠ **那不是改善是組成變動**——搬走的 `mi-04`(PASS)／`mi-05`(FAIL) 一 PASS 一 FAIL。
同日稍後把兩者**去掉新聞子句**補回主檔（`lex-16`／`lex-17`，見下方〈量尺補回兩條〉），
`lex-17` 再拆成 require_chunk ＋ anchored_pct 兩條（進池 ≠ 有用它），共 7 條。
⚠ **這 7 條的判讀必須跑兩輪以上**：實測同一份 collection 上 r1 是 PASS 7／FAIL 0、r2 是 PASS 4／FAIL 3，差異全來自 Plan 子問題變異，不是系統改動。

**③ `verify_answer_validators` 閘門④ 一度 FAIL 3 項。**
`_news_freshness_gaps` 的 cutoff 讀真實 KB coverage，KB 沒新聞就算不出缺口 → 三條陽性斷言
測不出東西。**那是量尺失去判別力，不是機制壞掉**（同本檔〈稽核回傳 0 筆先當壞消息〉）。
修法是讓閘門**自帶合成 coverage**，而不是把斷言刪掉——現在它守的是「新聞若復活，警語必須
立刻正確」，且不再與 KB 當下內容耦合，比原本更好。（該閘門其後擴到 77/77，見 docs/AGENTIC.md A10。）

#### 後續：時效警語一度整個死掉（2026-08-19 當天補回）

拔除新聞時我把 `_news_freshness_gaps` 標成「閒置但保留」，**低估了後果**。實測：

```
用財報回答即時題、web 沒補到 → freshness_gaps = []  →  時效警語 = ''
```

缺口的舊判準是「**用了 KB 新聞、而那則新聞過期**」。KB 沒有新聞 → 判準沒有指涉對象 →
**警語永遠不印**。但風險沒有消失，只是換了位置：即時題 → Grader 正確判不足 → 去打 web →
**web 預算用完（`QUERY_WEB_BUDGET=3`）或搜不到** → 答案回頭用財報 chunk 生成 → **零揭露**。
使用者看到一段自信的「目前市值」，底下引用的是 10-K。

**修法**：新增 `_unmet_realtime_gaps`，判準改成「**這個子問題需要即時資料
（Grader 的 `realtime_need != none`）**」。分工照 CLAUDE.md：
「需不需要即時」有判斷成分 → LLM（已在 Grader 內，不多花一次呼叫）；
「這次有沒有拿到 web」是確定性的 → 沿用 `_format_unresolved_freshness_notice` 既有的
`web_used` 過濾（**刻意不在兩個地方各判一次**，那必然漂移）。
警語措辭也分流：realtime 缺口講的是「知識庫本來就沒有這種資料」，不是「新聞有點舊」。

**閘門⑤b（10 條）＋ 變異測試**：把 `_unmet_realtime_gaps` 改成恆回空（＝回到 bug 狀態）→
**7 條乾淨 FAIL**；還原 → 62/62 PASS。⚠ 第一版變異測試丟的是 `IndexError` traceback——
崩潰雖然也算偵測到，但它會蓋掉後面所有斷言，所以斷言改用 `[:1]` 取值，讓機制壞掉時
**乾淨地 FAIL 而不是炸**。

⚠ **這一組的陰性對照是「財報題 → 零缺口」**。少了它，一個「一律產生缺口」的實作也會全綠，
而那會讓時效警語印在每一道財報題底下——警語與有出處的數字互相矛盾，比沒有警語更糟
（2026-08-14 已經踩過一次，見 `_format_unresolved_freshness_notice` 的 docstring）。

**教訓**：拔掉一個資料來源時，要檢查的不只是「誰會壞」，還有「**誰的判準會失去指涉對象**」。
後者不會拋錯、不會 FAIL，只會安靜地永遠回空。

#### 量尺補回兩條：`lex-16`／`lex-17`，以及一次「只跑一輪就下結論」的自我打臉（2026-08-19）

拆題庫把 `check_number_defects` 從 6 條打到 4 條，而搬走的兩條**一 PASS 一 FAIL**——等於整條零噪音驗收線同時少掉一個護欄與一個進度指標。補法是把那兩題**去掉新聞子句**、只留財報半，以 `lex-16`／`lex-17` 進 65 題母檔。`lex-17` 刻意**逐字沿用 `mi-05` 的原題前半、其餘一字不改**，讓「新聞子句」成為唯一變因。

##### 先講結論：拿掉新聞子句**沒有**修好 `mi-05`

| run | `MSFT_Fundamentals#0` 進池？ | 答案 |
|---|---|---|
| r1 | ✅ | 18.30%，標明 TTM |
| r2 | ❌ 撈到 `#1` | 18%（＝10-K 財年，增加 501 億美元）|

r2 的訊息逐字就是 `mi-05` 的原症狀。所以 `lex-17` 以 **`known_defect`** 登錄，不是護欄。

##### 真正的教訓：我只看了 r1 就宣告根因被推翻

第一輪跑完（r1 全 PASS）＋ 一支單發檢索探針，我寫下了「`mi-05` 的根因是新聞污染、與 `mix-07` 同一個病、rerank 長度偏好那個假設不成立」，並且**已經改進了 BACKLOG、CHANGELOG 與本檔**。r2 跑完立刻推翻。

這正是本檔〈量測噪音〉整節在講的事，而我在**同一個 session 內**又犯了一次：
- **這條管線本來就不是確定性的**。Plan 產生的子問題會變（實測 48% 不一致），而 `mi-05` 這個缺陷的觸發**恰恰取決於子問題長什麼樣**。
- **`mi-05` 的記載自己早就寫過這件事**：2026-08-12 補過一句「部分取決於 Plan 產生的子問題」（`ground`／`ground2` 各 3 run 各有 1 次 PASS）。我讀到了那句話，卻仍然用 1 個 run 下結論。
- **「只跑一輪」的危險是不對稱的**：跑出 FAIL 只會讓人多查一次，跑出 PASS 會讓人宣告修好、**還會順手把舊記載改掉**——錯誤結論會被寫進文件，比沒查更糟。

所以舊記載真正錯的只有**強度**（「4/4 穩定」——2026-08-12 已自我更正成 8/10）。那句「懷疑 #1 長三倍造成 rerank 偏好」**到現在仍未驗證，仍然不是結論**。

##### 真的被拔除新聞修好的是 `mix-07`

同一批 run 裡 `mix-07` **2/2 從 FAIL 翻成 PASS**（`I don't have enough information` → 答出 $29.5B），而它記載的根因本來就是「Plan 節點把財報事實譯成新聞查詢 → 候選池全是 News chunk → 拒答」。**這一題才是拔除新聞的直接收益**，且它是零噪音量到的。

##### 順帶修掉兩個量尺缺口（都是 r2 逼出來的）

1. **`col-11` 的 anchor 措辭寫死** → 見本檔〈數字缺陷指標的五次失效〉第五次。
2. **`expect_pct` 的 ±1pt 容差擋不住「數值接近但口徑不同」的錯值**。兩條都補了 `expect_text` 當第二判準：
   - `col-11` 補金額 `545 億／$54.5B`（只屬於 Microsoft Cloud 整體）。放寬 anchor 之後 r2 抓到真 FAIL，但那是**險勝**——該答案裡 Consumer 雲端成長率恰好也是 29%，只要落進窗口就會用對的分數獎勵錯的內容。
   - `lex-17` 補字面 `18.3`。`expect_pct: 18.3` 對上 10-K 的 `18%` 差 0.3，**在 ±1pt 下會 PASS**——那正是 `mi-05` 的 metric_design 早就寫下的陷阱，r2 就長這樣。⚠ 刻意**不加 forbid**：「TTM 18.3% ＋ 財年 18%」兩個口徑並陳並標注清楚是**好答案**，照 `anchored_pcts` docstring 的判準，這種情況不可用 forbid。

**順帶量到但沒有登錄的**：單發檢索探針測四種問法問 MSFT 營收成長率，`#0` 的 rank 依序是 5／1／完全沒進 top-5——最後那個是口語的「微軟的營收成長率是多少？」。**沒有登錄成主張**，因為 10-Q 的季度成長是合法的另一種口徑，判它錯等於用斷言獎勵一個沒有根據的偏好。記在 BACKLOG 當觀察。

### live web 能不能取代 KB 新聞：①路由這一半量完了，不是瓶頸（2026-08-19，**動 web 判斷式或決定要不要錄 fixture 前必讀**）

#### 先把問題拆開：兩個子問題的成本差一個數量級

| | 問什麼 | 誰決定 | 成本 | 量尺 |
|---|---|---|---|---|
| ① | 這題**會不會**被送去 web | Planner ＋ Grader（LLM） | 只燒 LLM | `eval/probe_news_web_routing.py` |
| ② | web 拿回來的東西**夠不夠**回答它 | Tavily 回應品質 | 連網、燒 Tavily | `record_web_fixture.py` ＋ `check_web_claims.py` |

**① 是 ② 的必要條件**：一題若根本不會觸發 web，錄再多 fixture 也救不了它——那是路由問題不是內容問題。
原本的計畫是直接去錄 37 題的 fixture，那等於在不知道有幾題走不到 web 的情況下先付錢。

**零網路的作法**：把 `_tavily_search` 換成計數樁（回空字串），其餘管線**原封不動**跑真的 Plan／檢索／Grade。
⚠ 不要另外抄一份判斷式——抄寫版本會漂移（`verify_web_gate_isolation.py` 閘門① 已經吃過這個虧）。
⚠ 樁回空字串 ＝ 模擬「web 有打、但什麼都沒撈到」，所以這一步**只量路由、不量答案品質**。

#### 結果（1 輪，37 題 ＋ 8 題對照）

| 臂 | 類別 | 觸發 web |
|---|---|---|
| news_set | news | 13/15 |
| news_set | **multi_intent** | **15/15** |
| news_set | colloquial | 2/2 |
| news_set | multi_hop | 5/5 |
| control(strict) | lexical／semantic／mixed | **0/6** |

`multi_intent` 那一格最值得看：那是「財報半 ＋ 新聞半」的複合題，**最危險的失敗形狀是財報半讓 Grader 判「夠了」而整題不打 web**。實測沒有發生。

兩題沒觸發，查完都不是路由壞掉：
- `news-02`（WWDC Siri）：KB 的 `AAPL_10Q_202606.html#32` 真的寫了 Siri AI 功能 → Grader 判夠。答案開頭就寫「並未被資料直接提及」再引財報，**有揭露**。
- `news-05`（NVIDIA 賣中國晶片）：Planner 明確 replan 出「改用網路搜尋查…」的子問題，卻被 KB 的 10-K／10-Q 內容滿足 → 不打 web。**這正是「證據後置」設計在運作**，不是缺陷。
  ⚠ **但它不穩定**：同一題重跑一次就變成 web×1。所以「2 題不叫 web」是**單輪觀察不是穩定行為**，
  真實觸發率 ≥ 35/37。下結論請 `--repeat`。

#### 順帶做掉的第一次端到端驗證：時效警語真的會印

`_unmet_realtime_gaps`（2026-08-19 當天補的）設計時針對的形狀是「即時題 → 打了 web → **預算用完或搜不到** → 回頭用財報 chunk 生成 → 零揭露」。
樁回空字串**恰好就是那個形狀**（而且它在生產也真實存在：Tavily 掛掉／預算用完／搜不到）。實測兩題都印出：

```
⚠ 資料時效：NVDA 需要即時／近期資料，知識庫最新期別截至 2026-06-12（查詢日 2026-08-19）；
Web 未提供可用補充，因此以上內容不代表涵蓋至查詢日。
```

其中 `col-08`（「NVIDIA 現在值多少錢」）的答案本體是 **2026-06-12 的市值快照講成「目前的市值」**——正是 CLAUDE.md 記著的那個危險形狀，而警語把它接住了。

#### 陰性對照踩到的坑：「現在市值」不可以當陰性對照

第一版把 `col-08`（NVIDIA 現在值多少錢）放進 strict 對照，它打了 3 次 web 被記成「浪費」。
**錯的是對照不是系統**：市值在 KB 裡是 2026-06-12 的快照，而 `eval/web_claims.json` 的 `web-01`（Apple 目前的市值）對同型問題的斷言正是 `web_calls_gte: 1`。
→ **同一件事在兩支腳本裡有相反的期望 ＝ 量尺自相矛盾**，那比任何一邊判錯都糟。
修法是把對照分兩級：`CONTROL_STRICT`（期別明確指定，斷言必須 0 次）／`CONTROL_LOOSE`（「最近一年／TTM」措辭，**只觀察不斷言**）。TTM 是會計口徑不是 wall clock，但它離「最近」只有一個字，Grader 判成需要即時未必是錯的。

#### 一個**不可以拿來下結論**的數字

21/37（57%）打滿了 `QUERY_WEB_BUDGET=3`。**這是樁造成的**——樁回空字串 → Grader 永遠不滿意 →繼續改寫再打。真實 web 有內容時多半一次就夠。
它唯一能誠實支撐的結論是 **② 的成本上界：錄 37 題的 fixture 最多 111 次 Tavily 呼叫**。

另外 90 次 web query 裡有 28 次的 `realtime_need` 是 `none`——**web 不只為了即時性，也為了「KB 根本沒有」**，這是對的行為。

#### ② 開始之前要先解決的一個量尺問題（**已在同日的 ② 裡照這個結論做了**）

那 37 題的 gold 是「2026 年 6 月的新聞說了什麼」，而 live web 回答的是「現在的網路說什麼」——**這是兩個不同的問題**。拿 web 答案去對新聞 gold 打分會系統性地低估，而低分的原因與「web 好不好」無關，是題目本身綁在一個時點上。
→ ② 的驗收**不能**是「web 能不能重現新聞答案」，只能是「web 對這些**題型**產出的答案可不可信」（有引用／來源在白名單／數字逐字可回溯／時效有揭露），也就是沿用 `check_web_claims.py` 的斷言形態，而不是 RAGAS。

### live web 取代 KB 新聞：②內容這一半也量完了——可信，但發現一個 live 專屬的引用缺陷（2026-08-20）

接續上一節的 ①。fixture 錄製：37 題 ＋ 3 題陰性對照，**86 筆 Tavily 原始回應**，as-of 2026-08-20，寫進 `eval/web_fixture_news37.json`（**新檔**，不碰綁 as-of 2026-08-15 的舊 fixture）。

#### 驗收標準為什麼不是「對照新聞 gold」

那 37 題的 gold 是「2026 年 6 月的新聞說了什麼」，live web 回答的是「現在的網路說什麼」——**這是兩個不同的問題**。拿 web 答案去對新聞 gold 打分會系統性低估，而低分的原因與 web 好不好無關，是題目本身綁在一個時點上。
所以改用 `check_web_claims.py` 的**性質斷言**：走不走 web／引用主機在不在白名單且非地區子網域／引用長不長得像出處。零噪音、與時點無關。

#### FAIL 5 題：live 路徑會吐出指向不存在來源的引用

5 題（`news-03`／`news-07`／`news-13`／`mi-02`／`mi-07`）的答案含 **`【Reference 7, chunk #15】`** 這種標記——它不是檔名、不是網址，**指向不存在的東西**。

三件事讓它從「格式瑕疵」變成真缺陷：
1. **那 5 題的有效 KB 引用是 0**。不是「多了一個壞引用」，是**整份答案沒有任何可追溯的 KB 出處**，而答案裡有大量財報數字（`news-13` 的市值、TTM 營收、P/E 全掛在假引用下）。
2. **這是 live 專屬的**。同一套程式：snapshot 路徑 **0/100**、live 路徑 **5/37**。
3. **validator 有抓到，只是放它過去**。`_extract_citations` 把 `Reference 7` 解析成`("Reference 7", 15)` → 不在 allowlist → 判成捏造 ID → 丟回重寫，但 `CITATION_VALIDATOR_MAX_RETRIES = 1`，用完就 `break` 然後 **原樣 `return answer`**。
   ⚠ 而該處的 trace 寫的是「重試耗盡，**走機械式收尾**」——**當時程式裡沒有任何機械收尾**。註解描述了一個不存在的行為，這比沒有註解更糟。（2026-08-20 已改成照實說，並真的補上一個確定性修補，見下。）

**修法（2026-08-20 當天做掉了）**：`Reference N` 的編號**是我們自己給的**
（`rq.build_user_prompt` 產生 `[Reference i+1: source, chunk #idx]`），
所以 `N → allowed_chunks[N-1]` 是**確定性映射**，屬於 Python 那一半，不必再問 LLM。
新增 `_repair_reference_citations`，在 `_validate_and_fix_citations` 的迴圈開頭先跑。

**這次設計的重點是兩個守門條件，不是修補本身**：
① `N` 超出候選範圍 → 不動；② 引用裡的 `chunk #M` 與第 N 筆的 `chunk_index` 不一致 → 不動。

理由是**失敗方向不對稱**：漏修 ＝ 維持現狀（不會更糟）；而猜錯 ＝ 把「無法追溯」變成「**看起來可追溯的錯引用**」，讀者會相信它。
條件② 還有一個副作用值得記下來：**它讓「排序假設」不必被證明**——原本我只有「用 `sources` 當代理排序、14 筆有 10 筆對得上」這種支持性證據，而兩半一致時那筆修補是**被資料自己確認過的**，不依賴任何假設。

**閘門⑨ 12 項**，`verify_answer_validators` 77 → **89/89**。三向變異測試：

| 變異 | 結果 |
|---|---|
| 機制恆不作用 | 7 條 FAIL |
| 拿掉一致性守門② | **誤報對照精準 FAIL 1 條** |

真實答案上的修補率：**還原 16 筆、5 題有 3 題完全清乾淨**。
⚠ 這是**下界**——量的時候用結果檔的 `sources` 當代理排序（跨子問題聯集），生產路徑用的是手上真正的 `allowed_chunks`。
⚠ **不是全部修得掉，而且那是刻意的**：守門條件擋下的那些走原本的重寫路徑，重試用完仍會原樣出貨。**已知極限，因為猜錯比不修更糟。**

**端到端證據（帶 `AGENTIC_TRACE` 的 replay，零網路）**：

──[mi-07]   citation repair: 還原 3 筆（守門條件擋下 0 筆）

5 題裡 **2 題的模型仍然吐出序號引用，兩題都被完整還原、0 筆被守門擋下**；事後掃描 5 題**全部 0 個假引用、有效 KB 引用 1~5 筆**。

⚠ **另外 3 題（news-07／news-13／mi-02）這一輪模型根本沒吐序號引用**——它們的 PASS **不能算在修法頭上**，那是 LLM 變異。把「修法生效」與「這次剛好沒發生」分開講是必要的：先前那個 `check_web_claims` **PASS 40／FAIL 0** 是在「修法 ＋ 重新生成」兩個變因同時動的情況下拿到的，**單看它證明不了任何事**。

⚠ 順帶推翻了我自己的一個保守估計：真實 `allowed_chunks` 排序下**守門條件一筆都沒擋下**（0/15）。先前用結果檔 `sources`（跨子問題聯集）當代理排序量到「14 筆有 4 筆對不上」——**那 4 筆確實是代理排序的假象**，如當時標註的一樣，那個數字是下界。

#### 同一個 session 內第三次踩「量尺失去判別力」

閘門⑨ 的端到端斷言第一版**讀 `experiments/web_fixture_answers_news37_all.json`**。把修好的 replay 併回那個檔之後，那條斷言當場變成 `dirty=0` 而 FAIL——**不是機制壞了，是量尺沒東西可量**。

⚠ 而本檔對應的閘門② **早就寫著這條規則**：「陽性答案逐字凍結在測試檔裡，不讀 `experiments/`；讀結果檔的話，一修好陽性就消失，閘門會隨修法生效而自己失去判別力」。
**我寫了那條規則、讀過那條規則，然後在同一天違反它。** 修法是把修法前的 20 筆序號引用（連同各自的候選清單）**逐字凍結進測試檔**。

`mh-07`（歐洲逾 100 億歐元投資是哪家公司）web 打了 3 次，答案誠實地說「新聞稿中並未出現」。`mh-09`（穆迪評信用正面的 847.5 億融資案）同樣沒引用 web，改用 KB 的近似值推論（「META 已發行約 840 億美元票據…與 847.5 億最接近」）並自己標明「現有文件未直接披露」。
→ **web 有沒有撈到可用內容不在系統控制內**，斷言它等於把外部世界寫進量尺。所以這兩題只斷言 `web_calls_gte: 1`，不斷言 `must_cite_any_web`。

#### 為什麼這批**不能**用 `numbers_must_be_in_fixture`

這是本節最容易被下次的自己重踩的一格。那條斷言是這支腳本最強的一條（測幻覺），但**這批題天生是混合的**（財報半＋新聞半），答案裡 KB 數字與 web 數字並存。
實測 `news-13` 的 20 個「三位數兩位小數」有 7 個不在 fixture——**逐一讀完全部是 Fundamentals 的市值／TTM 營收，一個幻覺都沒有**。
→ **沒有任何字面樣式能把兩種來源分開**，硬套只會製造假 FAIL。要真的驗數字來源，需要系統**逐數字標出處**，那是另一件事。

#### 對「要不要把新聞放回 KB」這個決定的意義

路由不是瓶頸（35/37）、來源合規（白名單 100%、地區子網域 0）、時效有揭露。**唯一擋在前面的是引用可追溯性，而那是本地程式的缺陷、不是 web 的缺陷**——它在 snapshot 路徑上不存在，也不會因為把新聞放回 KB 而改善。
→ 沒有任何一項證據支持「把新聞加回 ingest」。

題庫 100 → 63 → 65 讓 `GOLD_BASELINE` 與 `NOISE` 同時失效。⚠ **gold 重量完就宣告「量尺修好了」是最自然、也最危險的講法**——那會讓下一個人拿一個沒有效的噪音門檻去判斷顯著性。

**gold 上限**（把 reference 當系統答案，contexts 沿用同一份 agentic 結果 → 只換一個變因）：

| | n=100 舊 | **n=65 新** |
|---|---|---|
| answer_correctness | .989 | **.972** |
| context_recall | .766 | **.788** |
| context_precision | .822 | **.843** |
| nv_context_relevance | .965 | **.969** |
| faithfulness | .656 | **.659** |

#### 噪音：新測到的值**沒有直接採用**

同一份結果檔餵 judge 兩次，實測 |j1−j2|：recall .0170／precision **.0050**／nv .0040／faith .0100／relevancy .0040／correctness .0070。

→ **取新舊較大值**。噪音門檻取大只會要求更多證據，永遠不會少要求，**錯的方向是安全的那一邊**。
⚠ 只量了一對＝一次抽樣不是上界；要收斂 precision 的門檻得多跑幾對。

#### 修法前的系統現況（`gj_mdna_65q_r1`，乾淨的 before 臂）

`nv_context_relevance` 已到頂；`faithfulness` 0.816 **反而贏過 gold 0.659**（已知：gold 依 gold_files 生成、與實際 contexts 不同源）；recall／relevancy／precision 差距都在 0.04 內。
**唯一有實質空間的是 `answer_correctness` 0.642 vs 0.972**——而那 0.330 的落差**在換題庫前後幾乎沒變**（100 題時 0.329），代表它不是題目組成造成的。
⚠ 仍不可讀成「還有 33% 可進步」：該指標是長度／詳略對齊假象、對 retrieval 免疫。

#### after 臂的判準（**在跑之前寫死**）

⚠ 先看數字再決定怎麼讀，是這個專案犯過最多次的錯（同日就有四次「量尺與被測物耦合」）。所以先寫死：

**主判準＝零噪音，不是 RAGAS。** `lex-17` 的三條主張在 before 臂**全部 FAIL**：
① `require_chunk`：`#0 缺席（同檔撈到 #1）` ② `anchored_pct`：答 10-K 財年 18%（`501 億美元`）③ `require_text`：既沒給 18.3% 也沒有口徑說明。
→ **三條同時轉 PASS ＝ 修法有效**；只轉一兩條要逐條讀答案，不可以算「部分成功」。

**RAGAS 只當副判準，而且預期它看不出差別。** 三個修法一共只動到個位數題目，而 65 題的 MDE 換算成「要幾題從 0 修到 0.5」仍是 4~7 題。⚠ **所以 RAGAS 沒有變化是預期結果，不是修法無效的證據**——這句話必須寫在看到數字之前。
反過來，若 RAGAS 出現超過噪音門檻的**下降**，那才要查（可能是揭露警語改變了答案長度／措辭而影響 `answer_correctness`）。

#### 判準的用處在於它擋下了「部分成功」這個講法（2026-08-21）

after 臂跑出 **PASS 5／FAIL 3，與 before 臂逐條相同**，且 `require_chunk` 的訊息從
「同檔撈到 #1」變成「**該檔完全沒被撈到**」＝更壞。照預先寫死的判準記為 **null result**。

⚠ **這裡有一個很好聽、但錯的解讀隨手可得**：「Fundamentals 從 #1 變成不出現，是因為修法正確地
拒絕了零比率的 chunk，所以其實是進步。」前半句是真的，後半句不是——使用者拿到的答案沒有變好，
而判準寫的是三條同時轉 PASS。**能自圓其說的敘事和有效的修法，在數字上長得一樣。**

逐層印出來之後，兩個真因都在前一天修法的**下面一層**（碼上細節見 CHANGELOG 2026-08-21）：

| | 真因 | 為什麼前一天看不到 |
|---|---|---|
| A | 保底掃的 `run_state.pool` **本來就沒有 `#0`**——生產是英譯 query，`MSFT_Fundamentals #0` 連 RRF 的 20 個候選都沒進（中文原句反而進得去，rank 7） | 前一天的假設是「`#0` 在池裡、只是沒被挑中」，那個假設從來沒被驗過 |
| B | `_basis_disclosure_notice` 讀 `chunk["period_basis"]`，而 `rq.retrieve()` **沒把這個欄位放進 chunk dict** → validator 在線上**結構性永遠不觸發** | 閘門⑪ 的 8 條斷言全部拿測試自己造的 dict 餵進去，**全綠** |

**B 是量尺與被測物耦合的第六次，而且是最難自己發現的一種形狀**：前五次的耦合是「量尺讀了修法會改動的產物」，
這次是「量尺**自備輸入**，於是從來沒有驗過生產供不供得出那個輸入」。
「payload 裡有這個欄位」和「chunk dict 裡有這個欄位」是兩件事，中間隔著一個建構子——
而閘門⑪ 原本**有**一條活體斷言在掃 payload，掃出 `{'fiscal_year': 3805, 'TTM': 22}`、PASS，
**正好把人的注意力擋在建構子前面一步**。
→ 通則：**驗證器讀哪個欄位，就要有一條斷言拿真實資料餵生產的建構路徑**，不能只驗資料源有那個欄位。
實作上把建構抽成具名函式（`rq._payload_to_chunk`）就是為了讓這件事可測。

變異測試把這個形狀直接照出來：**M1（建構子不帶 `period_basis`）→ ⑪ 原本那 8 條照樣全 PASS，只有新加的 ⑪b 叫。**

#### RAGAS 副判準：一個假警報，以及它揭穿的量尺缺陷（2026-08-21）

after2 臂對照**前一天那一輪** r1 的聚合分數，`answer_correctness` **−.009**，而門檻是 .007

|---|---|---|---|---|
| context_recall | .774 | .780 | .006 | .017 |
| context_precision | .804 | .817 | .013 | .046 |
| nv_context_relevance | .969 | .969 | .000 | .008 |
| faithfulness | .816 | .819 | .003 | .010 |
| answer_relevancy | .855 | .858 | .003 | .004 |
| **answer_correctness** | **.642** | **.630** | **.012** | **.007** ⚠ |

**同一份輸入、同一個 judge，correctness 差 .012** → 那條 .007 的門檻是錯的（來自單一對樣本）。
改用同期的 passB 當基準重比，after2 的真實差值是 **+.003**，六個指標**全部在噪音內、全為正或持平**。
→ `NOISE["answer_correctness"]` **.007 → .012**（取兩對較大值）。

**兩個教訓，第二個比第一個難堪：**
1. **跨輪比 RAGAS 聚合值 ＝ 把 judge 噪音算進系統差異。** A/B 兩臂要在同一批判分裡比，
   或各自附一個同期基準。已把這句話印進 `eval_ragas_vs_rubric.py` 的判讀護欄。
2. **寫下警告不等於服從警告。** 那支腳本的註解裡本來就寫著「**一對樣本只是噪音的一次抽樣，
   不是噪音的上界**」——寫得完全正確，然後同一段程式仍然用一對定了 correctness 的門檻，
   而我引用那個門檻時也沒有回頭看那句話。⚠ 引用任何 `NOISE` 常數之前，先看它是幾對量出來的。

**逐題差分（兩臂配對）**：總和 **+0.184**、平均 **+0.003**。
被修法動到的 6 題（Fundamentals 從零比率 chunk 換成 `#0`）平均 **−0.029**，
其餘 59 題（碼路徑不可達）平均 **+0.006**。
⚠ **這個 −0.029 不足以下結論**：n=6，而單題波動輕易到 ±0.3（實測 `col-11` −.46、`col-08` +.45，
兩題都在碼路徑之外）。要判斷「補進 `#0` 會不會誘使模型在該答財期值時改答 TTM」，
需要的是**針對那 6 題的逐題人工複審**，不是聚合分數——已記進 [`BACKLOG.md`](BACKLOG.md)。

**端到端修好之後**（`experiments/agentic/gj_lex17_smoke.json`）：`lex-17` 三條全 PASS，答案引到
Fundamentals `#0`、明列 **TTM 18.30%**，每個數字都標了所屬期間。口徑警語**沒印**是對的
（沉默條件③：引用裡已經有 TTM）。
⚠ 兩點殘留，不要當成修好：① 開頭第一句仍以 10-K 財年 **18%** 當結論；
② `anchored_pct` 是靠 `expect_text` 析取才 PASS（anchor 抓到的仍是 18%）
——**它現在和 `require_text` 幾乎重複，名字說的事情已經不再量了**。這是量尺放寬的常見代價：
加一條析取讓它更容易通過，判別力就從那一條身上轉移走了。

### 「永不過期」被誤用成「能證明夠新」：拔除新聞才暴露的時效洞（2026-08-19，**改 web 觸發條件前必讀**）

**怎麼發現的**：使用者確認「證據後置」設計之後，第一步是**量 Grader 到底有沒有照設計運作**。
零 LLM、真實檢索池、8 個問題 —— 結果 6 個即時類問題**有 4 個時效改判不會觸發**。

| 問題 | need | 池中最新日期 | 修前的時效改判 | 修後 |
|---|---|---|---|---|
| 蘋果最近有什麼消息？ | days | 2026-06-30 | ✅ 觸發 | ✅ |
| **微軟最近有什麼消息？** | days | **2026-12-31** | ❌ 不觸發 | ✅ |
| **NVIDIA 最近有什麼新進展？** | days | **2026-12-31** | ❌ 不觸發 | ✅ |
| 特斯拉最近有什麼消息？ | days | 2026-06-12 | ✅ | ✅ |
| **微軟現在的股價是多少？** | **intraday** | **2026-12-31** | ❌ 不觸發 | ✅ |
| **NVIDIA 目前的市值多少？** | **intraday** | **2026-12-31** | ❌ 不觸發 | ✅ |

⚠ **這張表量的是「時效改判有沒有觸發」，不是「web 會不會被叫」——第一版把兩者混為一談，
已更正。** 後續對照（舊行為 vs 新行為，同池同 Grader）顯示這 4 題**舊碼下 web 一樣會被叫**，
因為 Grader 自己就判 `sufficient=False`。**主防線是 LLM 的判斷，時效改判是第二道。**
這是〈稽核回報 FAIL，先問是不是量尺錯〉的鏡像：我量到一個元件失效，卻報成了系統級失效。

**這個 bug 的真實代價**（兩項，都成立）：
① `kb_unfixable` 恆為 `False` → 每個子問題白燒 `MAX_REWRITES=2` 輪改寫才走 web。
   **那正是 `kb_unfixable` 被造出來要防的死迴圈**（2026-08-14：7 子問題 × 3 輪 = 21 次檢索空轉）。
② **第二道防線被靜默關閉**：LLM 若判錯 `sufficient=True`，就沒有任何東西接得住。
   ⚠ 這一項的價值**無法在「LLM 判對」的題上量到**——要量它得構造 LLM 會判錯的題，目前沒有。

**根因**：`_source_newest_date` 把 10-K 的 4 碼財年戳一律算成該年 12/31 ——
`MSFT_10K_2026` → **2026-12-31，未來日期**。而 `_stale_for_realtime` 取全池 `max(dates)`。
於是財報不只是**棄權**，它**替整個候選池背書說「夠新」**。

**「永不過期」與「能證明夠新」是兩件事，舊碼把它們混成同一件。** 這個混淆在 KB 有新聞時無害
（池裡有 8 碼真實日期的新聞 chunk 壓著 max）；新聞拔掉後財報成了唯一日期來源，洞就露出來了。

⚠ **這個行為是刻意的，而且被斷言釘住**：`verify_web_gate_isolation` 閘門⑤ 原本有一條
`("即時 vs 10-K（財年期間非發布日）", "intraday", Y, False)` —— 直接斷言「10-K 不判過期」。
它的**原意是對的**（別讓財報去*觸發* web），錯在實作用 `max()` 讓它變成背書。

**⚠ 4 題裡只有 1 題是拔除新聞造成的。** 「微軟最近有什麼消息？」含「消息」二字，以前會被
`looks_like_news_query` 硬路由到 `doc_type=news`、池子裡只有新聞 → 洞被遮住。
另外 3 題（含最危險的「微軟現在的股價是多少？」）**從來沒被那道路由攔過 ＝ 洞一直都在**。
也就是說 CLAUDE.md 那句「漏網的代價是把三週前的數字講成『今天股價』」，
對 MSFT／NVDA 一直有一個沒被發現的缺口。

#### 修法：把「時效證據資格」寫成明文

新增 `_is_freshness_evidence(source)`：**只有 8 碼真實日曆日期算證據**（現況 ＝ Fundamentals；
新聞若復活也是）。4 碼財年／6 碼財報期間**不算證據，也不算過期**——它們單純不參與這個判斷。
`_kb_ceiling_date` 必須套用**同一套資格判準**（它的 docstring 本來就要求兩邊同算法）。

沒有任何合格證據時回傳哨符 `NO_REALTIME_SOURCE(-1)`，Grader 的 `missing` 訊息分流成
「候選中沒有任何能證明時效的來源」。

**⚠ 這推翻了一個先前刻意的成本判斷，理由是算式反轉了。** 舊註解寫：

> 誤判過期會叫 web 白跑一趟，誤判新鮮只是維持現狀，前者才是我們要避免的成本。

**那句話在 KB 有新聞時成立**（「維持現狀」＝ 用幾天前的新聞回答）。KB 只剩財報之後，
「維持現狀」＝ **拿 10-K 回答今天股價**，成本大得多。所以對 `intraday`／`days`
改成「證明不了夠新就上網」，而 `none`（財報期間數字）維持永不過期、完全不受影響。

#### 閘門⑤ 新增的兩條

- **回歸鎖**：`("未來日期的 10-K 不得蓋過真實日期來源", "days", Y+F, True)`
  —— 舊碼 `max(2026-12-31, 2026-06-12)` 落在未來 → 判不過期；新碼只認 8 碼 → 62 天。**這條在新舊實作之間有判別力。**
- **誤報對照**：`("池裡有 1 天前的真實日期來源 → 不判過期", "intraday", Y+FRESH, False)`
  —— 沒有它，「一律判過期」也會全綠。

#### LLM 那半：8/8 且零抖動（`eval/probe_realtime_need.py`，2026-08-19）

修好 Python 半之後，整條路只剩 `realtime_need` 分類沒被量過。8 題 × 3 輪：

**危險錯誤（實時題判成 `none`）0 題、浪費錯誤 0 題、跨輪不穩定 0 題。**

判讀要看**不對稱的錯誤**而不是整體準確率：`none` 誤判成實時只是白燒一次 web；
實時誤判成 `none` 才是「拿 10-K 回答今天股價」。四題 `none` 是**陰性對照不可省**——
少了它們，一個「一律回 `days`」的 Grader 也會滿分。

其中「**NVIDIA 最近有什麼新進展？**」不含「新聞／消息／報導」任何字樣，正是被拆掉的
`looks_like_news_query` 詞表會漏的形狀（18 個措辭漏 10 個）。LLM 判準接住了——
**這是「詞表換 LLM 判斷」這個決定的第一組正面證據。**

⚠ 這支**不是閘門**：MoE 不固定路由，8/8 是這一次的觀測不是保證。要當回歸保護請釘成
`llm_replay` fixture。

#### 方法論

兩個方向的教訓，都在同一件事上：

**① 沒有人回報過故障**，因為「時效改判沒觸發」不會拋錯、不會 FAIL，只會讓 agent 多燒兩輪
改寫。量到它的唯一原因是**先寫下「這個機制應該怎麼運作」再去量**，而不是等它出事。

**② 但第一版把元件失效報成了系統失效。** 我量到 `_classify_staleness` 不觸發，就寫成
「web 不會被叫」——沒有去看生產閘門其實是 `not verdict["sufficient"]`，而 LLM 那一路
獨立成立。**這正是〈稽核回報 FAIL，先問是不是量尺錯〉的鏡像**：確認缺陷時，要問的是
「這個失效傳得到端到端嗎」，而查證成本只是**再跑一次同樣的對照、把舊行為裝回去**。

### 量測噪音與重放快取（2026-08-09，**跑任何 A/B 之前必讀**）

**核心事實：這個專案的量測解析度比多數改動的效果粗一個數量級。**

| 噪音層 | 實測 | 量法 |
|---|---|---|
| RAGAS judge | `context_precision` **0.046**（兩次獨立樣本 0.0459／0.0452 複現）、`context_recall` 0.002～0.013 | 同一份結果檔重評兩次（`--from-results` 指同一檔、`--output` 換名） |
| Plan 節點 | **12/25 題（48%）子問題不同** | 同輸入連呼叫 `_plan_subqueries` 兩次 |
| query 英譯 → 檢索 | **47/100 題 top-8 不同** | 同組態完整重跑兩次 |

`temperature=0` **不等於**確定性：`gpt-oss-120b` 是 MoE，溫度只固定取樣、不固定專家路由。
**MDE（95%, n=100）**：recall 0.029／precision 0.036／faithfulness 0.028／correctness 0.019 —— 換算成「要幾題從 0 修到 0.5」是 **4~7 題**。ingest 層那種「動 2~5 題」的改動在原理上就量不出來。

**跑 A/B 的正確做法**：設 `RAG_REPLAY_CACHE=eval/replay_cache.json`（見 [`llm_replay.py`](../llm_replay.py)），兩臂共用同一份 plan／英譯／Grader 決策，差異才只剩你改的那一項。**同一份 fixture 內別再重生成**——它跟 `reference_answers.json` 一樣，不需要唯一正確，只需要固定且對所有組態一視同仁。

**但共用一份 fixture 只是 K=1 個 block**：結論條件於那一次 plan 抽樣，分不出「B 真的較好」與「B 在這個 plan 下剛好較好」。要多 block **不需改碼**——`RAG_REPLAY_CACHE` 是路徑，一個 block 一個檔，block 內兩臂共用、跨 block 重抽（同 block 內**必須先後跑**，並行＝兩臂都 miss＝等於沒 block）。⚠ **blocking 是必要條件不是充分條件**：擋不住 Grader（跨 collection 必然 miss，而那是對的）、生成層 `GEN_TEMPERATURE=0.3`、RAGAS judge，所以「已經 blocked」≠「差異可解讀」。旗標語法與其餘細節見 [`llm_replay.py`](../llm_replay.py) docstring。

**指標的可追空間**（把 `reference_answers.json` 原文當答案餵回去評分，n=100，判讀護欄會自動印）：

| metric | 系統 | gold 當答案 | 判讀 |
|---|---|---|---|
| answer_correctness | 0.651 | **0.989** | **唯一有空間的指標** |
| faithfulness | 0.820 | **0.656** | **負空間**——gold 自己 61/100 題輸給系統，停止追 |
| answer_relevancy | 0.823 | 0.842 | 幾乎無空間 |
| context_precision | 0.867 | 0.822 | 噪音 0.046，單次差異不可解讀 |
| nv_context_relevance | 0.968 | 0.965 | 已飽和 |

> ⚠ **2026-08-09 起 `strip_citation_footer` 也剝句末 inline `【檔名, chunk #N】`**（佔答案本文 25% 字元）→ **當日之後的數字與之前的結果檔不可比**。剝除的理由是「像比像」不是「分數變好」——實測 correctness 反而 -0.041。
> ⚠ **「確定性指標」不會自動變確定**：量測路徑上只要還有一次 LLM 呼叫（例如 `full_translate_en` 的英譯），它就跟 RAGAS 一樣髒。用它驗收前先跑一次同組態重複量噪音。
> ⚠ **不要拿落在噪音裡的數字反推機制**——機制聽起來越合理越危險。2026-08-09 一天內提出三個機制假設、三個都被自己的確定性測試推翻（詳見 [`CHANGELOG_AGENTIC.md`](../CHANGELOG_AGENTIC.md) A5.5）。

**目前最大的未動槓桿**：`_check_sufficiency` 的 `relevant_ids` 只留下 **49.3%** 的候選（18/58 題最後只剩 1 個 chunk，全 100 題中位數 3 個），而 `context_recall ↔ correctness` 相關 0.53 是六指標最強、`precision ↔ correctness` 只有 0.14。等於每題用一次 LLM 判斷丟掉一半證據，換一個跟答對與否幾乎無關的指標。
> ⚠ **但「單純放寬候選數」已經量過，是零效果**——2026-08-05 的 `gj_widen_pool12_full100`：證據字元 +32%（6285→8305）、correctness **0.626→0.625**、precision **−0.053**、nv_relevance −0.028。多出來的席位裝的是冗餘。**要動的是「同樣 5 個席位裝 5 份不同證據」（Grader 前確定性去重），不是席位數。** 這條 null result 當時沒進 changelog，導致 2026-08-11 又提了同一個實驗跑到 40% 才被抓到——**提檢索層實驗前先 `ls experiments/`**，詳見 [`CHANGELOG_AGENTIC.md`](../CHANGELOG_AGENTIC.md) (6) 的 08-11 補記。

### 數字缺陷指標的五次失效（2026-08-10／2026-08-19，**拿它當閘門前必讀**）

`check_number_defects.py` 原本用「答案的第一個百分比 vs gold 的第一個百分比」。**四種比法被實測推翻，一天內兩輪**：

| 比法 | mix-03（確診答錯：答 24%，合併實為 20%） | 副作用 |
|---|---|---|
| 比**第一個** | 抓到 ✅ | col-11／mi-04／mi-08 **誤報**——頭條挑了 Azure 40%／LTM 12.8%，內容其實對 |
| 比**任一個** | **漏抓 ❌** | 答案的 21%（Productivity 分部）落在 gold 20% 的 ±1pt 內 |
| 接地後**先往後找、後往前找** | 抓到 ✅ | mi-04 **誤報**：head 寫「**16.6%（YoY）**，若以 LTM 計算則為 **12.8%**」→ 值在 anchor **前**，往後撈到別的主張 |
| 接地後**取最近（雙向）** | 抓到 ✅ | col-11 **誤報 1~2 個 run**：「Azure 40%，整體 Microsoft Cloud 則 29%」→ 最近的是 40% |

→ 兩層教訓。**第一層：不接地不行**——答案裡有 4~8 個百分比、容差 ±1pt，任何值幾乎都能湊到。**第二層：接地後「挑哪一個值」也猜不出來**——值在 anchor 前或後都是合法中文寫法，方向與距離都會在某個 run 上誤報。現行做法是問**集合成員關係**（`anchored_pcts`：anchor ±N 內的百分比集合，正解在不在／禁止值在不在），與措辭方向無關，實測 ±40／±60／±80 三個窗口結果相同。
> ⚠ **判別力由 `forbid_pct` 承擔，不是 `expect_pct`**：只問「正解在附近嗎」時，答案把正解與干擾值並陳也會 PASS。所以 `known_defect` 必須填 forbid（`_validate_claims` 啟動時強制），`regression_guard` 可以只填 expect。
> ⚠ **forbid 只在「錯值不會與正解正當並存」時可用**：col-11 的 Azure 40% 與 Cloud 29% 正當並存於鄰近，把 40 填成 forbid 會誤報兩個正確的 run。

> ⚠ **兩個記帳坑，都害過事**：
> ① **「某個 run 沒給百分比」被算成衝突** → 兩檔並列得到 10、單檔卻是 6／4／5。當時據此把閘門門檻設成「衝突 8 → ≤5」，**門檻與被比較的數字不可比，等於這道閘門沒有判定力**。現在分成獨立的「無法比對」桶，且**每個 run 各自算**。
> ② 稽核腳本第一版回傳「0 筆假象」不是好消息，是 gold 欄位名寫錯（`reference_answer` vs 正確的 `reference`）。同 memory `eval-measurement-pitfalls`。
#### 第五次（2026-08-19）：anchor 措辭寫死，答對了卻判成 N/A

`col-11` 的 anchor 是 `Microsoft Cloud|整體雲端`。2026-08-19 的 run **答對了**——「雲端營收較去年同期大幅上升 **29%** 至 545 億美元」——但它用的措辭是「雲端營收」，anchor 整條落空 → 判 **N/A**。

這是 `anchored_pct` 最危險的失效方式，**跟前四次不同**：前四次是判錯（FAIL/PASS 給反），這次是**護欄安靜地停止量測**。三態設計本來就是為了不讓它變成 PASS（做對了），但 N/A 只有在**有人真的去看**的時候才會變成資訊——量尺不會自己說「我這次沒量到東西」。

修法是把 anchor 放寬成 `Microsoft Cloud|整體雲端|雲端營收|雲端服務`。⚠ **放寬的判準是「同一個主張的其他合法中文寫法」，不是「把更多數字納進窗口」**——前者恢復判別力，後者會讓不相干的百分比落進集合、把 expect 變成幾乎必中。`expect_pct` 仍是 29、仍不設 `forbid_pct`（Azure 40% 與 Microsoft Cloud 29% 正當並存）。

⚠ **這條與 CLAUDE.md〈硬編碼詞表是警訊〉不衝突，但很接近**：anchor 本質上就是詞表，所以它**只能用在「已人工驗證過的單一主張」上**，不能拿來做感知。真正的防線是 N/A 必須人工看——這次就是這樣抓到的。

> ⚠ `number_claims.json` 的每一條都要**人工驗證過才登錄**（`verified` 欄位寫怎麼驗的）。`status` 兩種：`known_defect`（現在會 FAIL，修好要變 PASS）／`regression_guard`（現在 PASS，防日後退步）。

### A5.5 2026-08-09 量測基礎建設：先讓實驗可被相信，再談優化

這一節不是功能改動，是**把「為什麼指標優化不動」查到底**的結果。結論是：**量測的解析度比改動的效果粗一個數量級，而且量測路徑自己也在抖。**

#### (1) 三層噪音，全部大於訊號

| 層 | 實測 | 量法 |
|---|---|---|
| RAGAS judge | `context_precision` 均值移動 **0.046**（兩次獨立樣本 0.0459 / 0.0452 複現）；`context_recall` 0.002 / 0.013 | 同一份結果檔重評兩次 |
| Plan 節點 | **12/25 題（48%）子問題不同** | 同輸入、`temperature=0` 連呼叫兩次 |
| query 英譯 → 檢索 | **47/100 題 top-8 不同**（重複對 149 vs 151） | 同組態完整重跑兩次 |

`temperature=0` 不等於確定性——`gpt-oss-120b` 是 MoE，溫度只固定取樣、不固定專家路由。

**MDE（95%, n=100）**：recall 0.029 / precision 0.036 / faithfulness 0.028 / correctness 0.019 → 換算成「要幾題從 0 修到 0.5」是 **4~7 題**。而 ingest 層的改動（期間邊界 11 個 chunk、影響 2 題）**在原理上就量不出來**。這不是運氣，是設計問題。

#### (2) `llm_replay.py`：檢索前 LLM 中間產物的重放快取

接三個點：`_plan_subqueries`、`translate_query_to_english`、`_check_sufficiency`。未設 `RAG_REPLAY_CACHE` 時**完全 no-op，生產路徑不受影響**。

**key 的兩個相反設計，各有理由**：
- plan / translate 的 key **不含 system prompt** —— planner 的 prompt 內嵌隨 collection 變動的 KB Coverage Snapshot，納入 key 會讓跨 collection A/B 全部 miss，正好毀掉唯一用途。副作用：改 planner prompt 時快取不會自動失效，要手動刪檔。
- checker 的 key **含這次看到的候選 id** —— 候選變了是**合法 miss**，那正是被測改動造成的差異，用舊決策蓋掉會把訊號洗掉。

**它買到什麼、買不到什麼**：買到 A/B 兩臂共用同一份 plan；**買不到生產端穩定**（MoE 路由不確定不打算解）。代價是固定下來的是「某一次抽樣」不是「正確答案」——跟 `reference_answers.json` 同一種東西，**定版後別再重生成**。

fixture：`eval/replay_cache.json`（plan 100 / translate_en 181 / check 206）。

#### (3) 判讀護欄：讓分數無法被誤讀

`eval_ragas_vs_rubric.py` 每次跑完在 OVERALL 底下印出每個指標的**噪音門檻**與 **gold 上限**。gold 上限來自把 `reference_answers.json` 原文當成系統答案餵回去評分（n=100）：

| metric | 系統 | gold 當答案 | 判讀 |
|---|---|---|---|
| answer_correctness | 0.651 | **0.989**（85/100 滿分） | 唯一有空間的指標，距上限 0.338 |
| faithfulness | 0.820 | **0.656**（61/100 輸給系統） | **負空間**，停止追 |
| answer_relevancy | 0.823 | 0.842 | 幾乎無空間 |
| context_precision | 0.867 | 0.822 | 噪音 0.046，量不出來 |
| nv_context_relevance | 0.968 | 0.965 | 已飽和 |

faithfulness 是負空間的原因：gold 依 `gold_files` 生成，與 agentic 實際撈到的 contexts 不同源。**繼續往上推等於要求系統答得比標準答案還保守。**

**推翻的舊結論**：`recall==1.0` 的 44 題，系統 correctness 0.724、gold 0.983 —— 證據全到位仍差 0.26，**瓶頸在生成層不在檢索層**。（先前我用 0.724 論證「correctness 有天花板」是錯的，gold 拿得到 0.989。）

#### (4) 剝 inline 引用標記：留下，但理由不是分數

`strip_citation_footer` 現在同時剝句末 `【檔名, chunk #N】`（佔答案本文 **25.0% 字元**）。**實測分數反而變差**：judge 重評 28 題 correctness **-0.041**；而零 LLM 的確定性測試顯示相似度分量只變 **+0.0011**（cosine 0.9105→0.9148），**「檔名雜訊稀釋 embedding」的假說證偽**。殘差來自 0.75 權重的 statement F1，未查清。

保留是方法論選擇（引用是 metadata、reference 一個都沒有，剝掉才 like-for-like）；照「分數變低就退回」做就是在 gaming 量尺。⚠ **這使 2026-08-09 之後的數字與之前的結果檔不可比。**

#### (5) 兩個 ingest/檢索層改動改成預設關閉

| 改動 | 量測 | 處置 |
|---|---|---|
| `_strip_tabular_blocks`（壓平表格去重） | 六指標無明確勝方；核心指標 precision 的差落在噪音內 | `--strip-dup-tables`，**預設關閉** |
| `_suppress_near_duplicates`（檢索層近重複抑制） | top-8 重複對 149→139（噪音區間 149~151，訊號約噪音 5 倍，**有效但很小**）；而最終 contexts 的重複本來就只有 18 對 / 11 題，**Grader 已清掉 88%** | `RAG_SUPPRESS_NEAR_DUP=1`，**預設關閉** |

#### (6) 尚未動的最大槓桿：Grader 保留率

`_check_sufficiency` 的 `relevant_ids` 只留下 **49.3%** 的候選（58 題單一子問題、池固定 5 → 143/290），**18/58 題最後只剩 1 個 chunk**，全 100 題最終 chunk 數中位數 = **3**。而 `context_recall ↔ correctness` 相關 **0.53**（六指標最強），`precision ↔ correctness` 只有 0.14。

**這條管線每一題都在用一次 LLM 判斷丟掉一半證據，換來一個跟答對與否幾乎無關的 precision。** 這是唯一每題都作用、因此唯一有機會超過 MDE 的系統性改動。正確的消融是**把確定性去重放在 Grader 之前**（讓 5 個席位裝 5 份不同證據），而不是單純放寬保留率。

##### 補記（2026-08-11）：「單純放寬」已經被量過了，是零效果

上面那句「不是單純放寬保留率」當時是推論。**2026-08-05 其實已經跑過完整 100 題**，只是結果檔沒進 changelog（`gj_widen_pool12_full100` / `gj_pool10_clean`，都在 `exp4` 上）——於是 2026-08-11 我又提了同一個實驗，跑到 40% 才被使用者一句「上次 grader 放寬不是反而會帶來更多雜訊嗎」問住，回頭翻檔案才發現。

| | 基準 `gj_v2_full100_20260806` | `pool10` | **`widen_pool12`** |
|---|---|---|---|
| 平均 chunk 數/題 | 3.04 | 3.29 | 3.94 |
| **平均證據字元/題** | 6285 | 6532 | **8305（+32%）** |
| **answer_correctness** | 0.626 | 0.625 | **0.625** |
| context_precision | 0.835 | 0.828 | **0.782（−0.053）** |
| nv_context_relevance | 0.958 | 0.925 | **0.930（−0.028）** |

**+32% 證據量 → correctness 動 0.001，precision 掉 0.053。** 多出來的席位裝的是冗餘與不相關。

**連帶推翻一個當天才提出的機制**：head collection 每題證據字元比 period 少 23%（8434→6525，chunk 數不變、chunk 變短），我據此推論那是 head correctness −0.032 的成因。但 **+32% 都動不了 correctness，−23% 就不可能是原因**。head 非 AAPL 那 42 題的退步目前**沒有已證實的解釋**。

**紀律補一條**（`verify-mechanism-before-claiming` 的前置步驟）：提實驗之前先 `ls experiments/` 找同名干預——**能證偽假設的測試可能已經跑過了**，而未寫進 changelog 的 null result 等於下次一定重跑。

#### 方法論教訓（當天犯了三次同一個錯）

| 我的機制假設 | 推翻它的確定性證據 |
|---|---|
| 「移除冗餘剝奪 chunk 自足性」（precision -0.0205） | judge 噪音 0.046，兩次複現 |
| 「correctness 有天花板」（perfect recall 只有 0.724） | gold 當答案拿 0.989 |
| 「inline 標記稀釋 embedding」 | 確定性 cosine 差 +0.0043 → 影響 +0.0011 |

共同模式：**先看到數字，再編一個合理的機制，然後沒去驗那個機制。** 定為紀律——**任何機制宣稱都要先有一個能證偽它的確定性測試**（零 LLM、可重跑、無抽樣變異）。另外：「確定性指標」不會自動變確定，只要量測路徑上還有一次 LLM 呼叫，它就跟 RAGAS 一樣髒。

## 反覆出現的方法論教訓
繞過 brain 測 ≠ 真實 graph／先排除工具環境毛病再懷疑系統／單次 LLM-judge 不能論因果、要確定性消融／
別過度外推（file-level 無效 ≠ chunk-level 無效、edgar_exp4 無效 ≠ 全面無用）／prompt 是機率不是保證，
grounding/citation 要靠 Python 強制不靠拜託模型。

## 操作備忘（文件重整時從 CLAUDE.md 收攏過來）

**標準跑法**（三步；reference 只需生成一次可重用）
```bash
# ① 生成 ground truth（已存在就不必再跑；--force 不帶 --ids 會洗掉人工校正）
.venv/Scripts/python.exe eval/gen_reference_answers.py

# ② 產生結果檔：agentic 版
.venv/Scripts/python.exe eval/run_agentic_on_evalset.py --module agentic_rag_v2 \
    --freshness-mode snapshot --output experiments/agentic/<名稱>.json
#    單管線版
.venv/Scripts/python.exe eval/eval_generation_llm_judge.py --output experiments/<名稱>.json

# ③ 切 .venv-ragas 算六指標
.venv-ragas/Scripts/python.exe eval/eval_ragas_vs_rubric.py \
    --from-results experiments/agentic/<名稱>.json \
    --reference-file eval/reference_answers.json --output experiments/agentic/ragas_<名稱>.json
```

- **只改動少數題的 reference 時不必重跑全部 RAGAS**：RAGAS 每題獨立評分，用 `--ids <題號…>` 只評改動題，再把新分數拼接回原結果。全部重跑只是多疊一層 judge 噪音。
- ⚠ **`eval_generation_llm_judge.py` 與 `eval_ragas_vs_rubric.py` 的 `--output` 預設值仍指向 `eval/`**，跑的時候要自己帶 `--output experiments/...`。`eval/` 只放輸入與標準答案；過期產物在 `eval/_archive_stale/`（未納版控，刪掉即永久遺失，所以只歸檔不硬刪）。
- **新機器還原評測環境**：`python -m venv .venv-ragas` → `pip install -r requirements-ragas.txt`（2026-08-07 用 `pip install --dry-run` 驗過：解析出 97 個套件，與當時環境的數量與關鍵版本一致）。兩個環境為何不能合併見 [`../README.md`](../README.md) §4-1。
- ⚠ **`answer_correctness` 偏低常是量尺問題**（長度對齊／false-negative gold），不是系統答錯——下結論前先讀 memory `ragas-correctness-length-artifact`、`eval-false-negative-gold`，以及本檔的〈判讀護欄〉。
