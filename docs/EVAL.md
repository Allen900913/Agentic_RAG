## 零、五條判讀鐵律

這五條是全檔反覆出現的教訓，每一條都被違反過至少一次：

1. **先問「這個差值超過噪音嗎」，再問「為什麼」。** MDE（95%, n=100）換算成「要幾題從 0 修到 0.5」是 **4~7 題**，而典型 ingest 改動只動 2~5 題。**不要拿落在噪音裡的數字反推機制——機制聽起來越合理越危險。**
2. **任何機制宣稱都要先有能證偽它的確定性測試**（零 LLM、可重跑、無抽樣變異）。實測有四個「聽起來合理」的機制假設被自己的測試推翻。
3. **稽核回傳「0 筆問題」先當壞消息查；稽核回報 FAIL，先問「是不是量尺錯」。** 兩個方向的查證成本一樣是一次 `grep`，而錯誤結論會被寫進文件。
4. **量尺不可與被測物耦合**（犯過六次）。兩種形狀：① 量尺**讀了修法會改動的產物**（陽性一修好就消失）② 量尺**自備輸入**，於是從來沒驗過生產供不供得出那個輸入。
5. **N/A 不能併進 PASS。** 它是「這一輪沒量到東西」不是通過——量尺不會自己說「我這次沒量到東西」。

## 二、量測噪音與重放快取

**核心事實：這個專案的量測解析度比多數改動的效果粗一個數量級。**

| 噪音層 | 實測 | 量法 |
|---|---|---|
| RAGAS judge | `context_precision` **0.046**（兩次獨立樣本 0.0459／0.0452 複現）；`answer_correctness` **0.012** | 同一份結果檔重評兩次 |
| Plan 節點 | **12/25 題（48%）子問題不同** | 同輸入連呼叫兩次 |
| query 英譯 → 檢索 | **47/100 題 top-8 不同** | 同組態完整重跑兩次 |

**`temperature=0` 不等於確定性**：`gpt-oss-120b` 是 MoE，溫度只固定取樣、不固定專家路由。

**MDE（95%, n=100）**：recall 0.029／precision 0.036／faithfulness 0.028／correctness 0.019 → **要幾題從 0 修到 0.5＝4~7 題**。ingest 層那種「動 2~5 題」的改動**在原理上就量不出來**。

### 噪音常數的兩個陷阱

⚠ **一對樣本只是噪音的一次抽樣，不是噪音的上界。** `NOISE["answer_correctness"]` 一度定成 .007（單一對），據此把一個 −.009 的差值判成「略高於噪音的下降」並開始找機制——**它是假的**：同一份輸入再餵 judge 一次就差 .012。改用同期基準重比後真實差值是 **+.003**。
> **兩個教訓，第二個比第一個難堪**：① **跨輪比 RAGAS 聚合值 ＝ 把 judge 噪音算進系統差異**，A/B 兩臂要在同一批判分裡比。② **寫下警告不等於服從警告**——那支腳本的註解裡本來就寫著「一對樣本不是噪音的上界」，然後同一段程式仍然用一對定了門檻。**引用任何 `NOISE` 常數之前，先看它是幾對量出來的。**

⚠ **取新舊較大值。** `context_precision` 新測 .005 看起來噪音小了十倍，但舊值 .046 的成因寫在碼上——**precision 對每個 context 做二元判定再依排名加權，最高排名那個判定翻面整題就 1.0→0.0**。這次剛好沒翻，不代表它不會翻。**門檻取大只會要求更多證據，錯的方向是安全的那一邊。**

### `llm_replay.py`：把 A/B 變成受控實驗

設 `RAG_REPLAY_CACHE` → 兩臂共用同一份 plan／英譯／Grader 決策／ratio／期間意圖／ticker，差異才只剩你改的那一項。

**key 的兩個相反設計，各有理由**：
- plan／translate 的 key **不含 system prompt** —— planner 的 prompt 內嵌隨 collection 變動的 KB Coverage Snapshot，納入 key 會讓跨 collection A/B 全部 miss，**正好毀掉唯一用途**。副作用：改 planner prompt 時快取不會自動失效，要手動刪檔。
- checker 的 key **含這次看到的候選 id** —— 候選變了是**合法 miss**，那正是被測改動造成的差異，用舊決策蓋掉會把訊號洗掉。

⚠ **blocking 是必要條件不是充分條件**：擋不住 Grader（跨 collection 必然 miss）、生成層 `GEN_TEMPERATURE=0.3`、RAGAS judge。所以「已經 blocked」≠「差異可解讀」。
⚠ **共用一份 fixture 只是 K=1 個 block**：結論條件於那一次 plan 抽樣。要多 block **不需改碼**——`RAG_REPLAY_CACHE` 是路徑，一個 block 一個檔，block 內兩臂共用、跨 block 重抽（**同 block 內必須先後跑**，並行＝兩臂都 miss＝等於沒 block）。
⚠ 買到的是「A/B 兩臂共用同一份中間產物」，**買不到生產端穩定**（MoE 路由不確定不打算解）。固定下來的是「某一次抽樣」不是「正確答案」——跟 `reference_answers.json` 同一種東西，**定版後別再重生成**。

> ⚠ **2026-08-09 起 `strip_citation_footer` 也剝句末 inline `【檔名, chunk #N】`**（佔答案本文 25% 字元）→ **當日之後的數字與之前的結果檔不可比**。剝除的理由是「像比像」不是「分數變好」——實測 correctness 反而 −0.041，而零 LLM 的確定性測試顯示相似度分量只變 +0.0011（**「檔名雜訊稀釋 embedding」的假說證偽**）。照「分數變低就退回」做就是在 gaming 量尺。
> ⚠ **「確定性指標」不會自動變確定**：量測路徑上只要還有一次 LLM 呼叫（例如英譯），它就跟 RAGAS 一樣髒。用它驗收前先跑一次同組態重複量噪音。

## 三、量尺飽和：切塊這條路已經到頂

**（提任何 ingest 實驗前必讀。）結論：RAGAS 的檢索類指標已經量不到切塊改動了，`answer_correctness` 的剩餘空間在生成層不在檢索層。**

### (1) 六個指標有五個已達或超過 gold 上限

上限常數＝**把 `reference_answers.json` 原文當成系統答案餵進去評的分數**。它回答「這個指標還有沒有可追空間」：

| metric | gold 上限（n=65） | 系統實測 | 判讀 |
|---|---|---|---|
| `context_recall` | .788 | .774 | 差 .014，噪音內 |
| `context_precision` | .843 | .804 | 噪音內 |
| `nv_context_relevance` | .969 | .969 | **到頂** |
| `faithfulness` | .659 | **.816** | **已超過（負空間）** |
| `answer_relevancy` | .871 | .855 | 幾乎無空間 |
| `answer_correctness` | **.972** | **.642** | **唯一有空間的（+0.330）** |

切塊／ingest 改動只能影響前三個檢索指標，而它們全部飽和。**再改也量不到，不是「改動沒效果」而是「尺沒有刻度了」。**

⚠ **`faithfulness` 是負空間**：gold 依 `gold_files` 生成、與實際 contexts 不同源，所以它自己拿不到高分。**往上推等於要求系統比標準答案更保守。停止追。**

### (2) 檢索已經不是瓶頸

把 100 題按檢索成敗分桶：

| 分桶 | 題數 | 平均 `answer_correctness` |
|---|---|---|
| `context_recall` = 1.0（檢索完全成功） | 44 | 0.684 |
| 0.5 ~ 0.99 | 42 | 0.669 |
| < 0.5（檢索失敗） | 12 | 0.543 |

檢索完美與檢索全失敗只差 **0.141**。就算把檢索全修到完美，correctness 也只推到 ~0.684 ＝ **+0.024，低於 0.067 的噪音底線**。而且 44 題檢索完美的題裡只有 5 題 correctness < 0.5。

**歷史軌跡佐證**：十二次全量跑分，`context_recall` 全落在 **0.73~0.77**、`answer_correctness` 全落在 **0.62~0.66**。整個離散範圍就是噪音寬度。

### (3) 剩下那 0.33 有多少是真的？部分不是

`answer_correctness` ＝ factual-F1(0.75) ＋ 語意(0.25)，主要由「系統答案 vs 固定 reference 的**詳略對齊**」決定。實例：`lex-07`（Apple FY2025 Diluted EPS）答 **$7.46**、`lex-14`（Meta）答 **$23.49**——**兩題數字都完全正確、引用也對**，correctness 卻只有 0.415／0.424。扣分來自參考答案多寫了佐證陳述（分子分母），RAGAS 的 statement-level F1 把它們算成 false negative。**它罰的是陳述集合的差異，不是對錯。**

⚠ 但**不能因此說整個 gap 都是假的**：gold 自己拿 .972，代表指標**給得出滿分**。量過 `log(答案長度比)` 與 correctness 的相關係數只有 **+0.125**（弱相關），也不是單純的冗長度問題。**目前沒有把「真的答錯」與「陳述顆粒度不同」分開的工具。**

⚠ **`answer_correctness` 別當 chunking／系統成敗閘門**，改用 recall/precision/faithfulness，或零噪音的逐條斷言。

### (4) 所以還能往哪走

1. **改生成層**——唯一還能動 `answer_correctness` 的槓桿，但要先想清楚要的是「答案更好」還是「分數更好」（`lex-07` 現在的答案對使用者已經夠好）。
2. **換量尺**——`check_number_defects` 那種確定性斷言是零噪音的，只是覆蓋率低。要數字驅動開發就得擴充它。
3. **接受現況收工。**

## 四、量尺自己壞掉的歷史

### 4.1 `check_number_defects` 的六次失效

`anchored_pct` 原本用「答案的第一個百分比 vs gold 的第一個百分比」。**四種比法被實測推翻，一天內兩輪**：

| 比法 | mix-03（確診答錯：答 24%，實為 20%） | 副作用 |
|---|---|---|
| 比**第一個** | 抓到 ✅ | col-11／mi-04／mi-08 **誤報**——頭條挑了 Azure 40%／LTM 12.8%，內容其實對 |
| 比**任一個** | **漏抓 ❌** | 答案的 21%（Productivity 分部）落在 gold 20% 的 ±1pt 內 |
| 接地後**先往後找、後往前找** | 抓到 ✅ | mi-04 **誤報**：「16.6%（YoY），若以 LTM 計算則為 12.8%」→ 值在 anchor **前** |
| 接地後**取最近（雙向）** | 抓到 ✅ | col-11 **誤報**：「Azure 40%，整體 Microsoft Cloud 則 29%」→ 最近的是 40% |

→ **兩層教訓。第一層：不接地不行**（答案裡有 4~8 個百分比、容差 ±1pt，任何值幾乎都能湊到）。**第二層：接地後「挑哪一個值」也猜不出來**——值在 anchor 前或後都是合法中文寫法。
現行做法是問**集合成員關係**（anchor ±N 內的百分比集合，正解在不在／禁止值在不在），與措辭方向無關，實測 ±40／±60／±80 三個窗口結果相同。

**第五次（anchor 措辭寫死）**：`col-11` 的 anchor 是 `Microsoft Cloud|整體雲端`，而某輪答案**答對了**卻用「雲端營收」這個措辭 → anchor 整條落空 → 判 **N/A**。
**這是最危險的失效方式，跟前四次不同**：前四次是判錯（FAIL/PASS 給反），這次是**護欄安靜地停止量測**。三態設計本來就是為了不讓它變成 PASS（做對了），但 **N/A 只有在有人真的去看的時候才會變成資訊**。

**第六次**：切片把百分比 token 剖半（`mix-09` 判 N/A 而答案是對的）。**這個量尺的兩次「答對了卻判 N/A」都不會叫，它只是安靜地停止量測。**

> ⚠ **判別力由 `forbid_pct` 承擔，不是 `expect_pct`**：只問「正解在附近嗎」時，答案把正解與干擾值並陳也會 PASS。
> ⚠ **forbid 只在「錯值不會與正解正當並存」時可用**。
> ⚠ **anchor 本質上是詞表**，只能用在「已人工驗證過的單一主張」上，不能拿來做感知。**放寬的判準是「同一主張的其他合法中文寫法」，不是「把更多數字納進窗口」**——後者會讓 expect 變成幾乎必中。
> ⚠ **兩個記帳坑**：① 「某個 run 沒給百分比」被算成衝突 → 門檻與被比較的數字不可比，等於這道閘門沒有判定力。現在分成獨立的「無法比對」桶，且**每個 run 各自算**。② 稽核腳本第一版回傳「0 筆」不是好消息，是 gold 欄位名寫錯。

### 4.2 「量尺與被測物耦合」的六次

| # | 形狀 | 怎麼被發現 |
|---|---|---|
| ①~③ | 量尺**讀了修法會改動的產物**（如端到端斷言讀 `experiments/`）→ 一修好陽性就消失、閘門自己失去判別力 | 修法生效後斷言當場 FAIL |
| ④ | `_news_freshness_gaps` 的 cutoff 讀真實 KB coverage，KB 拔掉新聞後三條陽性斷言測不出東西 | 閘門 FAIL，查出是量尺失去判別力不是機制壞掉 |
| ⑤ | anchor 措辭寫死 → 靜默 N/A | 人工看 N/A |
| ⑥ | **量尺自備輸入**：閘門⑪ 的 8 條斷言全部拿測試自造的 dict 餵進去、全綠，而生產的 `rq.retrieve()` **根本沒把 `period_basis` 放進 chunk dict** → validator 在線上結構性永遠不觸發 | 端到端 null result 後逐層印出來才發現 |

**⑥ 是最難自己發現的一種**：「payload 裡有這個欄位」和「chunk dict 裡有這個欄位」是兩件事，中間隔著一個建構子——而閘門⑪ 原本**有**一條活體斷言在掃 payload、PASS，**正好把人的注意力擋在建構子前面一步**。

→ **通則：驗證器讀哪個欄位，就要有一條斷言拿真實資料餵生產的建構路徑**，不能只驗資料源有那個欄位。實作上把建構抽成具名函式（`rq._payload_to_chunk`）就是為了讓這件事可測。
**變異測試把這個形狀直接照出來**：建構子不帶 `period_basis` → ⑪ 原本那 8 條照樣全 PASS，只有新加的 ⑪b 叫。

**修法要防的是「量尺讀了會被修好的東西」**：閘門② 的陽性答案因此**逐字凍結在測試檔裡，不讀 `experiments/`**。

### 4.3 false-negative gold（五批，全在 eval 側非系統）

reference 誤寫「來源未揭露」但語料白紙黑字有，**系統答對甚至比 gold 準，卻被打 recall=0**。兩個機制：(a) `relevant`/gold_files 範圍太窄漏標 (b) `gen_reference_answers.py` 檔內選錯 chunk 行/錯期別。

**全量稽核的結果（13 題 23 處錯，全部已修）**：
- **機械層 100% 乾淨**（glob 0 個落空、`pin_chunks` 全解析、逐字對齊、無 stale cache）。→ **量尺壞掉的地方全在語意層，機械檢查給不出警訊。**
- **10 倍單位錯 6 題 14 處**：來源寫 `$253.49B`，reference 直接抄成「253.49 億美元」（正解 2,534.9 億）。**對照組證明這不是隨機**——來源是 `(In millions)` 表格時換算全對（15 處 0 錯），**錯的只有「B 結尾」那一種字面**。
- **句內自我矛盾 2 題**（開頭「11.1 億」vs 內文「111.44 億」）→ **同一句話裡對的錯的並存，抽樣看必漏。**
- **期間錯置 2 題**（把 10-Q 的九個月累計當成單季）。

**根因＝防護「有印警告但不修」**：生成端早有兩道防護，但**重試耗盡後只 `print("⚠ 需人工檢查")` 就放行**，100 題輸出裡那行捲過去，沒有人檢查。同一種病在生成腳本裡共**四處**（`pin_chunks` 解析失敗靜默退回 dense-only／手轉「億」重試耗盡只印警告／快取只比對 `query` 不比對 `gold_files`／`lang` 預設 English）。

**修法＝勸不動就用程式修**（`repair_yi_against_source`）：三條件同時成立才動手——①來源有 `$N billion` ②來源沒有 `$N/10 billion` ③來源沒有 `$N*100 million`。回測 14/14 全抓、0 危險誤報。
> **寫 guard 時自己踩的兩個坑**（都被回測抓出來）：① 幣別標記寫成**可選** → 「10 億**使用者**」被當金額。**漏修無害、改壞有害，一律從嚴。** ② 「後接括號就當已雙寫」太粗 → 敘述性括號被誤跳過。

**方法論：判準要自足。** 「reference 的 N 億 vs 來源的 $N billion」單看會大量誤報（來源同時有 `$2.5B` 與 `$250 million` 就會撞），有效判準是 ① 雙寫括號內外自洽（`N 億美元（$M billion）` → N==M×10，全庫 0 錯）② 沒雙寫的才逐筆查來源字面單位。
⚠ **稽核腳本自身的 regex 也會騙人**：`(?![\w])` 抓不到 `$60.46B` 的尾隨 `B`，害四題被誤標「數字無出處」。

### 4.4 其他量尺特性

- **footer 毒害 faithfulness**：agentic 答案尾端的引用 footer 是 metadata、context 裡不存在 → RAGAS 逐 claim 判 unsupported，短答案佔比高被砸最重（**這解釋了 lexical 悖論：檢索近乎完美但 faith 全類最低**）。剝除後 faith 0.763 → **0.815**、lexical 0.672 → **0.889**。
- **`context_precision` 對多 chunk 比較題判定器不穩**：同一份 rec=1.0/faith=1.0/corr=0.89 的正確答案，precision 在 0/0.333/1.0 亂跳。**比較題（multi_hop）別信 precision 欄。**
- **`--from-results` 吃多個檔是「拼接同一臂」，不是 A/B**：同 id 的多筆會被平均，而那個平均正好落在歷史噪音帶裡、看起來毫無異常——**這樣燒掉過 2h49m**。
- **NaN 一定要補完再定稿**：補完前某差值是 +0.067（正好卡在門檻上），補完後 +0.063 明確落在噪音內。用 `--ids <失敗題>` 只重跑那幾題即可。
- **Python 輸出時 stdout 會被緩衝**（非 tty），背景跑分要加 `-u`。

### 4.5 live 量尺：斷言是零噪音的，輸入不是（2026-08-28）

`eval/web_claims.json` 的 `_meta` 自稱「判準是逐條斷言，零噪音」。**那個性質是從斷言的形式推來
的，沒有被量過。** 實際量了之後：

| 跑法 | web-02 | web-04 |
|---|---|---|
| mdna（cache 被污染） | PASS | FAIL |
| mdna（乾淨） | FAIL | FAIL |
| multiyear（cache 被污染） | FAIL | FAIL |
| multiyear（乾淨） | FAIL | **PASS** |
| multiyear 單題重跑 | **PASS** | — |

**同一份碼、同一個 collection，判定會翻面。** 教訓與 §4.2「量尺與被測物耦合」是同一族但形狀不同：
斷言本身確實是確定性的比對，**但餵給它的那一格（`n_web_calls`）是 LLM 決定的**。
→ **通則：判斷一把量尺是不是零噪音，要看它讀的欄位怎麼產生的，不是看它怎麼比對。**

三層成因，只有第三層是系統缺陷：

1. **fixture key 綁死 LLM 生成的 query 字面**（量尺問題）。Grader 的 targeted rewrite 每輪不同，
   實測吐出 `NVIDIA current stock price August 15 2026`，而 fixture 只錄了
   `NVDA current stock price today` / `NVIDIA current stock price live quote` → `FixtureMiss`。
   ⚠ **重錄 fixture 解決不了**：只是換一組會再度 miss 的 key。
2. **刻意的大聲失敗被 catch-all 吞掉**（量尺問題，**2026-08-28 已修**）。`_tavily_search` 對
   `FixtureMiss` 是故意 re-raise 的，但確定性 executor 的 `except Exception` 把它接成「降級」，
   連該子問題已建好的池一起丟，且結果檔不記 error → 外觀與「系統沒打 web」**完全無法區分**。
   這是 CLAUDE.md〈web_search 四條規則〉最後一條（診斷成本在觀測性）的第三次應驗：
   `AGENTIC_TRACE=true` 一開就看見了，不開則永遠在猜。

   **修法與一條通則**：把這三個例外（`FixtureMiss`／`RecordError`／`llm_replay.ReplayCacheMiss`）
   移出 `Exception` 階層，改繼承 `BaseException`。判準與 `SystemExit`／`KeyboardInterrupt`
   同一條——**「這不是可以就地處理的錯誤，這是『這次測量無效，停下來』」**。
   → **通則：一個「絕不可被吞掉」的保證，不要寫成契約（呼叫端記得 re-raise），要寫成型別。**
   契約是 O(n) 的：全碼庫 16 個 `except Exception`，漏一個就破功，而且破得靜默。
   驗收：閘門⑦ 9 項，4/4 變異全抓到（改回 `RuntimeError`／把 catch 擴大成 `BaseException`／
   拿掉 re-raise 各自被不同斷言抓到）；空 fixture 跑 web-02 從「產出 0 次 web 的結果檔、exit=0」
   變成「traceback ＋ 印出闖禍的 query ＋ exit=1」。
3. **`realtime_need` 對「近期動態」措辭真的會判錯**（系統缺陷，**同日已改善**）。
   `probe_realtime_need`：「NVIDIA 最近有什麼新進展？」0/3 → **5/5**、「蘋果最近有什麼消息？」1/3 → **5/5**，四題陰性對照一格不動。
   ⚠ **判讀限制**：這支量的是 Grader **單獨**的分類（固定池上呼叫 `_check_sufficiency`），不是端到端。端到端會不會真的打 web 還受 fixture key 那一層影響（見上面第 1 點），兩者不可互相推論。
   ⚠ 而且改善的是**準確度不是結構**：「KB 補不了就去 web」仍由一個三分類 LLM 欄位單點守著。
   → **通則：一個 LLM 分類欄位失手時，先問「是 prompt 沒講清楚，還是架構把太多責任壓在它身上」。**
   這次是前者（prompt 從頭到尾沒說「候選全是財報不構成填 none 的理由」），成本是幾小時；
   若當成後者去拆架構，成本是幾天，而且拆完仍然要回來寫這幾句話。

## 五、多年語料：損害與收益兩半

KB 原本只有**一年**（21 份），所以「答錯期別」結構上幾乎不可能發生——**過去所有評測分數都是在這個保護傘下拿到的**。2026-08-19 補到 **77 份**壓測，2026-08-27 升生產。

**決定的兩半必須都量**：損害探針量到的每一格都是代價，收益要另外一把尺。**升生產的決定不該建立在只有一半的證據上。**

### 5.1 損害：硬 filter 全吸收，沒提期間的題全崩

| intent | Δgold@5 | Δ排擠率 | Δ錯期率 | Δ兄弟密度 |
|---|---|---|---|---|
| **relative**（最新一季） | **±0.000** | +0.009 | **±0.000** | **+5.62**（1.90→7.52） |
| none（問題沒提期間） | −0.120 | **+0.400**（0.080→0.480） | +0.120 | +2.48 |
| explicit（明講年份） | −0.333 | +0.200 | +0.333 | +3.34 |

**① 結論跟直覺相反：競爭密度上升最多的那一類，完全沒有退步。** `relative` 的兄弟密度漲了 4 倍，指標一格都沒動——**metadata 硬 filter 完整吸收了 4 倍競爭**。這是「硬 filter 是唯一提供保證的方法」在本專案上的直接證據。

**② 陽性對照把硬 filter 的價值量化了，而且它隨語料放大：**

| 語料 | relative gold@5（路由開→關） | relative 錯期率（開→關） |
|---|---|---|
| 單年 | 0.857 → 0.809 | 0.000 → 0.048 |
| 多年 | 0.857 → **0.381** | 0.000 → **0.476** |

**同一個開關的價值放大了約 10 倍。** 那條路由在單年是可有可無的優化，KB 一長到兩年就變成不能拔的命脈。⚠ 而它原本的觸發**靠硬編碼詞表**，**漏一題的代價從「差一季」變成「差兩年」**——這就是把它換成 LLM 判斷的理由。

**③ 真正壞掉的是「問題沒提期間」那類**——沒有任何 filter 會觸發，所以沒有東西保護它們。

**④ F1（排擠）遠大於 F2（錯選）：68 個浪費席位 vs 4 題錯期。** 這個比例決定該修哪裡——**病灶是多樣性不是期別選擇**。⚠ **拆開報這兩個指標是必要的**：只看聚合的「gold@5 掉了 0.082」會把兩件事攪在一起，而它們該修的地方不同。

**⑤ 最有說服力的單例，也是文獻沒涵蓋的 failure mode。** `col-02`「微軟是怎麼把 AI 塞進 Office 那些軟體裡的？」——**top-5 有 4 席被 MSFT 三個年度 10-K 的同一節佔滿**。10-K 的 Item 1／1A 年年 80~90% 逐字相同，embedding 與 cross-encoder 兩層都分不出來。
查過的 temporal IR survey **沒有處理「同一份文件跨年份的近重複」**——學界 benchmark 多是新聞／知識圖譜，文件之間本來就不會逐字重複。**這是財報 RAG 特有的，不能指望照抄論文。**
⚠ 順帶推翻一個現成假設：`_suppress_near_duplicates` 的規則一寫著「跨檔絕不比——不同期的相同數字是巧合」。多年語料下 `AAPL_10K_2024` 與 `AAPL_10K_2025` 的同一張表**就是**真正的跨檔近重複。

**⑥ 這個量尺有一塊盲區，別誤讀**：少數題的 filing gold 連候選池都進不去（被 news 硬路由攔掉）。**那是別的缺陷，不是期別干擾**；它只拖低 gold@5，排擠與錯期兩個指標不受污染，且 before/after 同樣被排除 → Δ 仍然有效。**表格上獨立列成「池外」一欄就是為了不讓下一個人誤讀。**

### 5.2 兩個修法與四次自我否決

**最終數字**（45 題共同集，`RAG_REPLAY_CACHE` 全 hit、零 LLM 抽樣噪音）：

| 組態 | gold@5 | 錯期率 | 排擠率 | explicit | relative | none |
|---|---|---|---|---|---|---|
| **單年 `mdna`** | **1.000** | **0.000** | 0.062 | 1.000 | 1.000 | 1.000 |
| 多年 ＋ B | 0.933 | 0.067 | 0.213 | 0.667 | 1.000 | 0.920 |
| **多年 ＋ A ＋ B**（現行） | 0.956 | 0.044 | 0.204 | **1.000** | 1.000 | 0.920 |

- **A（`RQ_PERIOD_INTENT_LLM`，期間意圖交 LLM）**：`explicit` 類 0.667 → **1.000**、錯期率減三分之一。
- **B（`RAG_CROSS_PERIOD_COLLAPSE`，`keep=2`／`prefer=newest`）**：純 Python 後處理、零 LLM、零額外延遲，**在單年上逐題 no-op、在多年上自己生效**。「資料還不需要時不作用、需要時自己生效」才是敢翻預設的理由。
- **殘餘落差全在 `none` 類**（−0.044＝45 題掉 2 題）——**那一類沒有任何 filter 會觸發**。

⚠ **A 與 B 不能分兩次做**：B 的趨勢題保護（`period_ref=range` → 跳過 collapse）要靠 A，多年語料上線而 A 沒開，趨勢題會吃到 collapse 的 −6%，而且當期題會退步（收益探針 control 臂 4/4 → 3/4）。

**四次自我否決（這才是重點——四個都是我提的，四個都錯）：**

1. **`prefer="rank"`（留 rerank 最高那份）——嚴重退步。** 最直覺的寫法，實測 gold@5 **0.837 → 0.653**。原因是 **cross-encoder 對年份無感**，「分數最高」與「對的年份」無關：collapse 把 gold 整個刪掉。**降低排擠卻換來 F2，正是原本要防的東西換個方向發作。**
2. **`prefer="hybrid"`（一席給 rerank 最高、一席給最新）——等於不修。** 為了救「事實只存在於某一季」的事件錨定題而設計的，聽起來比 `newest` 有原則。實測 gold@5 ＝ 不修，還多刪一個 gold；而樸素的「兩個最新」剛好涵蓋那些題。**有原則的設計輸給運氣好的設計，就採用後者並寫下它是運氣。**
3. **`keep=1`——聚合最好，但那是拿趨勢題換的。** gold@5 高於 `keep=2`，但趨勢題期別數 **−38%**，而且**會讓單年 collection 退步**。⚠ 這一格改過：原本還寫了「新增 3 個沉默失效」，逐題人工讀原文後**撤回**——那 3 題全是量尺假陽性。所以 `keep=2` 只剩趨勢題這一條腿，但那條腿是獨立證據，決定不變。
   ⚠ **反過來也不能說 `keep=1` 安全**——這組 gold 裡沒有一題能證偽它，那是測資不足不是它沒問題。
4. **A 的第一版讓 `relative` 類退步 0.095——兩個設計錯，不是 LLM 判錯。**
   - `granularity=None` 時 `ladder_pick` 挑了「所有類型裡最新的」＝年報，把季報 gold 擠掉。舊的詞表路由本質上是**季路由**、只在偵測到年度意圖時讓路——**預設方向被我弄反了**。修法：`granularity` 缺漏一律落到 10-Q。
   - 「這一季…**跟去年同期相比**」LLM 判 `range`，**語意上完全正確**，錯的是我把 `range` 對應到「不注入 filter」。**財報有個領域事實**：單一份 10-Q 本身就含去年同期對照，**根本不需要撈兩份 filing**。修法：prompt 裡明寫這條，歸 `latest`。

**A 為什麼不能併進 `parse_query_filters`**：那個函式前面有 `_FILING_HINT_RE` 詞表閘門，實測**擋掉 21 題 `relative` 裡的 20 題**。那道閘門的正確性論證是「這類 query 的 LLM 本來就只會回空」，而那句話**只對『抽取明確約束』成立**；`period_ref` 問的正是隱含意圖。所以 A 用獨立函式＋獨立 replay kind，**不動任何既有 prompt、不讓任何既有 fixture 失效**。

### 5.3 收益：歷史題探針

〈損害〉量到的每一格都是代價，**沒有任何量尺在量收益**。這是補上的那把尺。

#### 造題階段就被自己的前提檢查擋下兩次

**① 原本舉的例子是錯的。** 「Apple FY2024 的總營收」——**那題單年 KB 本來就答得出來**：10-K 的合併損益表**自帶三年**、MD&A 自帶兩年。所以「去年」「前年」都不在收益區，**真正的收益區從 T-3 才開始**。拿 T-1／T-2 當收益題，會憑空灌出一倍以上的「收益」。

**② gold 不寫死檔名，而是由 `literal` 在 collection 裡確定性定位。** 這樣「gold 是哪幾份」與前提檢查「這個事實在單年 KB 到底在不在」**是同一個操作**，不會各自漂移。它當場擋掉兩個候選題（**兩個 collection 都找不到** → 那不是多年語料的收益，是語料裡根本沒有的東西）。

#### 三臂（historical 18 題 ＋ control 4 題，top-5）

| | 單年 `mdna` | 多年＋A | 多年（A 關） |
|---|---|---|---|
| historical：gold 進 top-5 | 0（**定義使然**） | **17/18** | 17/18 |
| historical：同節別期席位 | **33/90** | 10/90 | 10/90 |
| control：gold 進 top-5 | 4/4 | **4/4** | **3/4** |
| control：同節別期席位 | 0 | 0 | **7** |

**三件事要分開讀**：
1. **收益是語料買到的，不是修法買到的**（historical 那幾列 A 開與關**完全一樣**）。多年語料本身把 0/18 變成 17/18 → **兌現率 0.944**。⚠ 剩下的 0.056 才是這一列的資訊：**語料裡有 ≠ 撈得到**。
2. **單年 KB 對歷史題不是空手**——多數題的 top-5 至少有一席是「同一節、別的年份」。⚠ **這裡原本寫「那是有引用、看起來很有根據的錯答」——那句話已被推翻**（見下一節）：檢索把別年份端上來 **≠** 生成器會拿它充數。這一格是檢索層的**風險**，不是實害。
3. **當期題的損害是 A 擋掉的**（control 三列只在 A 關掉時才動）。這**獨立於損害探針**再一次證實了「別分兩次做」。

#### 兩個 FAIL 的成因**不同**，而且都不是「年份太多」

- **`bh-07`（Microsoft FY2023 營收）——命中比落空更糟。** A 正確解析出 `fiscal_year=2023`、硬 filter 也正確送出去；問題是**它命中了**。`fiscal_year` 的 filter 是與 `report_label_year` 的**雙座標系 OR**，而 `MSFT_10Q_202312` 的 `report_label_year` 正好是 `'2023'`（財年其實是 FY2024 Q2）。於是 Tier 1 命中了一份**標著 2023、卻不含 FY2023 年度數字**的季報，而真正含答案的年報被擋在門外。
  **對照組就在同一份結果檔裡**：問 FY2022 時語料裡**沒有任何** fiscal_year 2022 的 filing → Tier 1 落空 → **Tier 2 一降級，rerank 立刻把三年表排到第 1**。**落空會觸發救援，命中不會。**
  → **絕對年份 filter 隱含一個假設：「那一年的數字住在標著那一年的 filing 裡」。**
  ⚠ **回頭查證的結果比原本的推論嚴重：這不是多年語料的問題，現生產就在發生。** 在單年 collection 上問「Microsoft 在 2025 財年的營收是多少？」→ top-5 **五席全是 `MSFT_10Q_202512`**，含 FY2025 年度數字的年報被擋掉。**這題今天就是錯的**——只是 65 題題庫裡沒有任何一題是這個形狀。
  → **這是「先問是不是量尺錯」的反向版本：量尺沒叫，不代表系統沒壞。**
- **`bh-14`（AWS 2022 年淨銷售額）——實體解析，不是期別。** filter 只抽到 `fiscal_year=2022`、**沒有 ticker**：「AWS」沒有被解析成 AMZN → Tier 3 退回無 filter → top-5 是跨公司污染。**把它跟 `bh-07` 併成一個「多年語料的損害」數字，就會把兩個該修在不同地方的缺陷誤診成同一個。**

#### 這把尺自己的極限（引用上面的數字前要一起講）

- **判別力的來源，historical 與 control 兩列不一樣。** control 有真正的**陽性對照**（A 關掉就退步）。historical **沒有**：A 開關一樣，而單年臂的 0/18 是**定義使然、不是量測**。它不是滿分且兩個 FAIL 各有可查證的成因——那是**間接**證據。
- **這支量的是檢索，不是生成。**

### 5.4 生成端：擔心的那件事沒有發生

**問題**：單年 KB 把 33 席「同一節、別的年份」端到生成器面前，**生成器會不會拿它充數？**

| | before（單年） | after（多年） |
|---|---|---|
| 答對 | **0/18** | **16/18** |
| 承認問到的期間不可得（誠實） | **18/18** | 2/18 |
| **拿別年份硬答且沒交代** | **0** | **0** |
| control 答對 | 4/4 | 4/4 |

**危險態兩臂都是 0。** 單年 KB 面對「Alphabet FY2022 營收」給的是這種東西：

> 我沒有足夠的資訊…根據提供的 10-K，僅列示了 2023、2024 與 2025 年的營收金額（…），未包含 2022 年的營收資料。

**檢索層的風險沒有兌現成生成層的實害**——這是「不要把檢索指標直接讀成答案品質」的一個乾淨反例。

#### 量尺被自己的資料推翻三次，每一次都是「答對了卻被判成危險態」

1. **用 `looks_like_refusal()` 判誠實 → 整片判錯。** 那個函式問的是「整份答案都不作答」，還帶 150 字上限；而這裡最典型的誠實答案是**長的**（它要解釋有哪幾年）。**兩者是不同概念。**
2. **詞表漏英文與兩個中文措辭**（`I don't have enough information…`、「未**披露**」「無法**給出**」）。
3. **`literal` 是英文片語**（在英文語料裡做前提檢查），中文答案永遠不會逐字含它。修法是把兩個職責拆開：`literal` 管前提檢查與 gold 定位，新增 `answer_literals` 管「答案有沒有講出來」。

#### 最重要的副產品：**值不存在 ≠ 事實不存在**

`bh-07`／`bh-16` **在單年 KB 其實答得出來**——`MSFT_10K_2026` 的補充未審計表帶著**重述後**的值，而前提檢查比對的是原始值。10-K 會因改分部結構／會計政策**重述前一年數字**，於是**同一個事實在新年報裡是另一個值**，值比對的前提檢查看不見。

⚠ **抓到它們的不是前提檢查，是生成端這一輪**（單年臂把它們答出來了）→ `check_historical_generation.py` 的 before 臂實際上是**比值比對更強的前提檢查**，**新增收益題之後兩支都要跑**。兩題已標 `void`，檢索層數字同步更正（兌現率 0.900 → **0.944**）。

### 5.5 升生產的驗收：≥2 輪這條規則當場救了一次

| | 單年 r1 | 單年 r2 | 多年 r1 | 多年 r2 |
|---|---|---|---|---|
| `check_number_defects` | 8/0/0 | 8/0/0 | **7/1/0** | **8/0/0** |

多年 r1 那個 FAIL **不是升生產造成的**，三個獨立證據，缺一都還不能下這個結論：
1. **穩定性表顯示它在兩個 collection 上都在跳**（頭條數字 19% / 29% / 18% / 29%），單年自己就給過 19%。
2. **它引的五個 chunk 全部在單年 KB 裡**——「多年語料干擾」這個因果鏈的第一環根本不成立。
3. 這條主張的 `metric_design` 註記**早就記過同一個失效在單年的 r2 上發生過**，`expect_text` 就是為了擋這個而加的。它擋住了。

⚠ **如果只跑 r1 就收工**，這裡會寫成「升生產讓指標從 8/0 掉到 7/1」，然後大概會花半天去追一個不存在的期別干擾。

**新增的舊 filing 是真的有在用**：多年 r1 引用的 217 個 chunk 有 **45 個（20.7%）**來自新增的舊年度 filing，涉及 **23/65 題**。

**一個被誤報的旗標，讀完是量尺不是缺陷**：`mix-10`（gold 22%、答案頭條 2%）。逐字讀完發現多年版的答案**更完整**——多帶了一句歷史對照，**那反過來支持同一個結論**，而 22% 照樣有寫。`2%` 只是被「取頭條百分比」這個啟發式挑中。

### 5.6 期別探針的 gold 人工複審（引用 gold@k 的收益數字前必讀）

**① gold 的指稱沒有被新資料破壞**（唯一全綠的一項）：逐 `(ticker, form)` 比對，14 組全等，append-only 在 gold 層面成立。

**② 46/49 的 gold 就是該 `(ticker, form)` 最新的那一份，而 collapse 的規則正是「留最新」** → `gold@k` 對它**結構上偏袒**。這與「排擠席位與 collapse 規則同定義」是**同一種病的第二層**：第一層在指標定義上，第二層在 gold 分佈上。**引用增益時必須同時講這一句。**

**③ 那 3 題「gold 不是最新」的陰性對照，人工查證後全部無效**（更新的一季有逐字相同的段落／被路由到 news 而任何一臂 gold 都不在 top-k）→ **`keep=1` 造成「3 個沉默失效」這個說法不成立。**

**④ `wrong_period` 這個指標對「定性答案」會假陽性。** 逐題讀原文的四個案例裡兩真兩假：
- **真**：舊季說「2024 年至第二季生產約 844,000 輛」，gold 是「2026 年 860 千輛」——**差 2%、差兩年，抽掉年份人看不出來**。
- **假**：「higher net sales of **Pro models**」在四份 10-Q 逐字都有，定性結論完全相同。

**⑤ 萬用字元 gold 凍結後會「過嚴」，方向與②相反**：`MSFT_10K_2024` 提到 Copilot **35 次**（2026 版只有 17 次），檢索回舊年報不必然答錯，量尺卻記成 miss。凍結仍然是對的（不凍結會變成「撈到哪一年都算命中」），但**這把尺在那幾題上是低估不是高估**。

**兩把想拿來取代人工的聚合尺都失敗了，原因都是老坑**：
- 「gold 句子在舊 filing 逐字重現率」→ **被章節樣板句稀釋**（關鍵句四季重現，重現率卻是全場最低）。
- 「標準答案的數字在不在 gold 檔裡」→ 49 題有 23 題報「對不上」，**全是單位換算**（答案寫 `569.94` 億、filing 寫 `56,994` 百萬）。

### 5.7 Tier 1「命中」不等於「答得了」

承 `bh-07`。**這是這個專案第一個「先在量尺上抓到、再回頭在生產上複現」的缺陷。**

**先量清楚那半個 OR 到底買到什麼**（掃 77 份 filing）：

| | `fiscal_year == report_label_year` | 不相等 |
|---|---|---|
| **10-K** | **21 / 21（全部）** | **0** |
| 10-Q | 41 | 15 |

**10-K 的兩個欄位永遠相等** → 一份 10-K 若被 label-year 那半個 OR 撈到，它必然也被 strict 那半個撈到。所以**那半個 OR 的全部效果，就是額外放行「曆年標籤是 V、財年不是 V」的 10-Q**。

**修法**：`tier1_hit_is_qualified(filters, fused)`——Tier 1 撈到東西之後再問一次「這批東西裡有沒有任何一個的 `fiscal_year` 真的等於問的年份」。沒有 → 當作落空，照常降級 Tier 2。
- ⚠ **`fiscal_year` 為空的點算合格**（News／Fundamentals，`relax_empty_fields` 刻意放行的那條路）。一起判不合格就是誤殺。
- **blast radius 可枚舉**：生產語料上只有兩組 `(ticker, year)`。
- **65 題題庫一題都不受影響**——**這正是它從沒被抓到的原因**，不是它不重要。

**留下的代價**：曆年語意的年份查詢也被趕去 Tier 2。**內容沒變差**，變的是多一句揭露語——而那句話舊措辭是**自相矛盾**的（「沒有 2025 的資料，改用最接近的（…2025）」），因為 `actual` 是從 payload 收的、而那份季報的 `report_label_year` 就是 2025。⚠ **這句同時是使用者可見句與注入 generator 的事實**，說錯比不說更糟。改成講「所詢問**財年**」之後就成立了。
**這個缺陷本來就在，只是修法把更多查詢趕進這條路才被看見。**

⚠ 閘門的判別力在 **⑥b**：⑥a 全餵合成 payload，**哪天 ingest 讓 10-K 的兩個欄位也分歧，⑥a 照樣全綠而整個推理前提會崩**——⑥b 掃真實 payload 鎖住「10-K 恆等」與「至少一份 10-Q 不等」（後者少了它，⑥a 全綠只是套套邏輯，因為沒有作用對象）。

## 六、KB 拔除新聞

**（看到 news 類題目或分數變動前必讀。）**

### 為什麼：新聞與這個系統的正確性判準正交

|  | 記錄（filing／Fundamentals） | 流（news） |
|---|---|---|
| 權威性 | 法定揭露 | 聚合站與評論 |
| 時間標籤 | `fiscal_year`＋`fiscal_period` | **payload 覆蓋率 0%** |
| 正確性判準 | 期別對＋有引用＋數字可驗 | 夠新＋來源可信 |

這個專案為期別正確性做的每一層（切塊六層、期別階梯、跨期 collapse、期間意圖、citation validator、`check_number_defects`）**對新聞沒有一項成立**。

**資料實況（拔除前實測）**：24 檔／98 chunks ＝ 生產 collection 的 **2.5%**；日期停在 2026-07-21；分佈極不均（AAPL 7 則 vs AMZN／META 各 1 則）；4 檔是影片逐字稿。
**最尖銳的一項**：28 條來源標記有 **17 條（61%）**來自本專案自己的 `WEB_ALLOWED_DOMAINS` 會拒絕的站。**你已經定義過「什麼算有編輯流程的財經新聞」，而 ingest 進 KB 的新聞六成不合自己的標準。**

**代價與收益**：新聞佔 2.5% 語料，卻是拔除前**最大的殘留檢索失敗**——`looks_like_news_query`（20 個詞的硬編碼詞表）把複合題硬路由到 `doc_type=news`，filing gold 連候選池都進不去。拔除後實測某題 top-5 從「5 個 news chunk、gold 不在池裡」變成 filing gold 排名 1、2。

### 量尺的三個變動——**跨 2026-08-19 的分數一律不可直接比**

**① 題庫 100 → 63 → 65。** ⚠ **冷凍不是刪除**：那 37 題是日後驗收「live web 能不能取代 KB 新聞」唯一的現成題庫。**現在不要拿它跑分**——eval 預設 web 是關的，跑了必然全滅，那不是證據。

**② `check_number_defects` 6 → 4 → 7 條。** ⚠ **拆分當天掉到 4 條那不是改善是組成變動**——搬走的兩條一 PASS 一 FAIL。

**③ `verify_answer_validators` 閘門④ 一度 FAIL 3 項。** `_news_freshness_gaps` 的 cutoff 讀真實 KB coverage，KB 沒新聞就算不出缺口 → 三條陽性斷言測不出東西。**那是量尺失去判別力，不是機制壞掉。** 修法是讓閘門**自帶合成 coverage**，而不是把斷言刪掉——現在它守的是「新聞若復活，警語必須立刻正確」，且不再與 KB 當下內容耦合，**比原本更好**。

### 三個機制因此永久閒置（刻意保留，不刪）

`find_authority_conflicts`（R3 財報優先，`src_types == ["news"]` 這個桶永遠是空的）／`_news_freshness_gaps`（恆回空）／`rq.looks_like_news_query`（不再接在任何生產路徑上，只剩診斷探針拿它當分類標籤）。**閒置是對的，不是退化。**

### 後續：時效警語一度整個死掉

拔除新聞時把 `_news_freshness_gaps` 標成「閒置但保留」，**低估了後果**：缺口的舊判準是「用了 KB 新聞、而那則新聞過期」，KB 沒有新聞 → **判準沒有指涉對象 → 警語永遠不印**。但風險沒有消失，只是換了位置（即時題 → 打 web → 預算用完 → 回頭用財報生成 → **零揭露**）。

> **教訓：拔掉一個資料來源時，要檢查的不只是「誰會壞」，還有「誰的判準會失去指涉對象」。後者不會拋錯、不會 FAIL，只會安靜地永遠回空。**

### 量尺補回兩條，以及一次「只跑一輪就下結論」的自我打臉

補法是把搬走的兩題**去掉新聞子句**、只留財報半（`lex-16`／`lex-17`），讓「新聞子句」成為唯一變因。

**先講結論：拿掉新聞子句沒有修好它。**

| run | `MSFT_Fundamentals#0` 進池？ | 答案 |
|---|---|---|
| r1 | ✅ | 18.30%，標明 TTM |
| r2 | ❌ 撈到 `#1` | 18%（＝10-K 財年） |

**真正的教訓：我只看了 r1 就宣告根因被推翻。** 第一輪全 PASS 之後，我寫下了「根因是新聞污染」並且**已經改進了 BACKLOG、CHANGELOG 與本檔**。r2 跑完立刻推翻。
- **這條管線本來就不是確定性的**，而這個缺陷的觸發**恰恰取決於子問題長什麼樣**。
- **它自己的記載早就寫過這件事**（「部分取決於 Plan 產生的子問題」）。**我讀到了那句話，卻仍然用 1 個 run 下結論。**
- **「只跑一輪」的危險是不對稱的**：跑出 FAIL 只會讓人多查一次，**跑出 PASS 會讓人宣告修好、還會順手把舊記載改掉**——錯誤結論會被寫進文件，比沒查更糟。

**真的被拔除新聞修好的是 `mix-07`**（2/2 從 FAIL 翻成 PASS，`I don't have enough information` → 答出 $29.5B）。**這一題才是拔除新聞的直接收益**，且是零噪音量到的。

## 七、live web 能不能取代 KB 新聞

### 先把問題拆開：兩個子問題的成本差一個數量級

| | 問什麼 | 成本 | 量尺 |
|---|---|---|---|
| ① | 這題**會不會**被送去 web | 只燒 LLM | `probe_news_web_routing.py` |
| ② | web 拿回來的東西**夠不夠** | 連網、燒 Tavily | `record_web_fixture.py` ＋ `check_web_claims.py` |

**① 是 ② 的必要條件**：一題若根本不會觸發 web，錄再多 fixture 也救不了它。原本的計畫是直接去錄 37 題的 fixture，那等於**在不知道有幾題走不到 web 的情況下先付錢**。

**零網路的作法**：把 `_tavily_search` 換成計數樁（回空字串），其餘管線**原封不動**。⚠ 不要另外抄一份判斷式——抄寫版本會漂移。⚠ 樁回空字串 ＝ 模擬「web 有打、但什麼都沒撈到」，所以這一步**只量路由、不量答案品質**。

### ① 路由：不是瓶頸

| 臂 | 類別 | 觸發 web |
|---|---|---|
| news_set | news | 13/15 |
| news_set | **multi_intent** | **15/15** |
| news_set | colloquial ／ multi_hop | 2/2 ／ 5/5 |
| control(strict) | lexical／semantic／mixed | **0/6** |

`multi_intent` 那一格最值得看：那是「財報半 ＋ 新聞半」的複合題，**最危險的失敗形狀是財報半讓 Grader 判「夠了」而整題不打 web**。實測沒有發生。
兩題沒觸發，查完都不是路由壞掉（KB 真的寫了那件事／Grader 被 KB 內容滿足＝**「證據後置」設計在運作**）。⚠ 但**它不穩定**：同一題重跑一次就變成 web×1，所以「2 題不叫 web」是**單輪觀察不是穩定行為**。

**陰性對照踩到的坑**：第一版把「NVIDIA 現在值多少錢」放進 strict 對照，它打了 3 次 web 被記成「浪費」。**錯的是對照不是系統**——市值在 KB 裡是兩個月前的快照，而另一支腳本對同型問題的斷言正是「必須打 web ≥1 次」。
→ **同一件事在兩支腳本裡有相反的期望 ＝ 量尺自相矛盾，那比任何一邊判錯都糟。** 修法是把對照分兩級：`CONTROL_STRICT`（期別明確指定，斷言必須 0 次）／`CONTROL_LOOSE`（「最近一年／TTM」措辭，**只觀察不斷言**）。

**一個不可以拿來下結論的數字**：57% 打滿了 web 預算——**那是樁造成的**（回空字串 → Grader 永遠不滿意 → 繼續改寫再打）。它唯一能誠實支撐的結論是 **② 的成本上界**。

### ② 內容：可信，但發現一個 live 專屬的引用缺陷

**驗收標準為什麼不是「對照新聞 gold」**：那 37 題的 gold 是「2026 年 6 月的新聞說了什麼」，live web 回答「現在的網路說什麼」——**這是兩個不同的問題**。拿 web 答案去對新聞 gold 打分會系統性低估，而**低分的原因與 web 好不好無關**。所以改用性質斷言（零噪音、與時點無關）。

**結果：PASS 35／FAIL 5／N-A 0**

| 量到的性質 | 數字 |
|---|---|
| 觸發 web | 35/37（與 ① 完全一致） |
| 答案引用了 web | 33/37 |
| 引用主機全在白名單 | **是**，11 個網域 |
| 地區子網域（`ca.`／`hk.`…） | **0 次** ← `_host_allowed` 的本地複核有效 |
| 陰性對照打 web | **0/3** |

**5 個 FAIL 全是同一個 live 專屬缺陷**（`Reference N, chunk #M` 指向不存在的東西），修法與三向變異測試見 [`AGENTIC.md`](AGENTIC.md) A7。

⚠ **修法生效與「這次剛好沒發生」要分開講**：5 題裡只有 2 題的模型仍吐出序號引用（兩題都被完整還原），**另外 3 題這一輪根本沒吐**——它們的 PASS **不能算在修法頭上**。先前那個 `PASS 40／FAIL 0` 是在「修法 ＋ 重新生成」兩個變因同時動的情況下拿到的，**單看它證明不了任何事**。

**兩題「打了 web 卻沒引用」——記成觀察，刻意不斷言**：web 有沒有撈到可用內容**不在系統控制內**，斷言它等於把外部世界寫進量尺。

**為什麼這批不能用 `numbers_must_be_in_fixture`**（最容易被下次的自己重踩的一格）：那條斷言是最強的一條（測幻覺），但**這批題天生是混合的**（財報半＋新聞半），答案裡 KB 數字與 web 數字並存。實測某題的 20 個「三位數兩位小數」有 7 個不在 fixture——**逐一讀完全部是 Fundamentals 的市值／TTM 營收，一個幻覺都沒有**。→ **沒有任何字面樣式能把兩種來源分開**，硬套只會製造假 FAIL。

### 對「要不要把新聞放回 KB」這個決定的意義

路由不是瓶頸（35/37）、來源合規（白名單 100%、地區子網域 0）、時效有揭露。**唯一擋在前面的是引用可追溯性，而那是本地程式的缺陷、不是 web 的缺陷**——它在 snapshot 路徑上不存在，也不會因為把新聞放回 KB 而改善。
→ **沒有任何一項證據支持「把新聞加回 ingest」。**

## 八、分類別抵銷效應：單發 vs agentic

**（看到「整體無顯著差異」之前必讀。）結論：`context_recall` 整體只差 +0.055（噪音內），但那是 multi_hop +0.267、multi_intent +0.184 的大幅領先，被 lexical −0.078、semantic −0.073 的退步抵銷掉的結果。只看整體會得到「agentic 沒用」這個錯誤結論。**

**整體六指標**（同 collection、同題庫、web 全關）：

| metric | 單發 | agentic | 差值 | 判定（噪音 0.067） |
|---|---|---|---|---|
| context_recall | 0.711 | 0.767 | +0.055 | 噪音內 |
| context_precision | 0.772 | 0.835 | +0.063 | 噪音內 |
| nv_context_relevance | 0.860 | **0.963** | **+0.103** | **超過噪音** |
| faithfulness | 0.838 | 0.794 | −0.044 | 噪音內 |
| answer_relevancy | 0.678 | **0.822** | **+0.144** | **超過噪音** |
| answer_correctness | 0.616 | 0.658 | +0.042 | 噪音內 |

**agentic 贏在檢索相關性，但最終答案正確性 +0.042 過不了門檻——不能宣稱 agentic 讓答案更正確。**

**`context_recall` 攤開到類別**：multi_hop **+0.267**／multi_intent **+0.184**／colloquial +0.142／mixed +0.032／news −0.016／semantic **−0.073**／lexical **−0.078**。

**機制解釋**（與架構預期一致，不是事後編的）：agentic 把問題拆成子問題各自檢索。**需要多份不同證據的題拿到好處**；**單一精確詞查找的題被拆解引入雜訊**——lexical 單發已經有 0.911，本來就沒有讓 agentic 發揮的空間。

### ⚠ 三條判讀限制

1. **分類別的數字個別不顯著。** n=10~15 對應的門檻約 **0.17~0.21**。除了 multi_hop 勉強夠看，其餘**個別都在解析度以下**。有證據力的是「兩個指標下 multi_hop／multi_intent 都排前二、lexical 都墊底」這個**跨指標一致的模式**，不是任何單一數字。
2. **這不是控制變因的 A/B**：agentic 天生檢索多個子問題 → contexts 更多，**機械性地有利於 recall／relevance 類指標**。（另一個變因「檢索側模型不同」已被排除，見下節。）
3. **量尺在 agentic 這一側也飽和了**（`nv_context_relevance` 0.963 幾乎等於 gold 上限 0.965）。

**同型的早期觀察**：agentic 平均只收 3.31 chunk / 6.6k 字（單發 4.94 / 10.7k）→ **`context_precision` 的漲幅有一部分是機械性的**（收得少必然精準），別當純品質提升讀。

**faithfulness −0.068 查證為量尺偏誤，非幻覺**：逐題查證發現全是判官誤判或拒答退化，剔除後差值落在噪音內。三個機制：
- **拒答紅利**：單管線寫「reference materials do not provide…」只剩 1 個聲明 → **1.000**；agentic 兩跳都答對 → **0.333**。
- **雙寫稀釋**：agentic 寫 472 個數字 vs 單管線 302；**判官逐聲明查字面支持，算術正確的換算形字面不在來源 → 判 unsupported**。
- 長度中介假說**被推翻**（單管線短答 .910 > 長答 .811）。

**真錯誤只有 2 個，且都不是算術**（推翻「LLM 減法弱、該給 calculator」的直覺）：一題把「六個月累計」欄當單季（**減法除法全對，錯在運算元的期間欄**）；一題把單一部門當全公司（**運算元全在它自己的答案裡、全正確，只是選錯要報哪個**）。
→ **calculator/code-interpreter 對兩題都零效果**：前者會忠實回傳同樣的錯誤答案，後者根本沒觸發運算（它以為在引述）。**病灶在算術之前的「範圍/期間」選擇。**

## 九、檢索側 LLM 換模型

**（要換 query 前處理模型前必讀。）**

**為什麼這件事可以零噪音量**：檢索堆疊本身**沒有 LLM**（BGE-M3 → Qdrant → RRF → cross-encoder）。檢索側模型只驅動 query understanding，其中兩項輸出是結構化的 → 可逐題機械比對。

| | 120b#0 | 120b#1 | 20b#0 |
|---|---|---|---|
| gold recall@5 | 0.8479 | 0.8465 | **0.8459** |
| 完全撈不到 gold 的題 | col-07, lex-03, lex-07, lex-14 | 同左 | **同左** |
| 平均單次耗時 | **1.76s** | — | **3.57s** |

| 配對 | chunk 集合相同 | 平均 Jaccard |
|---|---|---|
| 120b#0 vs 120b#1（**噪音底線**） | 85/100 | 0.9476 |
| 120b#0 vs 20b#0（訊號） | 72/100 | 0.8971 |

**判讀**：候選池**確實**被換掉了（0.897 < 0.947，超過噪音），但**換掉的全是無關 chunk**——gold recall 差 0.0020，而同模型跑兩次的差是 0.0014，同一量級。**結論：檢索側兩個模型等價。**

**但方向是反的**：20b 在 NIM 上**慢一倍**。原本寫「用小模型求快」——**前提是假的**。該做的不是把單發降 20b，而是把 agentic 升 120b（同品質、快一倍）。

### 三個方法論教訓

- **字串比對對「翻譯」這種輸出沒有判別力。** 原本設計「逐題比 `translate_en` 字串」——實測 86/100 不同，但其中 **68 題是同一個模型自己跑兩次就不一樣**。噪音吃掉全部訊號。**唯一有意義的判準是「送進真實檢索器後結果有沒有變」。**
- **量任何「換模型」之前先確認那個模型真的被呼叫。** `parse_query_filters` 有 91/100 題被 `_FILING_HINT_RE` 效率 gate 擋在 LLM 之前 → 這個參數實際只影響 9 題。不先算這個，會把「gate 擋掉所以相同」誤讀成「兩個模型一樣好」。
- **A/B 兩臂的 LLM 輸出要先錄下來再釘死**，噪音底線用「同模型的第二次跑」而不是憑感覺設閾值。

## 十、操作備忘

**標準跑法**（三步；reference 只需生成一次可重用）
```bash
# ① 生成 ground truth（已存在就不必再跑；--force 不帶 --ids 會洗掉人工校正）
.venv/Scripts/python.exe eval/gen_reference_answers.py

# ② 產生結果檔：agentic 版
.venv/Scripts/python.exe eval/run_agentic_on_evalset.py --module agentic_rag_v2 \
    --freshness-mode snapshot --output experiments/agentic/<名稱>.json
#    單管線版
.venv/Scripts/python.exe eval/eval_generation_llm_judge.py --output experiments/<名稱>.json

# ③ 切 .venv-ragas 算六指標
.venv-ragas/Scripts/python.exe eval/eval_ragas_vs_rubric.py \
    --from-results experiments/agentic/<名稱>.json \
    --reference-file eval/reference_answers.json --output experiments/agentic/ragas_<名稱>.json
```

- **只改動少數題的 reference 時不必重跑全部 RAGAS**：RAGAS 每題獨立評分，用 `--ids <題號…>` 只評改動題再拼接回原結果。全部重跑只是多疊一層 judge 噪音。
- ⚠ **部分腳本的 `--output` 預設值仍指向 `eval/`**，跑的時候要自己帶 `--output experiments/...`。
- **新機器還原評測環境**：`python -m venv .venv-ragas` → `pip install -r requirements-ragas.txt`。兩個環境為何不能合併見 [`../README.md`](../README.md) §4-1。
- ⚠ **`answer_correctness` 偏低常是量尺問題**（長度對齊／false-negative gold），不是系統答錯——下結論前先讀本檔第三、四節。

### 反覆出現的方法論教訓（一句話版）

繞過 brain 測 ≠ 真實 graph／先排除工具環境毛病再懷疑系統／單次 LLM-judge 不能論因果、要確定性消融／別過度外推（file-level 無效 ≠ chunk-level 無效）／**prompt 是機率不是保證，grounding 與 citation 要靠 Python 強制、不靠拜託模型**／**提實驗之前先 `ls experiments/`——能證偽假設的測試可能已經跑過了**。
