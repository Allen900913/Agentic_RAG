# Agentic 管線知識庫

> **這裡放什麼**：agentic 各節點為什麼長這樣、validator 的設計與實測、哪些「更 agentic」的做法是負資產。
> **這裡不放什麼**：日期式變更記錄（→ [`../CHANGELOG.md`](../CHANGELOG.md)）、切塊層（→ [`INGEST.md`](INGEST.md)）、量測（→ [`EVAL.md`](EVAL.md)）、逐條斷言（→ 各閘門腳本自己的 docstring）。

## A1 架構主線：agency 只給需要決策的角色

**貫穿哲學**：**只有需要決策的角色才給 agency；不需要決策的角色給 agency 就是給它犯錯空間。**

**價值在確定性 planner 拆解，不是自由迴圈。** 三階診斷，每一階都推翻前一階：① 檔案層 gold 覆蓋 → agentic 檢索**不弱反大勝**（28/38 vs 單管線 12/38）→ 推翻「多源檢索弱」② claim/chunk 層 gold → 真實 v2 只 16/75、**乾淨 decomposition（無 ReAct executor）拿 35/75**、單管線 25/75 ③ 修法＝**v2 minus ReAct**（plan → 每子問題直接 retrieve → commit）＝現況。
**煙槍在 ② 那一格**：漏水點是 ReAct 執行層亂改 query＋亂搜，**不是** planner 拆解、**不是** doc-type filter。
⚠ **這條結論限於本語料**（結構化 `.txt` ＋ 長文 filing、中型模型）。agentic 真正的舞台是多跳／開放 web／真路由工具。

**為什麼 Grader（證據後置）不能上移到 Planner**：Planner 手上只有 coverage 摘要、**沒有真實 chunk**，只能用猜的；而猜錯的代價**不對稱**（猜「KB 沒有」但其實有 → 整題答不出來）。所以架構刻意把「夠不夠」延後到 Grader 看見真實候選之後。

## A2 檢索層的共用決定

（實作在 `rag_query.py`，兩條管線共用。）

- **`full_translate_en`**：中文問中文答，但召回 ＋ rerank 一律用英文譯句，消除 cross-lingual reranker 對「中文 query × 英文 chunk」評分平坦的問題。agentic **固定開**；生產 `rag_query.py` 預設仍 False（跟進與否未決）。
- **`period_basis` TTM 口徑消歧義**：Fundamentals `.txt` 已含算好的 TTM 比率 ＝ **路由問題非算術**。每 chunk 加 `period_basis` payload，命中 TTM 詞 → **單向**硬 filter（開雙向前要先跑全量 eval）。
- **`_ensure_ticker_coverage`／`_ensure_ratio_source_coverage`**：確定性保底，**只加不減、零 LLM**。**用程式碼保底而非改 Grader prompt／換大模型**——規則可用 metadata 確定檢查的，不交給機率元件每次重推。
  ⚠ **掃池的保底救不了「`#0` 連候選名單都沒進」**：生產是英譯 query，實測 `MSFT_Fundamentals #0` 連 RRF 候選都沒進。所以現在是**確定性補撈**（直接查 Qdrant），不是掃池。⇒ **`sources ⊆ retrieved_union` 不是不變量**。
- **Planner 的比率期間中性**：修 Plan 把「目前毛利率」釘成「FY2026 Q2 毛利率」→ 帶季度的 query 把 TTM/Fundamentals 整個濾出池。⚠ **這條 scoping 刻意收窄在「有實測失效」的邊界**：同型的估值比率（P/E、ROE）實測 Planner 本來就中性 → **別為不存在的 bug 加規則**。

## A3 一致性 validator：LLM 抽取 ＋ Python 判斷

**分界線**：「確定性 > 勸 LLM」講的是**不要把判斷交給 LLM**，不是不要用 LLM 做抽取。**抽取是感知任務（LLM 強），比對是邏輯任務（Python 可靠）。**

**結構**：`_extract_claims`（CHECKER_MODEL，temp=0）把答案每個數值宣稱抽成 `value/unit/metric/entity/scope/period_key/kind/basis/quote` → `find_claim_conflicts` 跑零 LLM 規則。

**為什麼 regex 版被整段刪掉**：① 它在用字串比對做感知（指標／主體／並陳措辭全靠寫死詞表），且已被實測抓包（`col-11` 漏抓，因為「另一份報告則顯示」不在清單裡）② **它從來沒跑過**——觸發條件是「LLM 抽取失敗」，200 份答案的失敗率是 **0**。

**第一版規則太天真，量測直接打臉**（觸發 8 題只有 ~2 個站得住）。誤報全是抽取器的**系統性樣態**，**修在規則層而不是回去勸抽取器**（抽取本身沒錯，錯的是我拿 level 去比）：

| 排除規則 | 理由 |
|---|---|
| ⓐ `level` 不參與比對（只比 change／growth_pct） | 「從 X 增至 Y」抽出的兩個 level 幾乎都被填同一個 period |
| ⓑ `basis` 進分組 key | YoY 92% vs QoQ 21%、reported vs 固定匯率是**合法並列** |
| ⓒ 共用同一段 quote 者不比 | 區間「EPS 增加 1 至 3 美元」被拆成兩筆 |
| ⓓ 百分比加總 ≈100 → 佔比不是矛盾 | Reality Labs 支出 70%/30% |
| ⓔ 同格出現 ≥3 個相異值 → 列舉不是矛盾 | `Regional data (+29%, +39%, +40%)` |

**最終量測（200 份存檔答案）**：LLM 版 **4/4 精準**，且 `col-11` 是 LLM 版獨有的真陽性。

**「怎麼知道兩個數字在講同一件事」——它不知道，只是無法證明不同。** 真正扛住正確率的是 **`_ALSO_MARK`**：它抓的不是語意判斷，而是**生成器自己宣告**「這是同一個指標的另一種說法」。**把不可解的共指問題換成可讀的表面標記。**
- entity 比較改成**對稱**（兩邊皆空也排除）；period 比較**維持非對稱**（改對稱就漏抓 `mix-06`）。

**In-Place Healing 提案：定位可行、裁決無解。**
① **定位可行且不需要 NER**——`_extract_claims` 已回傳 `quote`，591 條實測逐字命中 34.3%、**正規化空白/全形後 85.1%**，比對不上就 fallback（可偵測）。
② **裁決：提案沒有處理，而病灶正好落在這裡。** `col-11` 的四組衝突**兩邊都是對的**（19% 是單季、18% 是前九個月）——打穿操作集 `{抽換, 抹除, 標記}`：抽換沒東西可換、抹除會刪掉正確資訊、標記等於承認不確定。真正缺的是**期間限定詞**，那要**插入**文字且要回讀原文。
③ **真正的發現在 ingest 層**：那兩個 chunk 沒有期間標頭，是切塊時切掉的（見 [`INGEST.md`](INGEST.md) ②）。

→ **判準不是「Python 用得多不多」，是該子任務有沒有唯一正確答案**：抽取＝LLM；比對／定位＝Python；**裁決＝要回讀原文＝LLM，而這層現在不存在**。Python 沒有太多，是少了一層。
**成本**：每份答案固定多一次 CHECKER_MODEL 呼叫（中位 5.1s）。

## A4 期間接地：讓 validator 看得到原文

`_extract_claims` 原本的 user content 只有 `f"答案:\n{answer}"`——**它看不到任何 chunk，所以無法糾正答案的錯，只能忠實複製**。

**受控實驗**（答案文字固定，只換餵進去的原文）：

| 組別 | 誤報組數（3 輪） |
|---|---|
| ① 不餵原文 | 1 / 0 / 1 |
| ② 餵**無**期間標籤的原文 | 2 / 1 / 2 ← **比不餵更糟** |
| ③ 餵**有**標籤的原文 | 0 / 0 / 0 |
| ④ ③ 的同一批 chunks、程式剝掉注入標籤 | 2 / 1 / 0 |

③ vs ④ 是**乾淨對照**——同一批 chunks，唯一差別是那行 `[Three Months Ended…]` 在不在。**效果來自標籤，不是檢索變好。兩層缺一不可，且 ingest 必須先做。**

**中途走錯一次，記下來**：加了「舉證稽核」（填不出原文出處就把期間降級成 `unknown`），誤報從 3/6 降到 0/8 看起來成功，但補跑真衝突偵測是 **0/5**——**捏造的數字必然在原文查不到 → 必然降級 → 永遠抓不到幻覺。誤報歸零是因為整層被關掉了。**
→ **正確順序是「先偵測、再用原文駁回」，不是「先降級、再偵測」。**

**收斂版**：期間定位改用**零 LLM 字串比對**（`_ground_period_from_source`）——實測讓 LLM 自己查證，8 輪只有 4 輪真的去查。改成 Python 後誤報 5/5 全對、真衝突 5/5 全中、十輪零變異。
**`period_key` 取代自由文字 `period` 當同格判準**：同一個「截至 3/31 的九個月」被 LLM 寫成過四種代碼，而 `2026Q3` 還同時被拿去指單季與累計。`period_months`/`period_end` 直接讀原文標題就有，**不需要換算成財年季度代碼，而換算正是出錯的那一步**。
**限制**：只處理百分比（金額寫法太多，誤配風險高過收益）；擋不掉「查了但查錯」。

## A5 live／web 這條路：四個阻塞點與 eval 隔離的真正來源

**起點**：生產模式問四題時效題，web_search **0/4 觸發**。逐層拆下去發現不是一個 bug，是四個獨立阻塞點疊在一起。

**① 詞表閘門（已整段移除）**：`looks_like_news_query` 與 `_RELATIVE_TIME_RE` 都是硬編碼詞表，實測 18 個真實時效措辭**漏 10 個**（最諷刺的是「**即時**市值」打不到 web）。**漏網的代價不是答不出來，是自信地把舊資料當即時**：「特斯拉**今天**股價下跌 2.96%」來自三週前的新聞檔、「截至目前的即時市值 $4342.02B」來自兩個月前的 Fundamentals，三個都零時點揭露。
⚠ 這件事漂移過：第一次只從 web 觸發拿掉那兩道，**時效警語那道漏改**，而文件已寫成「全數移除」。**宣稱「全數移除」前跑一次 `grep`。**

**② 生成契約禁止引用 web（這是 binding 的那個）**：`rq.SYSTEM_PROMPT` Rule 1「Answer ONLY based on the provided reference materials」＋ Rule 8「Every number you state must be traceable to a cited chunk」。**決定性證據**：接好管線後三次跑分**仍全數退回舊快照的市值**，其中一次寧可拿舊市值除以股數**捏造**「每股 $204」——**違反 Rule 8 前半句「Never invent」，只為守住後半句**。**缺的從來不是格式，是許可**，而且**修法必須在 system message**（user message 版本已實測無效）。
⚠ 順帶：`_build_temporal_contract` 掛在 Planner／Replanner／Researcher 上，唯獨 `_write_final_answer` 漏接——不是「LLM 沒有時鐘」，是**系統造好了契約卻少接一個呼叫點**。

**③ Grader 不看時效**：`_CHECKER_PROMPT` 的「KB 時間天花板」條款（防無限空轉）讓 coverage 把 Grader 推向判「夠」。**修法刻意不改那段 prompt**，改在 Python 層做時效改判：「這題需要多新」給 LLM（`realtime_need` 三態），「來源多舊」給 Python。改判**只降不升**（只把 true 改 false）。

**④「永不過期」被誤用成「能證明夠新」**：`_source_newest_date` 把 10-K 的 4 碼財年戳算成該年 12/31 → `MSFT_10K_2026` → **2026-12-31（未來）**，而 `_stale_for_realtime` 取全池 `max(dates)`。**於是財報不只是棄權，它替整個候選池背書說「夠新」**（實測 6 個即時問題有 4 個改判不會觸發，含 intraday 股價題）。
**修法**：`_is_freshness_evidence(source)`——**只有 8 碼真實日曆日期算證據**；4/6 碼戳**不算證據也不算過期**。`_kb_ceiling_date` 必須套用**同一套資格判準**。
⚠ **這推翻了一個先前刻意的成本判斷，因為算式反轉了**：舊註解「誤判新鮮只是維持現狀」在 KB 有新聞時成立；KB 只剩財報之後，「維持現狀」＝**拿 10-K 回答今天股價**。
⚠ 兩個真實代價：① `kb_unfixable` 恆 False → 白燒 `MAX_REWRITES` 輪 ② **第二道防線被靜默關閉**。但**不等於 web 不會被叫**（主防線是 Grader 自己判 `sufficient=False`）——**確認缺陷時要問「這個失效傳得到端到端嗎」**。

**eval 隔離的真正來源（別再誤認）**：三道詞表閘門**都不是隔離機制**。隔離只靠 `freshness_mode == LIVE` 與 `ENABLE_WEB_SEARCH` 兩個獨立條件（`not verdict["sufficient"]` 是**生產端擋濫用**，不是隔離）。更根本的是：**eval 裡沒有任何一題需要 KB 以外的資料**——web 在 eval 中不是被擋掉造成損失，而是**根本用不上**。常駐證明是 [`../eval/verify_web_gate_isolation.py`](../eval/verify_web_gate_isolation.py)，其中**兩項是 byte-identical 斷言**（無 web 時 system message 逐字不變）＝**eval 基準不被動到的證明**。

**來源白名單**：`WEB_ALLOWED_DOMAINS` 分兩類（原始揭露方與有編輯流程的財經媒體），不收論壇與意見文。**濾空時明確回報查無、不退回全網**。⚠ 這是**授權清單**不是感知詞表，與「硬編碼詞表是警訊」不衝突。

⚠ **n=1 測不出這條路的任何東西**：八題各跑一次的回歸裡兩題看起來明顯退步，各補跑 2 次後**兩個都被推翻**。答案品質的 run-to-run 變異大於單次測試的解析度，而 web 又多疊一層隨機性。

## A6 web 檢索層的九個缺陷：主因是自己截掉摘要

**主因：`content[:300]`。** trace 印出的摘要是 `Apple market cap as of Augus`，完整原文是 `as of August 07, 2026 is $4572.79B`。Tavily 的 `content` 實測 596~1982 字，而**數據頁的數字排在站台樣板文字之後**。**300 字正好切在數字前一個字。資料一直都在。**
⚠ **可觀測性教訓比修法本身重要**：「Tavily 沒撈到」與「撈到了但被自己截掉」在只印 `→ 2163 chars` 的舊 trace 裡**長得一模一樣**。同一課後來又上了一次（只印域名不印網址，看不出 Reuters 的日期為何抽不到——日期在網址結尾）。

**Tavily 的能力邊界（決定架構的那組實測）**

| 模式 | `published_date` | 日期過濾 | 數據頁 |
|---|---|---|---|
| 預設／`topic="finance"` | 無 | 無 | **有**（macrotrends／stockanalysis／companiesmarketcap） |
| `topic="news"` ＋ `days=N` | **有** | **真的生效** | **全消失** |
| `start_date`／`time_range` | 無 | **靜默忽略** | 有 |

即時報價／市值題要的正是數據頁 ⇒ **不能**為了拿日期切到 news 模式。結論：預設 topic ＋ `search_depth="advanced"`，日期靠網址／內容推斷。

**另外五個缺陷**
- **D2 單一域名壟斷**：`companiesmarketcap.com` 用五種幣別變體吃掉全部 5 個名額 → 整次搜尋作廢。修法：先撈 12 則、單域名上限 2。
- **D3 無日期**：抽網址日期、濾明顯過時，並把日期**標進 prompt**。**抽不到日期的一律保留並標「未標示日期」**（數據頁沒有日期，而那正是即時題最需要的）。
- **D5 同頁多變體**：`/amp/`、`new.` 子網域、`http://` 各佔一個名額。
- **D6 地區子網域＝別的市場的報價**：`ca.finance.yahoo.com/quote/TSLA.NE`（加拿大 NEO）。Tavily 的 `include_domains` 是子網域包含式比對 → 收到結果後自己再複核（只認 exact ＋ `www.`）。
- **選擇權合約頁**：`finance.yahoo.com/quote/TSLA260814C00257500` 是買權不是股票。用 OCC 標準格式擋——**格式定義的封閉集合**。⚠ 同類但**未解**的是外國掛牌**路徑**（見 BACKLOG）。

**D4 web 呼叫無上界：計數器放錯層。** 實跑 7 次 web call 而 `WEB_SEARCH_MAX_CALLS = 3`——它記在 `_RunState.web_calls`，而 `_RunState` **每個子問題歸零**。子問題為什麼長到 7 個：時效改判讓子問題**恆為** `sufficient=False`，而 **KB 檢索在物理上不可能修復「KB 太舊」**，於是每輪 replan 都再加一個措辭更強調「請上網」的同義待辦。兩個修法：① `kb_unfixable` 旗標 → 立刻跳出改寫迴圈（21 次檢索降到 4 次）② `QUERY_WEB_BUDGET`（query 級、上鎖、只在 graph 入口歸零）。

**`kb_unfixable` 的誤殺，與「候選池 ≠ KB」**：第一版只看候選池最新那筆，但**池子裡最新是 62 天前，不代表 collection 沒有 3 天前的**。修法靠一個**與 query 無關**的量：`_kb_ceiling_date()` 從 coverage map 取「這些 ticker 在整個 collection 裡最新到哪一天」。

| 候選池最新 | collection 天花板 | 判定 |
|---|---|---|
| 過期 | 也過期 | `kb_unfixable=True` — 再檢索還是同一批檔案 |
| 過期 | **夠新** | `kb_unfixable=False` — 是**這次檢索沒撈到**，保留改寫機會 |
| 夠新 | — | 不改判 |

**天花板與候選池共用同一個日期算法**（不然比出來的大小沒有意義）；**coverage 掃不到時保守當 `True`**。⚠ 判斷邏輯抽成 `_classify_staleness()` 的**唯一理由是可測**：內嵌在 LLM 回傳處理裡的分支，**閘門碰不到就等於從沒被證偽過**。

**被自己推翻的修法：用字串相似度認同義待辦。** 分離度是**負的**——正向（同一需求）最低 jaccard 0.04，負向（不同需求）最高 **0.50**（「蘋果的即時**市值**」vs「蘋果的即時**本益比**」）。**沒有任何門檻能分開這兩類。** 整段撤掉，改成**不判語意、只封成本**。

**兩個追加**：① **修訂條款的排序規則原本是反的**——「以標示日期最新的來源為準」讓 22 天前的報導壓過未標日期的即時行情頁。**對「當下數值」類問題這個偏好是反的**（持續更新的行情頁沒有日期才是今天的值）→ 按問題類型分岔，`WEB_STALE_DAYS["intraday"]` 90 → **7**。② **時效警語與答案自相矛盾**（答案引用了兩個 web 來源，底下卻印「Web 未提供可用補充」）——缺口是**逐待辦**算的而警語**整篇只印一次**。**警語與答案互相矛盾比沒有警語更糟。**

## A7 live web 的可重現評測：把不確定性切開，而不是硬定 gold

**問題**：live web 沒辦法定 gold，所以 A5／A6 那整套機制在 eval 裡**執行次數是 0**，唯一的證據是 n=1 軼事。

| 部分 | 用什麼測 | 為什麼 |
|---|---|---|
| 白名單／去重／單域名上限／日期算術／預算／`kb_unfixable` | `verify_web_gate_isolation.py` | **零 LLM、零網路、秒級**。已經有了，**不重測** |
| Generator 有沒有真的引用 web、衝突時有沒有並陳並標時點 | `web_replay.py` fixture ＋ `check_web_claims.py` | **必須含 LLM**，所以必須固定輸入 |

**為什麼不用 RAGAS**：這條路只有 5 題，MDE 換算約 **0.17~0.21**——任何分數都落在噪音裡。

**四個設計上的坑（每一個都會讓 fixture 失效而不自知）**
1. **錄的層級**：必須錄 `TavilyClient.search()` 的**原始回應**——`_tavily_search()` 的回傳是跑完白名單複核 → 去重 → 上限 → 抽日期 → 過濾 → 截斷之後的成品，**錄在那裡等於把要測的六道一起 mock 掉**。
2. **`get()` 與 `put()` 兩邊都要 deepcopy**（下游會就地寫 `_pub_date`）。`put()` 少 → 落盤 `TypeError` 且 atexit 的例外**不影響 exit code**＝安靜掉一筆；`get()` 少 → **更嚴重**：第二次重放時抽日期那段**根本不執行**，fixture 就不再是固定輸入。
3. **只錄 web 不夠，要連 `llm_replay` 一起錄**（送給 Tavily 的 query 由 LLM 決定，MoE 溫度 0 不固定路由）。
4. **斷言不能寫死成某一次錄製的答案**：錄製時引 stockanalysis 的 `$4.46 兆`、重放時引 yahoo 的 `$4.45 兆`——**兩個都在 fixture 裡、都正確**。**fixture 是一個值空間，不是單一答案。** 斷言只能測「不論它挑哪個都必須成立」的性質，最強的一條是**答案裡每一個報價都必須在 fixture 原始內容裡逐字出現**（零幻覺斷言）。

**驗收與判別力**：兩次獨立取樣都 5/5 PASS，照「全綠先當壞消息查」注入六種變異 → **6/6 全被抓到**（最後一種「只竄改其中一個股價」是加上零幻覺斷言之後才抓得到的）。
⚠ **「斷言零噪音」不等於「結果零噪音」**：產生結果檔的那一步有 LLM 取樣變異。`5/5 PASS` 的正確讀法是「**這一次取樣**沒問題」，要提升信心只能多取樣，**重跑檢查器沒有用**。
⚠ **而且斷言的 FAIL 也可能是量尺錯**：某次 FAIL 說「平均股價 $196.82」是憑空生成——**是誤報**（fixture 表格裡有 `196.8165`，答案正確地四捨五入）。我拿它當真陽性，寫了一整條 BACKLOG、一段 CHANGELOG、一節 docs 才發現。→ **「0 筆問題先當壞消息查」需要一個鏡像條款：稽核回報 FAIL，也要先問「是不是量尺錯」。**

**live 專屬的引用缺陷（37 題驗收時抓到）**：5 題的答案含 `【Reference 7, chunk #15】`——不是檔名、不是網址，**指向不存在的東西**。三件事讓它從「格式瑕疵」變成真缺陷：① **那 5 題的有效 KB 引用是 0**（整份答案沒有任何可追溯的出處，而答案裡有大量財報數字）② **這是 live 專屬的**（snapshot 0/100、live 5/37）③ **validator 有抓到，只是放它過去**（重試上限用完就 `break` 然後原樣 return）。
⚠ 該處的 trace 寫的是「重試耗盡，走機械式收尾」——**當時程式裡沒有任何機械收尾。註解描述了一個不存在的行為，這比沒有註解更糟。**
**修法**：`Reference N` 的編號**是我們自己給的**（`rq.build_user_prompt`），所以 `N → allowed_chunks[N-1]` 是**確定性映射**。**重點是兩個守門條件**：① `N` 超出候選範圍 → 不動 ② 引用裡的 `chunk #M` 與第 N 筆的 `chunk_index` 不一致 → 不動。理由是**失敗方向不對稱**：漏修＝維持現狀，猜錯＝把「無法追溯」變成「**看起來可追溯的錯引用**」。
⚠ 三向變異最危險的一條是 **`Reference 0`**：Python 的 `[-1]` 是合法索引，少了範圍守門它會**安靜地**指到最後一筆，而其他越界值反而會當場炸。**會吵的那種比較安全。**

## A8 期別稽核：答案自稱「最新一季」卻引用了較舊的期別

**一次誤診值得先寫下來**：第一份根因分析每一步都對，結論卻錯（把 coverage 印出來才發現 `MSFT_10K_2026` 的 stamp 是**財年**不是日曆期末，該檔實際涵蓋到 2026-06-30、距 as-of 只有 46 天，**KB 一點都不缺**）。**先把要判斷的東西印出來，再猜成因**——這次「印出來」只花了一次 Qdrant scroll。

**真正的缺陷**：MSFT 最新一季是 Q4 FY2026，它**沒有獨立的 10-Q**（被包進 10-K）。系統把「最新一季」解析成「候選裡最新的那份 **10-Q**」，而不是「該公司在證據集合裡最新的**期別**」。

**三個設計決定**
1. **判準看答案，不看問題。** **答案寫出「最新一季」時，它就是在做一個宣稱**，而「你引的是不是證據裡最新的一期」是純比對。**這是驗證答案自己的宣稱，不是猜使用者意圖** → 誤報風險低，漏判只是維持現狀。（另一個理由：在 Grader prompt 加欄位會動到 snapshot 的 Checker prompt，破壞「eval 基準逐字不變」。）
2. **排序不能用 `_source_newest_date()`**（它把 `TICKER_10K_YYYY` 算成該年 12/31，而各家財年結束月份不同）：`NVDA_10K_2026` vs `NVDA_10Q_202604` 用日期比會判反，用 `(fiscal_year, fiscal_period)` 才對。期別欄位靠**擴充 coverage 掃描的同一次 scroll** 建表，比改全專案共用的 retrieve 投影安全。
3. **每家要比兩輪**：只比「全期別最新」會漏——**修好第一輪之後重生成的答案自己暴露的**（它照指示引了 10-K，卻拿 FY2026 Q2 當「最新單季」而 Q3 就在證據裡）。**「最新一季」問的是最新的「季」。**

**宣稱詞辨識：窮舉清單在同一次迭代內就漏了兩個。** 第一版寫成 `最新一季|最新季度|…` 的窮舉，修正後重生成的答案寫的是「最新**單季**」與「最新公布的**季報**」——**validator 對自己造成的新問題視而不見**。改成「錨詞（最新／最近）＋ 5 字內期別詞，中間不許有數字」。
> **窮舉措辭必漏，而且往往漏在你自己下一輪產生的措辭上。** 詞表能用的前提是「**錨詞 + 結構**」而不是「列舉實例」。

**時效警語同步從「看問法」改成「看結果」**：改成看**這個子問題實際 commit 了誰的 chunk**，零詞表而且更準。
⚠ **後來 KB 拔除新聞，這個判準又整個失去指涉對象**（`_news_freshness_gaps` 恆回空），而風險沒消失只是換了位置（即時題 → 打 web → 預算用完 → 回頭用財報生成 → **零揭露**）。新判準是「**這個子問題需要即時資料卻沒拿到 web**」。
> **教訓：拔掉一個資料來源時，要檢查的不只是「誰會壞」，還有「誰的判準會失去指涉對象」。後者不會拋錯、不會 FAIL，只會安靜地永遠回空。**
⚠ 這一組的**陰性對照是「財報題 → 零缺口」**。少了它，一個「一律產生缺口」的實作也會全綠。

## A9 R4：web ↔ 財報衝突要求「並陳」而不是「裁決」

**缺口**：`find_authority_conflicts`（R3）只看 `chunks` 的 `src_types`，而 live web 走 `web_extra` **字串**、不是 chunk → 只出現在 web 的數字拿到空的 `src_types` → R3／R4 一律跳過。

**為什麼不擴充 R3**（整條的核心判斷）：R3 的動作是「**判新聞那個為錯**」——那對 KB 新聞成立（它在構造上就是舊的），**web 不是這樣**：它可以合法地比任何 filing 都新（盤中報價、8-K 事件、財報已發布但 10-Q 未申報）。宣告「財報永遠對」會讓系統**系統性地報舊數字**。

**R4 的動作**：同一格出現互斥數值、一邊只在 web、另一邊在財報 → 要求答案**兩個都講、各自標出處與時點**。

**為什麼「並陳」在誤報下是安全的**（選這個動作而不是裁決的主要理由）：最大的誤報來源是「同一指標、不同期間」，而誤報時要求模型做的事是「把兩個值連同各自的時點講清楚」——**那對不同期間的兩個值本來就是正確行為**。裁決型規則沒有這個性質：判錯一次就是把對的數字刪掉。⚠ 所以真正會出事的方向不是漏抓，是**話太多**。

**能力上界**：claims 是從**答案**抽的，所以 R4 只看得到「答案自己講了兩個互斥的值」。
**順帶修掉的一個洞**：`_ground_source_type` 原本開頭是 `if not chunks: return`，於是「候選池空、只有 web」——**那正是 live 路徑的常見形狀**——整個跳過 grounding。

## A10 Synthesize 的 validator 疊法與共用守門

生成後依序跑：`_validate_and_fix_citations` → 一致性（R1~R4）→ 期別 → reflect → 數字溯源 → 並陳（R5/R6）。
**順序不是隨意的**：一致性放在 reflect **之前**（讓 reflect 稽核已調和的版本）；期別放在一致性**之後**（期別改對可能連帶換掉數字）；**數字溯源放最後**（它是唯一會看 reflect 重生成結果的檢查）。

**四道守門共用 `rq.looks_like_refusal`**
⚠ 舊版寫成 `answer.startswith("I don't have enough")`——**英文字面、只認開頭**，而 Writer 講中文 → 一份剛說自己沒有依據的答案，還會付**至少兩次 LLM 呼叫**去稽核一個沒有東西可稽核的對象。
⚠ **危險方向不是漏判而是判過頭**：真的有依據的答案被當成拒答 → 四道 validator **一次全部跳過**。`REFUSAL_MAX_CHARS = 150` 就是擋這件事的（**長的誠實答案不算拒答**）。
⚠ 同一個守門寫錯出現過**兩個消費端**（引用尾巴那次只改了尾巴，這四道漏改）→ 閘門⑭a 因此是**逐個 validator 走 AST 驗，不是字串 grep**。

**拒答不得附「📚 引用來源」**：那段尾巴宣稱「Generator 實際依據的 chunk」，印在一份剛說自己沒有依據的答案底下就是**假的宣稱**（實測 4175 份答案／59 份拒答，**21 份帶著引用尾巴出貨**）。
⚠ **但 `looks_like_refusal` 裡的 `strip_evidence_tail` 不能因此拿掉**：`_node_synthesize` 在 collected/web 皆空時走的是另一條路（拒答 ＋ 時效警語），那個 ⚠ 尾巴是**該留的**（「答不出來，因為 KB 只到 X」是有用的揭露）。

## A11 期間降級揭露：兩個獨立通道，不是一個

**缺口**：`rq.retrieve` 在 Tier 1 落空、降級 Tier 2 時會產生一句揭露，單管線兩邊都接了，agentic 的 `_retrieve_chunks` 寫成 `chunks, _note = ...` **整句丟掉**——於是「系統會不會揭露」在所有 agentic 評測上結構性恆為 0，**量到的 0 是在覆述一行程式碼**。

| 通道 | 做什麼 | 若缺會怎樣 |
|---|---|---|
| **注入 Generator prompt** | 讓生成器知道「這批 chunk 不是你問的那個期間」 | 靜默拿替代期間當原期間答——**有引用、看起來有根據** |
| **顯示給使用者** | 呼叫端印出來（CLI `⚠️` / SSE 事件） | 模型沒照做時使用者完全不知情 |

**注入是機率的，顯示是保證的**——兩個都要。
⚠ **刻意不用「機械式附加到答案尾巴」**：時效警語與口徑揭露是**答案生成完才算得出來的 metadata**，而期間降級是**生成之前就已知的輸入條件**——寫進 prompt 才治得了「靜默替換」。**答案字串不動。**
⚠ **收集點只能有一個**：`_retrieve_chunks` 有五個呼叫點，逐個回傳必然有人漏接 → 收在 `_RunState.period_notes`。跨子問題的去重放在合併層（**逐待辦算、整篇印一次**）。
⚠ **它必須跟著每一次重生成走**（validator 的重生成會換掉 `extra_user`），共 16 個接點。
⚠ **量尺：⑮b 與 ⑮e 不可互相取代。** 最有價值的變異是「呼叫點寫了 `period_note=`、但傳的值永遠是空字串」——AST 驗關鍵字的 ⑮b **全綠**，只有驗**值**真的從 state 流到 Generator 的 ⑮e 叫得出來。**接線鎖要驗的是值不是關鍵字**（這是同一個教訓的第三次）。

## A12 multi_hop 依賴：業界怎麼做，以及本 repo 為什麼那樣接

**動手之前查的**（三篇獨立來源結論一致）：依賴由規劃器**當結構吐出來**，子問題用佔位符指涉前一跳（MuSiQue 的 `#1`、A.DOT 的 `$var_d`）→ 執行前跑**確定性結構檢驗**（必填欄位 → 無懸空引用 → 無環）→ 懸空是 **prune ＋ warning**，不是靜默丟掉也不是整個計畫作廢。
出處：[Agentic DAG-Orchestrated Planner](https://arxiv.org/html/2603.14229v1)、[RAG for Multi-Hop QA Based on Structured Planning](https://dl.acm.org/doi/10.1145/3789506)、[When RAG Meets Query Planning](https://arxiv.org/html/2607.00508)、[Maestro Order](https://arxiv.org/pdf/2606.23983)、[From Agent Loops to Structured Graphs](https://arxiv.org/pdf/2604.11378)。

**本 repo 的三個差異，每個都有理由**
1. **無環檢查不用 Kahn／DFS，用 `0 <= depends_on < id`。** todo `id` 是**依清單位置**指派的，所以這個條件同時保證無懸空、無自環、無環，是 O(n) 的全序檢查。副產品比 Kahn 更有用：**id 0 恆被剪成 `None` ⇒ 永遠至少有一個 ready todo，`_node_execute` 結構上不會 deadlock**。⚠ **2026-09-11 R4 第一次拿到實地驗證**：Planner 真的吐了 `id=4 depends_on=4`（自我依賴），位置規則當場剪掉並留 trace。
2. **「Planner 說沒有」與「Planner 沒說」分成兩個欄位**（`depends_on` ＋ `deps_declared`）。業界論文假設規劃器一律輸出完整計畫，本 repo 不能（既有 fixture 全是加欄位之前的格式），而**沒有這個區分就會退化成「詞表仍然是實際做決定的人」**。
3. **多留了一個有意識的例外**：Planner 宣告 `null` 但子問題字面上沒有主詞時仍然延後——那句話**單獨拿去檢索時沒有主詞**，是**字面事實不是感知**，且代價不對稱。⚠ 這個例外**必須帶分母**（`plan_stats.deps_disagreed`），否則它會變成「詞表從後門回來」。

⚠ **這條路目前在題庫上是量不到的**：`eval_set.json` 的 5 題 multi_hop **候選集合全部寫在題面上**，Planner 正確地扇出、`deps_count` 為 0。實際踩到依賴的是「Magnificent Seven 裡淨利最高的那一家的毛利率」這種形狀，而題庫裡沒有，且造那種題**不可以併進 `eval_set.json`**（分母不可變）。
⚠ **文獻自己指出的天花板**：[Failure Modes in Multi-Hop QA](https://arxiv.org/pdf/2601.12499) 的「weakest link effect」——第一跳錯了整題就錯。實跑當場看到一次（第一跳連跑三輪 `sufficient=False`，top-k 裝不下七家的 Fundamentals）。**那是檢索問題不是依賴問題，不要用依賴機制去補它。**
⚠ **已知缺陷（未修）**：`_fill_dependent_hop` 的 `_DEP_PLACEHOLDER_RE.sub(entity, task)` **會把每一個 `#N` 都換成同一個 entity**（`在 #0、#1、#2 中` → `在 NVIDIA、NVIDIA、NVIDIA 中`）。根因有兩層，只修上面那層沒用：**`depends_on` 是單一 int，結構上表達不了「這一跳依賴三個父 todo」**，而比較型的 hop 天生是多父的。見 BACKLOG。

## A13 重生成鏈的回歸：業界怎麼做，以及為什麼這裡不做迴圈

**問題**：`_node_synthesize` 是六道的修補鏈，每一道抓到就**整篇重生成**。引用有守（每道內部都補跑 citation 稽核），其他不變量沒有——後面那道可以破壞前面那道修好的東西，而**前面那幾道已經跑完、沒有人再看**。碼上的排序是**兩兩推理**出來的，那個論證只在「後面不會破壞前面」時成立。

**查的（四篇）**：整篇重生成會讓先前已滿足的約束被破壞，解法是 targeted correction（[Self-Review Framework](https://arxiv.org/html/2507.05598v1)）；critique↔refine **迴圈**每次 refine 之後重跑全部約束（[DeCRIM](https://arxiv.org/pdf/2410.06458)）；競爭型軟約束會讓管線**震盪**（[Meta Self-Refining](https://arxiv.org/pdf/2507.10590)）；**沒有外部回饋的自我修正常常反而變差**（[Limits of Self-Correction](https://www.preprints.org/frontend/manuscript/b753c9b8a11bbed2b3db90713e4cc83d/download_pub)）。

**本 repo 做的是單向守衛，不是迴圈。三個理由**
1. **成本結構不同。** DeCRIM 每輪 refine 要一次 LLM 呼叫，而這裡一題已燒 50~60 次；相對的，本 repo 的 critique 側**本來就是零 LLM 的偵測器** ⇒ 「重生成之後重算一次全部指紋」幾乎不要錢。**免費的那一半先做，要錢的那一半先量。**
2. **「不會更糟」與「會更好」是兩件事，前者才是這裡的病。** 守衛保證前者（任何一格變差就退回原答案）。
3. **第四篇那條結論站在我們這邊**：本 repo 的回饋是零 LLM 的確定性偵測器，不是模型自我評分。

**⚠ 守衛的判準有三個容易寫錯的地方**（都有誤報對照，閘門㉑）：**逐格比較不是加總**（四格是四種不同的病，加總會讓「修好一個期別錯、引入一個捏造數字」看起來持平）／**相等就接受**（以「沒變好就退回」當判準會把整條修補鏈關掉）／**空的重生成不是退回**（那是 LLM 呼叫失敗，是別的病）。
**⚠ 指紋刻意不含 `find_claim_conflicts`**：它要先跑一次 LLM 抽取，收進來就毀掉「critique 免費」這個前提。代價是**「一致性被重生成破壞」這一型目前量不到也守不到**。
**⚠ 2026-09-10 的 R3 推翻了原本「這條鏈其實沒在互相破壞」的前提**（三輪 24 次重生成有 1 次退回：`lex-03` 的 `untraceable 0→2`）。**決定不變，但理由換了**：守衛零成本地擋下了它 ＝「不會更糟」已有保證；critique↔refine 要買的是**退回之後剩下的缺陷修不修得掉**，而那仍然沒有量尺。
