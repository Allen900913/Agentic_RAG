## A1 架構主線：agency 只給需要決策的角色

**貫穿哲學**：**只有需要決策的角色才給 agency；不需要決策的角色給 agency 就是給它犯錯空間。**

### v2 的價值是確定性 planner 拆解，不是自由迴圈

`multi_intent` 退步的三階診斷，每一階都推翻前一階：

| 階 | 量什麼 | 結果 |
|---|---|---|
| ① | 檔案層 gold 覆蓋 | v2 檢索**不弱反大勝**（28/38 vs 單管線 12/38，嚴格超集）→ 推翻「多源檢索弱」 |
| ② | claim/chunk 層 gold | 真實 v2 只 16/75、**乾淨 decomposition（無 ReAct executor）拿 35/75**、單管線 25/75 |
| ③ | 修法 | **v2 minus ReAct**：executor 改確定性（plan → 每子問題直接 retrieve → commit）＝現況 |

**煙槍在 ② 那一格**：漏水點是 ReAct 執行層亂改 query＋亂搜，**不是** planner 拆解、**不是** doc-type filter。

⚠ **這條結論限於本語料**（結構化 `.txt` ＋ 長文 filing 混合、中型模型）：動態編排自由度是負資產。agentic 真正的舞台是**多跳／開放 web／真路由工具**。

### multi_hop 的依賴解析（新能力，全程無 LLM 改寫）

Type B「識別再查」第二跳帶未解代名詞 → `_is_dependent_hop`／`_resolve_hop_entity`／`_fill_dependent_hop`；`_node_execute` 分波延後 ＋ 實體回填，`_node_replan` 兩道 guard。**確定性回填不幻覺。**
實測 10 題零拒答、實體解析 5/5 命中；multi_hop 是全類最紮實的一類（faith .904／recall .892）。

### 為什麼 Grader（證據後置）不能上移到 Planner

Planner 手上只有 coverage 摘要、**沒有真實 chunk**，只能用猜的；而猜錯的代價**不對稱**（猜「KB 沒有」但其實有 → 整題答不出來）。所以架構刻意把「夠不夠」的判斷延後到 Grader 看見真實候選之後。

## A2 檢索層的共用決定

（實作在 `rag_query.py`，兩條管線共用。）

- **`full_translate_en`**：中文問中文答，但 dense/sparse 召回 ＋ rerank 一律用英文譯句，消除 cross-lingual reranker 對「中文 query × 英文 chunk」評分平坦的問題。agentic `_retrieve_chunks` **固定開**；生產 `rag_query.py` 預設仍 False（跟進與否未決，見 BACKLOG）。
- **`translate_query_en`（舊旗標，只影響 rerank）**：`max(原句分, 英譯分)` 重評、不動召回池。⚠ 曾兩次被誤植成 escalation-only，**勿再犯**。
- **`period_basis` TTM 口徑消歧義**：Fundamentals `.txt` 已含算好的 TTM 比率 ＝ **路由問題非算術**，不該讓 LLM 現算。每 chunk 加 `period_basis` payload（fundamentals→TTM、10-K/Q→fiscal_year）；命中 TTM 詞 → **單向**硬 filter（fiscal_year 有標籤但不硬路由，開雙向前要先跑全量 eval）。
- **`_ensure_ticker_coverage`／`_ensure_ratio_source_coverage`**：確定性保底，**只加不減、零 LLM**。ratio 意圖 commit 後缺該公司 Fundamentals 就補回。**用程式碼保底而非改 Grader prompt／換大模型**——規則可用 metadata 確定檢查的，不交給機率元件每次重推。
  ⚠ 但**掃池的保底救不了「`#0` 連候選名單都沒進」**：生產是英譯 query，實測 `MSFT_Fundamentals #0` 連 RRF 的 20 個候選都沒進（中文原句反而進得去，rank 7）。所以現在是**確定性補撈**（直接查 Qdrant），不是掃池。
- **Planner 的比率期間中性**：修 Plan 把「目前毛利率」釘成「FY2026 Q2 毛利率」→ 帶季度的 query 把 TTM/Fundamentals 整個濾出池、答錯口徑。⚠ **這條 scoping 刻意收窄在「有實測失效」的邊界**：同型的估值比率（P/E、ROE）實測 Planner 本來就保持期間中性、3/3 不釘季度 → **別為不存在的 bug 加規則**。

## A3 一致性 validator：LLM 抽取 ＋ Python 判斷

**分界線**：「確定性 > 勸 LLM」講的是**不要把判斷交給 LLM**，不是不要用 LLM 做抽取。**抽取是感知任務（LLM 強），比對是邏輯任務（Python 可靠）。**

**結構**：`_extract_claims`（CHECKER_MODEL，temp=0）把答案每個數值宣稱抽成 `value/unit/metric/entity/scope/period_key/kind/basis/quote` → `find_claim_conflicts` 跑零 LLM 規則。

### 為什麼 regex 版被整段刪掉

1. **它在用字串比對做感知**——指標靠寫死詞表（「資料中心營收」裡也有「營收」）、主體靠寫死的公司/分部清單（不在清單就抽成空）、並陳靠寫死的措辭清單。而且已被實測抓包：`col-11` 漏抓，原因就是「另一份報告則顯示」不在措辭清單裡。
2. **它從來沒跑過**——觸發條件是「LLM 抽取失敗」，200 份答案的離線量測失敗率是 **0**。等於一段沒被測過、卻要永久維護的死碼。

### 第一版規則太天真，量測直接打臉

agentic 觸發 8 題只有 ~2 個站得住（regex 版是 2/2）。誤報全是抽取器的**系統性樣態**，**修在規則層而不是回去勸抽取器**——因為抽取本身沒錯（把「$330 提升至 $365」看成兩個 level 是正確的，錯的是我拿 level 去比）：

| 排除規則 | 理由 |
|---|---|
| ⓐ `level` 不參與比對（只比 change／growth_pct） | 「從 X 增至 Y」抽出的兩個 level 幾乎都被填同一個 period |
| ⓑ `basis` 進分組 key | YoY 92% vs QoQ 21%、reported 33% vs 固定匯率 29% 是**合法並列** |
| ⓒ 共用同一段 quote 者不比 | 區間「EPS 增加 1 至 3 美元」被拆成兩筆 |
| ⓓ 百分比加總 ≈100 → 佔比不是矛盾 | Reality Labs 支出 70%/30% |
| ⓔ 同格出現 ≥3 個相異值 → 列舉不是矛盾 | `Regional data (+29%, +39%, +40%)` 是四個地區 |

**最終量測（200 份存檔答案）**：LLM 版 **4/4 精準**（regex 版 3/3），且 `col-11` 是 LLM 版獨有的真陽性。

### 「怎麼知道兩個數字在講同一件事」——它不知道，只是無法證明不同

真正扛住正確率的是 **`_ALSO_MARK`**：它抓的不是「我對數字的語意判斷」，而是**生成器自己宣告**「這是同一個指標的另一種說法」。**把不可解的共指問題換成可讀的表面標記。**
- 「指標詞相同」很粗糙，分不出總體與分部；三個「整體 vs 部分」誤報全靠 `_ALSO_MARK` 才沒被殺。
- entity 比較改成**對稱**（`a["ent"] != b["ent"]` 即排除，含兩邊皆空）——擋掉「伺服器產品」誤報，且 3/3 真陽性全保留。
- period 比較**維持非對稱**：改對稱就漏抓 `mix-06`（`period=q vs None`）。

### In-Place Healing 提案：定位可行、裁決無解

**提案**：不重寫整段，改用程式精準定位出錯那一句，只抽換/抹除/標記。

- **① 定位可行，而且不需要 NER**——`_extract_claims` 已經回傳 `quote`。591 條存檔 claim 實測：逐字命中 34.3%，但**正規化空白/全形後 85.1%**（那 51 個百分點純粹是窄不斷行空格與 markdown `**` 的差異）。剩 12~15% 是抽取器真的改寫，但比對不上就 fallback，**可偵測**。再上一個 NER 去重推已經有的東西，只是多一層失敗面。
- **② 裁決：提案沒有處理，而病灶正好落在這裡。** `col-11` 的四組衝突**兩邊都是對的**——19% 是單季、18% 是前九個月。這直接打穿操作集 `{抽換, 抹除, 標記}`：**抽換**沒東西可換進去、**抹除**會刪掉正確資訊、**標記**是唯一活下來的但那等於承認不確定而非修復。真正缺的是**期間限定詞**，那要**插入**文字且要知道哪個數字配哪個限定詞——必須回去讀原文。
- **③ 真正的發現在 ingest 層**：那兩個 chunk 沒有期間標頭，是切塊時把標頭切到別的 chunk 去了。**生成器不是讀錯，是資訊不在 context 裡。** → 見 [`INGEST.md`](INGEST.md) ②。

**判準不是「Python 用得多不多」，是該子任務有沒有唯一正確答案**：抽取＝開放感知→LLM；比對＝封閉邏輯→Python；定位＝給定 quote 的封閉問題→Python；**裁決＝要回讀原文→LLM，而這層現在不存在**。按這個表，Python 沒有太多，是少了一層。

**成本**：每份答案固定多一次 CHECKER_MODEL 呼叫（中位 5.1s，平均抽 4.0 筆宣稱／題）。

## A4 期間接地：讓 validator 看得到原文

`_extract_claims` 原本的 user content 只有 `f"答案:\n{answer}"`——**它看不到任何 chunk，所以無法糾正答案的錯，只能忠實複製**。

**受控實驗**（答案文字固定，只換餵進去的原文）：

| 組別 | 誤報組數（3 輪） |
|---|---|
| ① 不餵原文 | 1 / 0 / 1 |
| ② 餵無期間標籤的原文 | 2 / 1 / 2 ← **比不餵更糟** |
| ③ 餵有標籤的原文 | 0 / 0 / 0 |
| ④ ③ 的同一批 chunks、程式剝掉注入標籤 | 2 / 1 / 0 |

③ vs ④ 是**乾淨對照**——同一批 chunks，唯一差別是那行 `[Three Months Ended…]` 在不在。**效果來自標籤，不是檢索變好。** ② 更糟的原因：原文殘留的章節標題讓抽取器把四筆全套上同一期。**兩層缺一不可，且 ingest 必須先做。**

### 中途走錯一次，記下來

加了「舉證稽核」——要求 LLM 填 `period_evidence`，填不出原文出處就把期間降級成 `unknown`。誤報從 3/6 降到 **0/8**，看起來成功。但補跑真衝突偵測是 **0/5**：**捏造的數字必然在原文查不到 → 必然降級 → R1 永遠抓不到幻覺，而幻覺正是要抓的東西。誤報歸零是因為整層被關掉了。**

→ **正確順序是「先偵測、再用原文駁回」，不是「先降級、再偵測」**；查不到出處要**保留答案自述的期間**。

**收斂版**：期間定位改用**零 LLM 字串比對**（`_ground_period_from_source`）。實測讓 LLM 自己查證，8 輪只有 4 輪真的去查、其餘直接照抄答案。改成 Python 後誤報 5/5 全對、真衝突 5/5 全中，**十輪零變異**。

**`period_key` 取代自由文字 `period` 當同格判準**：實測同一個「截至 3/31 的九個月」被 LLM 寫成過 `2026YTD`／`2026Q1Q2Q3`／`2026Q3`／`unknown` 四種，而 `2026Q3` 還同時被拿去指單季與累計 → **字串比對雙向失效**。`period_months`/`period_end` 直接讀原文標題就有，**不需要換算成財年季度代碼，而換算正是出錯的那一步**。

**限制**：只處理百分比（金額寫法太多：`$2.6 billion`／`$2,600 million`／`26 億美元`，誤配風險高過收益）；擋不掉「查了但查錯」。

## A5 live／web 這條路：四個阻塞點與 eval 隔離的真正來源

**起點**：生產模式問四題時效題，web_search **0/4 觸發**。逐層拆下去發現不是一個 bug，是四個獨立阻塞點疊在一起。

### 阻塞點① 詞表閘門（已整段移除）

`looks_like_news_query` 與 `_RELATIVE_TIME_RE` 都掛在 web 補救判斷式上，都是硬編碼詞表。實測 18 個真實時效措辭，`_RELATIVE_TIME_RE` **漏 10 個**。最諷刺的是「**即時**市值」比「目前」更明確要求即時資料，卻打不到 web。

**漏網的代價不是答不出來，是自信地把舊資料當成即時資料**：

| 答案 | 實際來源 |
|---|---|
| 「特斯拉**今天**股價下跌 2.96%」 | 三週前的新聞檔 |
| 「蘋果**截至目前的即時市值** $4342.02B」 | 兩個月前的 Fundamentals |

三個都零時點揭露。

⚠ **這件事漂移過**：第一次只從 **web 觸發**拿掉那兩道，**時效警語那道漏改**，而文件已寫成「全數移除」，兩天後才發現。**這類「同一個名字出現在兩處、只改了一處」的漏改，`grep` 一次就找得到，值得在宣稱「全數移除」前跑一次。**

### 阻塞點② 生成契約禁止引用 web（這是 binding 的那個）

`rq.SYSTEM_PROMPT` 三條規則合起來讓 web 內容**不可引用因而不可用**：Rule 1「Answer ONLY based on the provided reference materials」、Rule 2 引用格式、Rule 8「**Every number you state must be traceable to a cited chunk**」。

**決定性證據**：接好管線（web 資料確實進到 prompt）後，三次跑分**仍全數退回舊快照的市值**，其中一次寧可拿舊市值除以 10-K 股數**捏造**「每股 $204」——**違反 Rule 8 前半句「Never invent」，只為守住後半句**。一個單純搞不清誰新誰舊的模型會直接抄那個標著 `as of` 的新值；它沒有。**缺的從來不是格式，是許可。**

**修法必須在 system message**。舊版已在 user message 寫「若引用請用 `[web: 網址]`」——**沒用**。拿 user turn 去赦免 system rule 權重太低。

⚠ 順帶：**Generator 一直沒有時間契約**——`_build_temporal_contract` 掛在 Planner／Replanner／Researcher 上，唯獨 `_write_final_answer` 漏接。不是「LLM 沒有時鐘」，是**系統造好了契約卻少接一個呼叫點**。

### 阻塞點③ Grader 不看時效——而且 coverage 讓它更嚴重

`_CHECKER_PROMPT` 的「KB 時間天花板」是為了防無限空轉加的，明文寫「若候選已涵蓋 KB 最新可得資料，即使子問題要求的期間比 KB 更新，也要判 sufficient=true」。**結果 coverage 知識把 Grader 推向判「夠」**：撈到兩個月前的 Fundamentals 就 `sufficient=True`，web 永遠打不到。

**修法刻意不改那段 prompt**（防空轉規則本身還需要），改在 Python 層做時效改判：

| 子任務 | 給誰 | 為什麼 |
|---|---|---|
| 「這題需要多新」 | LLM（`realtime_need` 三態 `intraday`／`days`／`none`） | 沒有唯一正確答案 |
| 「來源多舊」 | Python | 確定性 |

單一天數門檻行不通——「今天股價」容忍 1 天、「最近進展」容忍一週，差一個數量級。改判**只降不升**（只把 true 改 false），不繞過 Grader 原本的離題判斷。

### 阻塞點④「永不過期」被誤用成「能證明夠新」

`_source_newest_date` 把 10-K 的 4 碼財年戳一律算成該年 12/31 → `MSFT_10K_2026` → **2026-12-31（未來日期）**，而 `_stale_for_realtime` 取全池 `max(dates)`。**於是財報不只是棄權，它替整個候選池背書說「夠新」。**

這個混淆在 KB 有新聞時無害（池裡有真實日期的新聞 chunk 壓著 max）；**新聞拔掉後財報成了唯一日期來源，洞就露出來了**——實測 6 個即時類問題有 4 個時效改判不會觸發，含 intraday 股價題。

⚠ **4 題裡只有 1 題是拔除新聞造成的**。另外 3 題（含最危險的「微軟現在的股價是多少？」）**從來沒被那道詞表路由攔過 ＝ 洞一直都在**。

**修法**：`_is_freshness_evidence(source)`——**只有 8 碼真實日曆日期算證據**。4 碼財年／6 碼財報期間**不算證據，也不算過期**，單純不參與這個判斷。`_kb_ceiling_date` 必須套用**同一套資格判準**。

⚠ **這推翻了一個先前刻意的成本判斷，理由是算式反轉了。** 舊註解寫「誤判過期會叫 web 白跑一趟，誤判新鮮只是維持現狀」——**那句話在 KB 有新聞時成立**（維持現狀＝用幾天前的新聞回答）。KB 只剩財報之後，「維持現狀」＝**拿 10-K 回答今天股價**，成本大得多。

⚠ **這個 bug 的兩個真實代價**：① `kb_unfixable` 恆為 `False` → 每個子問題白燒 `MAX_REWRITES` 輪改寫 ② **第二道防線被靜默關閉**（LLM 若判錯 `sufficient=True` 就沒有東西接得住）。
⚠ 但**不等於 web 不會被叫**：那 4 題舊碼下 web 一樣會觸發，因為 Grader 自己就判 `sufficient=False`。**主防線是 LLM 判斷，時效改判是第二道。** 第一版把元件失效報成了系統失效，**這是〈稽核回報 FAIL，先問是不是量尺錯〉的鏡像**：確認缺陷時要問「這個失效傳得到端到端嗎」。

### eval 隔離的真正來源（別再誤認）

三道詞表／相關性閘門**都不是隔離機制**。隔離只靠兩個獨立條件，各自都足夠：

| 條件 | 角色 |
|---|---|
| `freshness_mode == LIVE` | eval 預設就是 `snapshot` |
| `ENABLE_WEB_SEARCH` | `--no-web` 設 False |
| `not verdict["sufficient"]` | **生產端擋濫用**，不是隔離 |

更根本的一點：**eval 裡沒有任何一題需要 KB 以外的資料**。snapshot 模式把「最新」重新定義成「KB 中最新可用資料」。web 在 eval 中不是被擋掉造成損失，而是**根本用不上**。
⚠ 但 eval **不保證檢索找得到**——eval 消除的是「時間上搆不到」，不是「檢索搆不到」。

常駐證明：[`../eval/verify_web_gate_isolation.py`](../eval/verify_web_gate_isolation.py)（六道閘門 79 項）。其中兩項是 **byte-identical 斷言**（無 web 時 system message 逐字不變、snapshot 的 Checker prompt 不含新欄位）——**那是 eval 基準不被動到的證明**。

### 來源白名單（放行 web 引用的必要配套）

放行「web 數字可引用」而不管來源品質才是危險組合。`WEB_ALLOWED_DOMAINS` 分兩類：原始揭露方（SEC／交易所／IR 站／stockanalysis）與有編輯流程的財經媒體。不收論壇與意見文。
**白名單濾空時明確回報查無、不退回全網**——靜默 fallback 等於白名單沒生效卻沒人知道。
⚠ 這是**授權清單**不是感知詞表，與「硬編碼詞表是警訊」不衝突：它不試圖理解內容，只決定哪些來源准進來。

### 量測教訓：n=1 測不出這條路的任何東西

八題各跑一次的回歸裡，兩題看起來明顯退步。**各補跑 2 次後兩個都被推翻**——重跑中都產出了比修法前更好的答案。**答案品質的 run-to-run 變異大於單次測試的解析度**，而且 web 又多疊了一層隨機性（Tavily 每次回的東西不同）。

## A6 web 檢索層的九個缺陷：主因是自己截掉摘要

### 主因：`content[:300]`

trace 印出的摘要是 `Apple market cap as of Augus`。完整原文是 `as of August 07, 2026 is $4572.79B`。Tavily 的 `content` 實測 596~1982 字，而**數據頁的數字排在站台樣板文字之後**（導覽列、登入、幣別切換、廣告）。**300 字正好切在數字前一個字。資料一直都在。**

⚠ **這件事的可觀測性教訓比修法本身重要**：「Tavily 沒撈到那個數字」與「撈到了但被自己截掉」在只印 `→ 2163 chars` 的舊 trace 裡**長得一模一樣**。同一課後來又上了一次——只印域名不印網址，導致看不出 Reuters 的日期為何抽不到（日期在網址**結尾**）。

### Tavily 的能力邊界（決定架構的那組實測）

| 模式 | `published_date` | 日期過濾 | 數據頁 |
|---|---|---|---|
| 預設／`topic="finance"` | 無 | 無 | **有**（macrotrends／stockanalysis／companiesmarketcap） |
| `topic="news"` ＋ `days=N` | **有** | **真的生效** | **全消失** |
| `start_date`／`time_range` | 無 | **靜默忽略** | 有 |

即時報價／市值題要的正是數據頁，所以**不能**為了拿日期切到 news 模式。結論：走預設 topic ＋ `search_depth="advanced"`，日期靠網址推斷。

### 另外五個缺陷

- **D2 單一域名壟斷**：`companiesmarketcap.com` 用五種幣別變體吃掉全部 5 個名額，五則內容相同且都不含目標數字 → 整次搜尋作廢。修法：先撈 12 則、單域名上限 2。
- **D3 無日期**：2020 年的報導與今天的值並列。修法：抽網址日期、濾明顯過時，並把日期**標進 prompt** 讓生成端自己排序。**抽不到日期的一律保留並標「未標示日期」**：數據頁沒有日期，而數據頁正是即時題最需要的。
- **D5 同頁多變體**：`/amp/`、`new.` 子網域、`http://` 各佔一個名額。
- **D6 地區子網域＝別的市場的報價**：`ca.finance.yahoo.com/quote/TSLA.NE`（加拿大 NEO）、`cn.wsj.com`。**與 `apple.com` 收進 `apps.apple.com` 是同一個缺陷類**：Tavily 的 `include_domains` 是子網域包含式比對。改不了它，就在收到結果後自己再複核一次（只認 exact ＋ `www.`）。
- **選擇權合約頁**：`finance.yahoo.com/quote/TSLA260814C00257500` 是買權不是股票，頁上的價格是權利金。與地區子網域同一類（**拿到的是別的標的**），差別在前者是主機名、後者是路徑。修法用 OCC 標準格式（`{代號}{YYMMDD}{C|P}{8 位履約價}`）——**格式定義的封閉集合**。
  ⚠ 同類但**未解**的是外國掛牌**路徑**（見 [`../BACKLOG.md`](../BACKLOG.md)）。

### D4 web 呼叫無上界：計數器放錯層

實跑 7 次 web call，而 `WEB_SEARCH_MAX_CALLS = 3`。原因是它記在 `_RunState.web_calls`，而 `_RunState` **每個子問題歸零**——「上限 3 次」的真實語意是「每個子問題 3 次」。

子問題為什麼會長到 7 個：時效改判讓子問題**恆為** `sufficient=False`，而 **KB 檢索在物理上不可能修復「KB 太舊」**，於是每輪 replan 都再加一個措辭更強調「請上網」的同義待辦。兩個修法：
1. `kb_unfixable` 旗標 → 執行層立刻跳出改寫迴圈（21 次檢索降到 4 次）。**這是結構性的**：只要「不足的原因是資料不在 KB 裡」就適用。
2. `QUERY_WEB_BUDGET`（query 級、上鎖、只在 graph 入口歸零）→ 封住總成本。

#### `kb_unfixable` 的誤殺，與「候選池 ≠ KB」

第一版只看 `_stale_for_realtime()`，而那量的是**候選池**裡最新那筆。**池子裡最新是 62 天前，不代表 collection 沒有 3 天前的**——很可能只是這輪措辭沒命中它。那種情況改寫真的有救，卻被當成「沒救」跳過。

修法是靠一個**與 query 無關**的量：`_kb_ceiling_date()` 從 coverage map 取「這些 ticker 在整個 collection 裡最新到哪一天」。

| 候選池最新 | collection 天花板 | 判定 |
|---|---|---|
| 過期 | 也過期 | `kb_unfixable=True` — 再檢索還是同一批檔案 |
| 過期 | **夠新** | `kb_unfixable=False` — 是**這次檢索沒撈到**，保留改寫機會 |
| 夠新 | — | 不改判 |

- **天花板與候選池共用同一個日期算法**。兩邊若用不同算法，比出來的大小沒有意義。
- **coverage 掃不到時保守當 `True`**：無法證明「還有更新的」就不宣稱可修。

⚠ 判斷邏輯抽成 `_classify_staleness()` 而不是留在 `_check_sufficiency()` 裡，**唯一理由是可測**：內嵌在 LLM 回傳處理裡的分支，**閘門碰不到就等於從沒被證偽過**。

### 被自己推翻的修法：用字串相似度認同義待辦

**實測分離度是負的**：

| | jaccard | containment |
|---|---|---|
| 正向（同一需求）**最低** | 0.04 | 0.17 |
| 負向（不同需求）**最高** | **0.50** | **0.70** |

最糟的負向是「蘋果的即時**市值**」vs「蘋果的即時**本益比**」——不同需求、字面幾乎一樣；而正向的「蘋果的即時市值是多少？」vs「即時網路搜尋 Apple 最新市值」只有 0.04。**沒有任何門檻能分開這兩類。** 整段撤掉，改成不判語意、只封成本——**能封住成本就不需要判斷語意**。

### 兩個追加：規則寫反了，以及警語與答案自相矛盾

**① 修訂條款的排序規則原本是反的。** 日期標進 prompt 之後，「特斯拉今天股價」把一則 **22 天前**的報導當成「最新可得」，反把**未標日期的即時行情頁**降為次要。機制沒壞——日期確實抽到了。錯的是規則本身：「以標示日期最新的來源為準」。
**對「當下數值」類問題，這個偏好是反的**：持續更新的行情頁（沒有日期）才是今天的值，有日期的報導講的是那一天的事。
→ 修訂條款按問題類型分岔；`WEB_STALE_DAYS["intraday"]` 90 → **7**。**問當下數值時，任何有日期的舊報導都不可能是答案，留著只會製造更好聽的錯誤。**

**② 時效警語與答案自相矛盾。** 答案主體引用了兩個 web 來源，底下卻印出「**Web 未提供可用補充**」。成因是 scope 錯配：缺口是**逐待辦**算的，而警語**整篇只印一次**。
**警語與答案互相矛盾比沒有警語更糟**——它會讓讀者不信任明明有出處的數字。修法是依「這一次跑分到底有沒有用到 web」分岔措辭。

## A7 live web 的可重現評測：把不確定性切開，而不是硬定 gold

**問題**：live web 沒辦法定 gold（資料每天在變），所以 A5／A6 做的整套機制在 eval 裡**執行次數是 0**（snapshot 恆關），唯一的證據是 n=1 實跑軼事——而 A5 自己就寫過「n=1 測不出這條路的任何東西」。

### 切法：確定性的與含 LLM 的分開，各用各的量尺

| 部分 | 用什麼測 | 為什麼 |
|---|---|---|
| 白名單／去重／單域名上限／日期算術／預算／`kb_unfixable` | `verify_web_gate_isolation.py` 六道閘門 79 項 | **零 LLM、零網路、零 Qdrant、秒級**。已經有了，**不重測** |
| Generator 有沒有真的引用 web 數字、衝突時有沒有並陳並標時點 | `web_replay.py` fixture ＋ `check_web_claims.py` 逐條斷言 | **必須含 LLM**，所以必須固定輸入 |

「VCR 只為了測預算／白名單有沒有生效」是**重複投資**。fixture 的價值在**解鎖含 LLM 的端到端路徑**，這是唯一新增的能力。

**為什麼不用 RAGAS**：這條路只有 5 題，MDE 換算約 **0.17~0.21**——任何分數都落在噪音裡。判準改成零噪音的逐條斷言，PASS／FAIL／**N-A** 三態。

### 四個設計上的坑（每一個都會讓 fixture 失效而不自知）

**① 錄的層級。** 必須錄 `TavilyClient.search()` 的**原始回應**，不能錄 `_tavily_search()` 的回傳字串——後者是跑完白名單複核 → 去重 → 單域名上限 → 抽日期 → 過時過濾 → 摘要截斷之後的成品。**錄在那裡等於把要測的六道一起 mock 掉。**
> 驗證方式：拿一份人工 fixture 塞進地區子網域＋非白名單主機＋amp 變體，確認下游照常濾掉（實測 5 筆原始 → 保留 1 筆）。

**② `get()` 與 `put()` 兩邊都要 deepcopy。** 下游會就地寫 `r["_pub_date"]`。
- `put()` 少 → 快取被塞進 `date` 物件 → 落盤 `TypeError`。首次錄製**安靜掉了第 8 筆**：atexit 的例外只印 traceback、**不影響 exit code**，看起來成功。
- `get()` 少 → **更嚴重**：同一 key 重放第二次時日期已被上一次塞好 → 抽日期那段**根本不執行**，兩次重放走不同程式路徑，**fixture 就不再是「固定輸入」**。
- 連帶：序列化失敗要在 `put()` **當場炸**（獨立型別並由呼叫端 re-raise），否則會被 `_tavily_search` 的優雅降級吞成「web 查無結果」。

**③ 只錄 web 不夠，要連 `llm_replay` 一起錄。** 送給 Tavily 的 query 是 Planner／Grader 的 LLM 輸出決定的，而 MoE 溫度 0 不固定專家路由 → 重放時會生出不同的 web query、直接 fixture miss。

**④ 斷言不能寫死成某一次錄製的答案。** 錄製時 LLM 引 stockanalysis 的 `$4.46 兆`、重放時引 finance.yahoo 的 `$4.45 兆`——**兩個都在 fixture 裡、都正確**。**fixture 是一個值空間，不是單一答案。** 斷言只能測「不論它挑哪個都必須成立」的性質：有沒有引用**任何** web 來源／主機是否都在白名單且非地區子網域／**答案裡每一個報價都必須在 fixture 原始內容裡逐字出現**（零幻覺斷言，最強的一條）／KB 舊值與其時點是否與 web 新值並陳。

> 附帶：驗收腳本第一版**自己誤報三題 FAIL**，因為正則只認 ASCII `[web:]` 而模型吐的是全形 `【web:】`。

### 驗收與判別力

兩次**獨立取樣**跑同一組斷言都 5/5 PASS。照「全綠先當壞消息查」的紀律，注入六種變異確認抓得到 → **6/6 全被抓到**。
> 最後那一種（**只竄改其中一個**股價）是加上零幻覺斷言之後才抓得到的：原本只要求「有一個價格形狀的數字」，改了一個仍有其他正確值留著就漏。

⚠ **「斷言零噪音」不等於「結果零噪音」。** 斷言本身確實是確定性的，但**產生結果檔的那一步有 LLM 取樣變異**。`5/5 PASS` 的正確讀法是「**這一次取樣**沒問題」，不是「這個系統不會出問題」；要提升信心只能多取樣，**重跑檢查器沒有用**。

⚠ **而且斷言的 FAIL 也可能是量尺錯。** 第四次取樣的 FAIL 說「平均股價 $196.82」是憑空生成——**是誤報**：fixture 表格裡有 `196.8165`，答案是**正確地四捨五入**。我拿那個 FAIL 當真陽性，寫了一整條 BACKLOG、一段 CHANGELOG、一節 docs，才在實作生產版檢查時發現。
→ **「稽核回傳 0 筆問題先當壞消息查」需要一個鏡像條款：稽核回報 FAIL，也要先問「是不是量尺錯」。** 兩個方向的成本一樣低（一次 `grep`）。

### live 專屬的引用缺陷（37 題驗收時抓到）

5 題的答案含 **`【Reference 7, chunk #15】`** 這種標記——不是檔名、不是網址，**指向不存在的東西**。三件事讓它從「格式瑕疵」變成真缺陷：
1. **那 5 題的有效 KB 引用是 0**。不是「多了一個壞引用」，是**整份答案沒有任何可追溯的出處**，而答案裡有大量財報數字。
2. **這是 live 專屬的**：同一套程式，snapshot 路徑 **0/100**、live 路徑 **5/37**。
3. **validator 有抓到，只是放它過去**：判成捏造 ID → 丟回重寫，但重試上限用完就 `break` 然後**原樣 return**。
   ⚠ 而該處的 trace 寫的是「重試耗盡，**走機械式收尾**」——**當時程式裡沒有任何機械收尾**。**註解描述了一個不存在的行為，這比沒有註解更糟。**

**修法**：`Reference N` 的編號**是我們自己給的**（`rq.build_user_prompt` 產生 `[Reference i+1: source, chunk #idx]`），所以 `N → allowed_chunks[N-1]` 是**確定性映射**，屬於 Python 那一半。

**重點是兩個守門條件，不是修補本身**：① `N` 超出候選範圍 → 不動；② 引用裡的 `chunk #M` 與第 N 筆的 `chunk_index` 不一致 → 不動。
理由是**失敗方向不對稱**：漏修 ＝ 維持現狀；而猜錯 ＝ 把「無法追溯」變成「**看起來可追溯的錯引用**」，讀者會相信它。
> 條件② 還有一個副作用：**它讓「排序假設」不必被證明**——兩半一致時那筆修補是被資料自己確認過的。

⚠ 三向變異測試裡最危險的一條是 **`Reference 0`**：Python 的 `[-1]` 是合法索引，少了範圍守門它會**安靜地**指到最後一筆，而其他越界值反而會當場炸。**會吵的那種比較安全。**

## A8 期別稽核：答案自稱「最新一季」卻引用了較舊的期別

### 一次誤診值得先寫下來

第一份根因分析每一步都對，結論卻錯：Grader 判 `realtime_need="none"` → `_stale_for_realtime` 短路 → 「KB 補不了就去 web」被單點守住 → **結論：該把相對期間指稱拆成獨立的軸**。

前面的機制描述**是真的**（見 BACKLOG）。錯在把這一題當成它的證據：把 coverage 印出來才發現 `MSFT_10K_2026` 的 stamp 是**財年**不是日曆期末，該檔實際涵蓋到 2026-06-30、距 as-of 只有 46 天。**KB 一點都不缺，按那個修法會把一題 KB 明明答得出來的問題送上網。**
> 這是〈web 這條路的診斷成本主要在觀測性〉的又一次印證：**先把要判斷的東西印出來，再猜成因**。這次「印出來」只花了一次 Qdrant scroll。

### 真正的缺陷

MSFT 最新一季是 Q4 FY2026，它**沒有獨立的 10-Q**（被包進 10-K）。系統把「最新一季」解析成「候選裡最新的那份 **10-Q**」，而不是「該公司在證據集合裡最新的**期別**」。更新的 10-K chunk 就在 commit 集合裡、rerank rank 4，沒被引用，答案也沒說「最新單季 KB 沒有獨立揭露」。

### 三個設計決定

**① 判準看答案，不看問題。** 判「使用者是不是在問最新一期」要嘛加詞表（換措辭就漏），要嘛在 Grader prompt 加欄位——但那會動到 snapshot 的 Checker prompt，破壞「eval 基準逐字不變」。轉個角度：**答案寫出「最新一季」時，它就是在做一個宣稱**，而「你引的是不是證據裡最新的一期」是純比對。**這是驗證答案自己的宣稱，不是猜使用者意圖** → 誤報風險低，漏判只是維持現狀。

**② 排序不能用 `_source_newest_date()`。** 它把 `TICKER_10K_YYYY` 一律算成該年 12/31（刻意高估新鮮度），而各家財年結束月份不同：

| | `_source_newest_date` | `(fiscal_year, fiscal_period)` | 實情 |
|---|---|---|---|
| `MSFT_10K_2026` vs `MSFT_10Q_202603` | 12/31 > 03/31 ✅ | (2026,FY) > (2026,Q3) ✅ | 10-K 較新 |
| `NVDA_10K_2026` vs `NVDA_10Q_202604` | 12/31 > 04/30 ❌ | (2026,FY) < (2027,Q1) ✅ | **10-Q 較新**（NVDA 財年 1 月底結束） |

期別欄位不在 `rq.retrieve()` 回傳的 chunk dict 裡，靠**擴充 coverage 掃描的同一次 scroll** 建 `source → (fiscal_year, fiscal_period)` 表——比改全專案共用的 retrieve 投影安全。

**③ 每家要比兩輪。** 只比「全期別最新」會漏，而且是**修好第一輪之後重生成的答案自己暴露的**：它照指示引了 10-K 並說明「全年 41%、未拆單季」，卻拿 FY2026 Q2 當「最新單季」，而 Q3 就在證據裡。**「最新一季」問的是最新的「季」，10-K 過關不代表季別選對。**

### 宣稱詞辨識：窮舉清單在同一次迭代內就漏了兩個

第一版寫成 `最新一季|最新季度|最新財季|…` 的窮舉。修正後重生成的答案寫的是「最新**單季**」與「最新公布的**季報**」——**兩個都不在清單裡，validator 對自己造成的新問題視而不見**。
改成「錨詞（最新／最近）＋ 5 字內期別詞，中間不許有數字」；數字那條讓「最新的 2026 年財報」這種**絕對期間**不誤觸。

> 這比一般警告更具體：**窮舉措辭必漏，而且往往漏在你自己下一輪產生的措辭上。** 詞表能用的前提是「**錨詞 + 結構**」而不是「列舉實例」，且失敗方向要釘在漏判側。

### 時效警語同步從「看問法」改成「看結果」

原本用兩個詞表**串聯**決定要不要產生時效缺口 → 有「最新」卻不是新聞措辭的題**一句警語都不會印**。改成看**這個子問題實際 commit 了誰的 chunk**。零詞表，而且更準——問法像新聞、答案其實全靠財報時，舊版會印一句無關的警語，新版不會。

⚠ **後來 KB 拔除新聞，這個判準又整個失去指涉對象**（`_news_freshness_gaps` 恆回空 → 警語永遠不印），而風險沒有消失只是換了位置：即時題 → 去打 web → **預算用完或搜不到** → 回頭用財報 chunk 生成 → **零揭露**。使用者看到一段自信的「目前市值」，底下引用的是 10-K。
新判準是「**這個子問題需要即時資料（`realtime_need != none`）卻沒拿到 web**」。
> **教訓：拔掉一個資料來源時，要檢查的不只是「誰會壞」，還有「誰的判準會失去指涉對象」。後者不會拋錯、不會 FAIL，只會安靜地永遠回空。**

⚠ 這一組的**陰性對照是「財報題 → 零缺口」**。少了它，一個「一律產生缺口」的實作也會全綠，而那會讓時效警語印在每一道財報題底下——警語與有出處的數字互相矛盾，**比沒有警語更糟**。

## A9 R4：web ↔ 財報衝突要求「並陳」而不是「裁決」

**缺口**：`find_authority_conflicts`（R3）只看 `chunks` 的 `src_types`，而 live web 的內容走 `web_extra` **字串**、不是 chunk → 只出現在 web 的數字拿到空的 `src_types` → R3／R4 一律跳過。

**為什麼不擴充 R3**（這是整條的核心判斷）：R3 的動作是「**判新聞那個為錯**」。那對 KB 新聞成立——它在構造上就是舊的。**web 不是這樣**：它可以合法地比任何 filing 都新（盤中報價、8-K 事件、財報已發布但 10-Q 未申報）。宣告「財報永遠對」會讓系統**系統性地報舊數字**。
⚠ `_consistency_check_and_fix` 的 docstring **早就寫下「把 web 併進去會改變 R3 的語意」**——那句話是對的，只是結論該是「新增一條動作不同的規則」而不是「所以不做」。

**R4 的動作**：同一格出現互斥數值、一邊只在 web、另一邊在財報 → 要求答案**兩個都講、各自標出處與時點**。兩邊都已標出處 ＝ 模型已經並陳了 → 沉默。

**為什麼「並陳」在誤報下是安全的**（選這個動作而不是裁決的主要理由）：最大的誤報來源是「同一指標、不同期間」（`period` 刻意不入 bucket key，因為 web／新聞幾乎不標精確期間）。而誤報時要求模型做的事是「把兩個值連同各自的時點講清楚」——**那對不同期間的兩個值本來就是正確行為**。裁決型規則沒有這個性質：判錯一次就是把對的數字刪掉。
⚠ 所以真正會出事的方向不是漏抓，是**話太多**（每個財報題底下都掛一段要求並陳）。

**能力上界**（寫清楚免得被當成保證）：claims 是從**答案**抽的，所以 R4 只看得到「答案自己講了兩個互斥的值」。答案只講其中一個、而另一個來源有不同值的情況**看不到**。

**順帶修掉的一個洞**：`_ground_source_type` 原本開頭是 `if not chunks: return`，於是「候選池空、只有 web」——**那正是 live 路徑的常見形狀**——整個跳過 grounding。

## A10 Synthesize 的 validator 疊法與共用守門

生成後依序跑：`_validate_and_fix_citations` → 一致性（R1~R4）→ 期別 → reflect → 數字溯源。

**順序不是隨意的**：
- 一致性放在 reflect **之前**，讓 reflect 稽核的是已調和過的版本。
- 期別放在一致性**之後**：期別改對可能連帶換掉數字，要讓 reflect 稽核最終版本。
- **數字溯源放最後**：它是唯一會看 reflect 重生成結果的檢查。

### 四道守門共用 `rq.looks_like_refusal`

⚠ 舊版寫成 `answer.startswith("I don't have enough")`——**英文字面、只認開頭**，而 Writer 講中文。中文拒答整句穿得過去，於是一份剛說自己沒有依據的答案，還會付 `_extract_claims` ＋ `_reflect_and_fix` **至少兩次 LLM 呼叫**去稽核一個沒有東西可稽核的對象。

⚠ **危險方向不是漏判而是判過頭**：真的有依據的答案被當成拒答 → 四道 validator **一次全部跳過** → 一致性／期別／數字溯源的保護同時消失。`REFUSAL_MAX_CHARS = 150` 的長度上限就是擋這件事的（**長的誠實答案不算拒答**）。

⚠ 同一個守門寫錯出現過**兩個消費端**：引用尾巴那次只改了尾巴，這四道漏改。**閘門⑭a 因此是逐個 validator 走 AST 驗，不是字串 grep**——改三道漏一道要叫得出來。

### 拒答不得附「📚 引用來源」

那段尾巴宣稱「Generator 實際依據的 chunk」，印在一份剛說自己沒有依據的答案底下就是**假的宣稱**。實測既有結果檔 4175 份答案／59 份拒答，**21 份帶著引用尾巴出貨**。

⚠ **但 `looks_like_refusal` 裡的 `strip_evidence_tail` 不能因此拿掉**：`_node_synthesize` 在 collected/web 皆空時走的是另一條路（拒答 ＋ 時效警語，live 才有），**不經過 `_compose_answer_tail`**。那個 ⚠ 尾巴是**該留的**（「答不出來，因為 KB 只到 X」是有用的揭露），所以要留的是尾巴，**該留的也是 strip**。

## A11 期間降級揭露：兩個獨立通道，不是一個

**缺口**：`rq.retrieve` 在 Tier 1 嚴格 filter 落空、降級 Tier 2 時會產生一句揭露（「知識庫沒有 X 在
所詢問財年（Y）的資料，以下回答改用最接近的可得期間（Z）」）。單管線兩邊都接了，agentic 的
`_retrieve_chunks` 寫成 `chunks, _note = ...` **整句丟掉**——於是「系統會不會揭露」在所有 agentic
評測上結構性恆為 0，**量到的 0 是在覆述一行程式碼**。

### 揭露是兩件事，要分兩個通道做

| 通道 | 做什麼 | 若缺會怎樣 |
|---|---|---|
| **注入 Generator prompt** | 讓生成器知道「這批 chunk 不是你問的那個期間」 | 靜默拿替代期間當原期間答——**有引用、看起來有根據** |
| **顯示給使用者** | 呼叫端把它印出來（CLI `⚠️` / SSE 事件） | 模型沒照做時使用者完全不知情 |

**注入是機率的，顯示是保證的**——兩個都要，缺一不可。這正是單管線的做法（`build_user_prompt` 的
第三參數 ＋ `print(f"⚠️  {fallback_note}")`），agentic 只是把同一組接回來。

⚠ **刻意不用「機械式附加到答案尾巴」**（時效警語與口徑揭露那個做法）。理由是兩者的性質不同：那兩段
是**答案生成完才算得出來的 metadata**（用了誰的新聞、引到哪個口徑），而期間降級是**生成之前就已知的
輸入條件**——寫進 prompt 才治得了「靜默替換」，附在尾巴只治「使用者不知情」。附加還有兩個代價：
與模型自己在開頭寫的那句重複，以及動到既有結果檔的答案文字。**顯示由呼叫端負責，答案字串不動。**

### 收集點只能有一個

`_retrieve_chunks` 有五個呼叫點（ReAct 工具、確定性迴圈、兩處例外降級、graph 崩潰降級）。逐個回傳
必然有人漏接，所以收在 `_RunState.period_notes`——**與 `web_notes` 同一個形狀、同一個理由**。
跨子問題的去重放在 `_node_execute` 的合併層：多個子問題問同一家同一年會產生逐字相同的句子，而這句話
整篇只該講一次（同 `_format_unresolved_freshness_notice` 的教訓：**逐待辦算、整篇印一次**的東西，
措辭與去重都要在合併那一層處理完）。

⚠ **它必須跟著每一次重生成走**，與 `web_extra` 同一條規則：validator 的重生成會換掉 `extra_user`，
寫在那裡的話揭露只活到第一次生成。五道 validator ＋ 它們內部回頭呼叫的 citation 稽核共 16 個接點。

### 量尺：⑮b 與 ⑮e 不可互相取代

閘門⑮ 的變異測試 5/5 全抓到，其中最有價值的一條是 **M3「呼叫點寫了 `period_note=`、但傳的值永遠是
空字串」**——⑮b（AST 驗每個呼叫點都帶了關鍵字）**全綠**，只有 ⑮e（monkeypatch 驗**值**真的從
state 流到 Generator）叫得出來。
> **接線鎖要驗的是值不是關鍵字**——這是 ⑧g（呼叫端引數被重構掉）、⑭a（改三道漏一道）之後同一個
> 教訓的第三次。三次都是「量尺自備輸入 → 從來沒驗過生產供不供得出那個輸入」的變形。

## A12 multi_hop 依賴：業界怎麼做，以及本 repo 為什麼那樣接

**2026-09-06 動手之前查的**（三篇獨立來源結論一致）：

| 做法 | 出處 |
|---|---|
| 依賴由規劃器**當結構吐出來**，子問題用佔位符指涉前一跳（MuSiQue 的 `#1`、A.DOT 的 `$var_d[.c]`、`#TaskN`） | [Agentic DAG-Orchestrated Planner](https://arxiv.org/html/2603.14229v1)、[RAG for Multi-Hop QA Based on Structured Planning](https://dl.acm.org/doi/10.1145/3789506)、[When RAG Meets Query Planning](https://arxiv.org/html/2607.00508) |
| 執行前跑**確定性結構檢驗**：必填欄位 → variable hygiene（無懸空引用）→ 無環（DFS／Kahn） | [A.DOT 附錄 C](https://arxiv.org/html/2603.14229v1)、[Maestro Order](https://arxiv.org/pdf/2606.23983) |
| 懸空引用是 **prune ＋ warning**，不是靜默丟掉、也不是整個計畫作廢 | [Maestro Order](https://arxiv.org/pdf/2606.23983)、[From Agent Loops to Structured Graphs](https://arxiv.org/pdf/2604.11378) |
| 依賴順序執行；第二跳把佔位符換成第一跳解出的實體 | 同上三篇 |

**本 repo 接法與業界的三個差異，每個都有理由：**

1. **無環檢查不用 Kahn／DFS，用 `0 <= depends_on < id`。** 本 repo 的 todo `id` 是**依清單位置**
   指派的，所以「只能依賴排在自己前面的」同時保證無懸空、無自環、無環，是 O(n) 的全序檢查。
   副產品比 Kahn 更有用：**id 0 的 `depends_on` 恆被剪成 `None` ⇒ 永遠至少有一個 ready todo，
   `_node_execute` 結構上不會 deadlock**。

2. **「Planner 說沒有」與「Planner 沒說」分成兩個欄位**（`depends_on` ＋ `deps_declared`）。
   業界的論文假設規劃器一律輸出完整計畫，本 repo 不能——`llm_replay` 裡錄的既有 fixture 全是
   加欄位之前的格式，而**沒有這個區分就會退化成「詞表仍然是實際做決定的人」**，那是 repo 自己
   記過的 `_RATIO_INTENT_RE` 形狀（CLAUDE.md〈LLM 與 Python 的分工〉最後一條）。

3. **多留了一個有意識的例外**：Planner 宣告 `null` 但子問題字面上沒有主詞時仍然延後。
   理由不是「詞表比較準」，是那句話**單獨拿去檢索時沒有主詞**——那是字面事實不是感知；
   而代價不對稱（多等一個 wave ↔ 無 ticker 的破檢索）。
   ⚠ 這個例外**必須帶分母**，否則它會變成「詞表從後門回來」：分歧記進
   `plan_stats.deps_disagreed`，日後拿不拿掉它靠那個數字。

**⚠ 這條路目前在題庫上是量不到的**：`eval_set.json` 的 5 題 multi_hop **候選集合全部寫在題面上**
（「在 A、B、C 三家中」），Planner 正確地選擇扇出、`deps_count` 為 0。實際踩到依賴的是
「Magnificent Seven 裡淨利最高的那一家的毛利率」這種**候選集合不在題面上**的形狀，而題庫裡沒有。
造那種題**不可以併進 `eval_set.json`**（分母不可變），要走獨立斷言集。

**⚠ 文獻自己指出的天花板**：[Failure Modes in Multi-Hop QA](https://arxiv.org/pdf/2601.12499) 的
「weakest link effect」——第二跳做得再對，第一跳錯了整題就錯。實跑當場看到一次：
「七家裡淨利最高的是哪一家」第一跳連跑三輪都 `sufficient=False`（top-k 裝不下七家的 Fundamentals），
解出的實體是 `Apple`。**那是檢索問題不是依賴問題**，不要用依賴機制去補它。
